# 《超级圣杯战争》抽卡数值挂机游戏 — 玩法与模块设计方案

> 版本：v1.0（设计阶段）｜平台：H5 网页（移动端竖屏优先，兼容桌面与微信内置浏览器）｜技术栈：Vue 3 + TypeScript + Vite + Pinia + Canvas 2D 自研战斗渲染器
> 本文件为实现前的最终设计基线，实现者请以此为准；开放决策集中在 §17，均不阻塞 Phase 0–2 开工。

---

## Summary

**目标**：做一款以"抽卡收集全球历史名人"为驱动的**数值成长型挂机游戏**。玩家抽取英灵、编成小队、挂机自动推关，通过等级/星级/技能/遗物/羁绊五条养成线把战力推高，周而复始。

**范围**：H5 网页版，竖屏移动端优先；核心可玩闭环（抽卡 → 养成 → 编队 → 挂机推关 → 离线结算）完整；首发**不含真实充值**，用游戏内货币 + 兑换码跑通抽卡经济；美术走**占位图 → AI 生图**两阶段。

**关键设计决策**（详见各章）：

1. **双标签角色体系**（五行相性 × 五维定位），替代 Fate 式单一职阶制。既避开 IP 雷区，又让同一英灵可出现在不同阵容中，搭配深度高于职阶制。
2. **敌人全部为非历史人物**（灵体/妖异/幻想体）。历史人物只以正面友方英灵出现——这是历史题材在国内审核下的硬红线，不是风格选择。
3. **重复抽卡转化为通用"英灵印记"**，不给命座/潜能。直接满足"重复角色强度提升 ≤ 基础属性 10%"的合规要求，同时不惩罚收集党。
4. **数值全部走独立乘区**，养成系统之间用乘法而非加法堆叠，避免后期膨胀失控且便于单系统调参。
5. **核心逻辑层（`core/`）纯 TypeScript、零 DOM 依赖**，可在 Node 下跑数值模拟与单元测试；概率公示表由代码同一份数据生成，杜绝"公示与实现不一致"这一合规硬伤。
6. **首发纯前端 + localStorage 存档**，不引入后端；后端（云存档/兑换码/配置下发）作为二期可插拔模块。
7. **PVP 走"竞技归一化"路线（关键决策）**：PVP 战场中等级、遗物强化等级、印记投入**完全归零**，只保留星级被动、技能等级、遗物套装、羁绊并**打折封顶**。养成深度转化为**策略广度**（战术选项更多）而非数值大小，从根本上消除 Pay-to-Win。
8. **竞技池由系统统一开放全部英灵**，玩家的抽卡进度不影响对局可用性；PVP 产出只进竞技专属池（外观/称号/有限抽卡券），**绝不回流银两、经验、强化石**。抽卡动力留在 PVE（收集/图鉴/外观），PVP 靠策略——同时满足合规中"不得以随机抽取与 PvP 竞争诱导过度消费"的要求。
9. **战斗层现在就预留 `BattleContext`**：`resolveStats(hero, context)` 按 `pve` / `arena` 分流属性解析。这是 PVP 扩展成本最低、收益最高的架构决策，必须在 Phase 1 落地，否则后期需重写整套战斗系统。

### 实施修正（2026-11，后端与登录系统）

> **决策 6 已变更**：原方案「首发纯前端 + localStorage 存档，不引入后端」不再成立。
> 首发**必须**具备真实后端认证与云存档，否则无法满足「强制登录才能进游戏」与
> 「登录即跨设备同步」的产品要求，也拿不到可用于发行审核的账号体系与数据披露能力。

| 项 | 原方案 | 现方案（已实施） |
|---|---|---|
| 后端 | 二期再做，首发不做 | **首发即有**：Node + Fastify + SQLite，仓库内 `server/` |
| 认证 | 无 | 账号注册 / 登录 / 刷新 / 登出 / 注销，强制登录才能进游戏 |
| 存档 | 仅本机 localStorage | **每账号一份云存档** + 本机副本，登录即跨设备同步 |
| 冲突合并 | 未定 | 时间戳大者胜（`savedAt`），落后方采纳新版本，不做字段级合并 |
| 兑换码 | 内置一次性代码表 | 维持不变（`core/config/economy.ts` 的本地表） |
| 配置下发 / 排行榜 / 竞技结算服务 | P1 / P2 | 仍未做，优先级不变 |

**未随之变更的部分**：数值系统、合规口径、PvP 隔离、抽卡概率与保底规则**全部不变**——
后端只承载「认证 + 云存档」，不参与任何战斗与数值计算，`src/core/` 仍是纯逻辑层。

**仍待决策**：部署目标（托管方 / 域名 / 持久卷 / HTTPS）未定，当前默认本地跑通 + 预留 Dockerfile；
无 SMTP，找回密码暂缺，缓解手段是保留导出存档串并提示玩家定期导出。

## 1. 目标与范围

### 1.1 要做的东西

一款单页 H5 游戏。玩家进入后看到编队界面，队伍自动挂机打关卡；关卡提供经验与材料；玩家抽卡拿到新英灵、投入养成、把战力推过下一道关卡门槛。核心体验是**"数字在涨 + 搭配在变 + 离线也在变强"**。

### 1.2 首发交付清单

| 项 | 首发范围 | 二期 |
|---|---|---|
| 关卡 | 10 章 × 30 关 + 章 BOSS = 310 关 | 无限章节、难度回溯 |
| 英灵 | 72 位（SSR 12 / SR 24 / R 24 / N 12） | 扩池至 120+ |
| 遗物 | 60 件 + 12 套套装效果 | 遗物重铸/词条锁定 |
| 卡池 | 常驻池 + 2 个主题限定池 | 联动池、活动池 |
| 战斗 | 自动回合制，倍速/跳过 | 手动干预技能优先级 |
| 付费 | 无（兑换码 + 游戏内货币） | 支付 + 通行证 + 商城 |
| PvP | PVE 天梯段位（§9.1）+ 竞技数据结构 + `BattleContext` 架构预留（§6.7） | 异步竞技场（Phase 11）、实时 PvP（远期可选） |
| 联网 | 无（纯本地存档） | 云存档 + 排行榜 + 公告 |

### 1.3 非目标（明确不做）

- 不做**实时** PvP 对战、不做公会、不做家园/社交系统、不做体力墙、不做每日强制在线时长。（PVP 扩展本身**纳入范围**，见 §6.6–§6.11：首发落地 PVE 天梯与异步竞技场的数据模型，实时对战列为远期选项。）
- 不做任何 Fate 原作元素：职阶制、职介卡、令咒、魔术体系、原作立绘、原作设定名词。借用的是"收集英灵 + 遗物 + 编队 + 自动战斗"的**结构**，表达全部原创。
- 不做真实支付、不接广告 SDK（仅预留适配层接口）。
- 不做配音、演出动画、剧情过场（仅文本与头像演出）。

## 2. 约束与红线

### 2.1 内容合规（国内发行必须遵守）

| 项 | 要求 | 本方案落实 |
|---|---|---|
| 概率公示 | 游戏内显著位置公示，精确到小数点后两位，区分"基础概率"与"含保底综合概率" | 抽卡页固定「概率公示」入口 + 设置页二级入口；公示表由 `core` 同一份 `pool.rates` 数据渲染生成 |

| 历史题材 | 不歪曲事实、不抹黑英雄、不传播历史虚无主义 | ① 敌人为非历史人物；② 文本中立且以正面事迹为主；③ 首发池不含近现代争议人物；④ 传记只述史实不评功过 |

| 未成年人 | 提示、理性消费提示、求助渠道 | 首发虽无充值，仍保留合规页与年龄声明 |
| 隐私 | 单独授权、境内存储、可导出 | 首发纯本地，无采集；埋点默认关闭且可一键清除 |

### 2.2 IP 边界

- 角色原型为真实历史人物（公有领域），美术必须原创，不得使用任何现成游戏/影视/博物馆图片（含博物馆摄影作品，摄影权另计）。
- 文案避免"某著名 IP 的某某英灵"的直接指涉；不出现"职阶""职介""从者""令咒"等强指向词。命定道具改称**「圣痕遗物」**。

### 2.3 技术约束（本机环境实测）

- Node.js v24.13.0、npm 11.11.0、Git 2.43.0 可用；**Python 不可用** → 所有数值模拟脚本用 Node + TypeScript 编写。
- 无 Python/无 GPU → 美术生成走外部图像模型 API + 本地后处理脚本，不做本地推理。
- 首发不引入后端 → 需保证"纯静态托管即可运行"。

### 2.4 本轮工作范围与授权边界

- 本轮（方案设计阶段）**仅产出本文件**：未创建任何源码文件、未安装依赖、未初始化 Git 仓库、未修改工作区任何其他内容。
- 方案通过评审并获得实施授权后，**Phase 0 是第一个写操作**（创建 `package.json`、`src/core/` 骨架、`tests/`、`.gitignore`）。在获得明确授权前不得开始写码。

## 3. 设计支柱

1. **数值是唯一语言**：所有系统都必须能翻译成一个玩家看得懂的数字（战力）。看不懂的深度不做。
2. **挂机不等于无脑**：自动战斗负责执行，**编队、遗物、羁绊、抽卡时机**才是玩家做的决策。
3. **每次上线 30 秒内有正反馈**：一键收取、一键升级、战力数字跳动。
4. **不惩罚离开**：离线收益只衰减不归零（保底 8h 满额），但在线效率恒定在线 3 倍。
5. **收集驱动 + 泛化养成**：抽到新英灵是快乐，但重复的英灵也有明确去处（印记），杜绝抽卡挫败感。

## 4. 核心循环

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   [挂机推关] → 经验/银两/材料/关卡掉落                 │
        │                                              │
        ▼                                              │
   [养成] 等级·星级·技能·遗物·羁绊 → 战力↑              │
        │                                              │
        ▼                                              │
   [编队] 6 槽位 · 五行相性 · 定位搭配 → 战力↑          │
        │                                              │
        ▼                                              │
   [卡关] 战力 < 关卡需求 → 战力不足                    │
        │                                              │
        └──→ [抽卡] 获得新英灵/印记/遗物 ──┘
```

### 4.1 三层循环与目标感来源

| 层级 | 周期 | 玩家在做什么 | 目标感 |
|---|---|---|---|
| 短循环 | 30 秒 – 2 分钟 | 收离线收益、一键升级、领日常、点一次推关 | 数字在涨 |
| 中循环 | 2 小时 – 1 天 | 抽卡、突破、换遗物、推 1-2 章 | 下一关/下一颗星 |
| 长循环 | 2 周 – 4 周 | 集齐 12 SSR、满羁绊、清完 10 章、赛季段位 | 图鉴完成度 |

**自检**：任何一个系统如果"上线点一下就没了"，它是失败的孤岛，必须被移除或改造。

### 4.2 核心循环外的两个异步驱动

- **离线收益**：给不常上线玩家的正反馈，保证长周期不流失。
- **每日/每周常驻**：`每日签到`（7 天循环）+ `竞技场周常`（天梯段位，含 PVE 梯队与异步 PvP 防守阵容）。

## 5. 数值系统（核心）

### 5.1 属性面板

**基础六维**（英灵自身）：

| 属性 | 键 | 作用 | 数值型挂机中的角色 |
|---|---|---|---|
| 攻击 | `atk` | 伤害输出基数 | 主输出项 |
| 防御 | `def` | 减伤基数（参与伤害公式分母） | 承伤项 |
| 生命 | `hp` | 生存上限 | 主生存项 |
| 速度 | `spd` | 行动顺序 / 回合数效率 | 稀缺乘区，防同质化 |
| 暴击 | `crit` | 暴击率 | 副乘区 |
| 暴伤 | `cdmg` | 暴击倍率 | 副乘区 |

**衍生三性**（不占养成位，由基础值换算，避免属性面板过载）：

- `dodge`（闪避）= f(spd, 等级)
- `hit`（效果命中）= f(spd, 定位)
- `res`（效果抵抗）= f(def, 等级)

### 5.2 战力公式

```
主战 = atk × 2.2 + def × 1.6 + hp × 0.28
暴击乘区 = 1 + crit × cdmg          // crit、cdmg 均按小数计
速度乘区 = 1 + min(spd, 600) × 0.0012
战力 = 主战 × 暴击乘区 × 速度乘区
```

设计意图：
- 战力只做**横向可比**（用于 PVE 门槛判定、排行榜），**不做战斗输入**。战斗仍走独立伤害公式，避免"战力"变成黑箱。
- `spd` 乘区有上限（600），防止速度成为唯一最优解。
- 任何养成系统的贡献都能在战力面板上看到增量（成长可视化是数值挂机的留存命脉）。

### 5.3 属性合成：独立乘区原则

```
最终属性 = 基础属性(等级, 星级)
         × (1 + 遗物加成%)
         × (1 + 天赋/技能被动加成%)
         × (1 + 羁绊加成%)
         × (1 + 境界突破加成%)
         × (1 + 进度增益%)
```

规则：
- 每个系统**独占一个乘区**，不做加法叠加。加法堆叠会让后期数值失去意义且难调参。
- 每个乘区可独立调参，控制总膨胀速度（数值飞轮的两个阀门之一）。
- 上限：任一乘区系数 ≤ +300%，防止单点爆炸。

### 5.4 养成线（5 条）

| 养成线 | 消耗 | 上限/门槛 | 作用 |
|---|---|---|---|
| **等级** | 英灵经验 | 1–240，分 4 境界：凡阶(1-60)/名阶(61-120)/圣阶(121-180)/神阶(181-240) | 基础属性主成长 |
| **星级** | 同名碎片 + 英灵印记 | 1★–6★，每星解锁 1 条被动天赋 | 基础属性倍率 + 被动 |
| **技能** | 术式结晶 + 银两 | 3 技能 × 1–20 级 | 战斗行为改变 |
| **遗物** | 遗物本体 + 强化石 + 银两 | 6 槽位，遗物 1–60 级，套装 2/4/6 件效果 | 最大乘区，深度主来源 |
| **羁绊** | 自动（编队触发） | 标签计数阈值 | 编队策略价值 |

**境界门槛**：进入下一境界需特定材料（如"名阶"需 1 张指定名阶突破书），制造周期性目标。

**经验曲线**：`expToNext(L) = 60 × 1.025^(L-1) × expScale(境界)`，`expScale` 为**绝对台阶系数**：凡阶 1 / 名阶 5 / 圣阶 15 / 神阶 40。

> **实施修正（Phase 2）**：原文写作 `60 × 1.115^(L-1)` 且「境界间用系数重置基准」。若指数按**境界内局部等级**重置，境界切换那一级的经验需求会断崖式下跌——
> `expToNext(60) = 60 × 1.115^59 × 1 = 36,929` → `expToNext(61) = 60 × 1.115^0 × 8 = 480`，**骤降 77 倍**。
> 后果是玩家一进新境界就能瞬间连升数级，境界门槛形同虚设。
>
> 修正为**全局等级指数 + 境界绝对台阶**：境界切换是 `expScale` 带来的**向上**台阶（真正的门槛），指数项按全局 239 级重新标定（`EXP_GROWTH` 由 1.115 下调为 1.025，`expScale` 由 1/8/40/200 重新标定为 1/5/15/40）。
> 实测：单人 Lv1→240 累计 ≈ 2.9×10⁷，6 人编队总需求 ≈ 1.77×10⁸，与主线经验投放 4.0×10⁸ 同量级（回收率 2.26×）。
>
> **同批修正**：`skillLevelCap` 原式 `realm.maxLevel - realm.minLevel + 1 + 10`，因每境界区间恒为 60，该表达式恒等于 70，**境界门槛完全失效**（Lv1 即可把技能升满 20 级）。改为 `level - realm.minLevel + 1 + 10`，进入新境界时技能上限回落至 11 级、随境界推进解锁到 20 级。

### 5.5 羁绊与定位标签

**五行相性**（相克环）：`金 → 木 → 土 → 水 → 火 → 金`
（我克者伤害 +25%，克我者 −15%）

| 五行 | 人物映射逻辑 | 示例 |
|---|---|---|
| 金 | 兵法、纪律、金属、锐器 | 韩信、孙武、凯撒、荆轲 |
| 木 | 医、韧、生长、隐忍 | 南丁格尔、诸葛亮、荆轲 |
| 水 | 智谋、变化、水利、机关 | 祖冲之、李冰、阿基米德 |
| 火 | 爆发、开拓、热血 | 项羽、亚历山大、拿破仑、圣女贞德 |
| 土 | 厚重、守护、土木、后勤 | 汉尼拔、鲁班、李冰 |

### 5.6 阵容

- **6 槽位**：前排 3（近战位）/ 后排 3（远程位）。
- 每个英灵有 `preferredSlots`（猛将偏前、器者/医者偏后），但**不强制**——允许自由编排（策略深度）。

### 5.7 离线收益曲线

```
离线时长 t (小时) → 效率 eff(t)：
  t ≤ 8    → 100%
  8 < t ≤ 12 → 线性衰减 100% → 60%
  t > 12   → 0（默认封顶 12h）

实际收益 = 在线速率 × 有效时长(小时) × eff(t) × 挂机倍率
```

- **在线效率恒定为离线的 3 倍**（活跃玩家 1 小时在线 ≈ 离线 3 小时），保证活跃有价值。
- 收益结算按"最近 N 场战斗"回放，而非简单按时长线性给——战斗有随机性，回放结算让收益与实际推关表现挂钩，且不会出现"挂机 12h 打不过却照样领满"的割裂感。
- 结算弹窗展示明细（打了多少场、掉落什么、经验多少），并预留「立即结算」按钮位（后续可接激励视频/道具），首发该按钮为"直接领取"。

### 5.9 PvP 数值隔离原则（摘要）

挂机游戏的养成线是**单调递增**的，而 PvP 要求**对等**——这是两者最根本的冲突。若直接把 §5.1–§5.4 的 PVE 数值搬进 PvP，结果是纯 Pay-to-Win：付费玩家用战力直接碾压，且战力数值无上界、无法收敛。

因此确立三条隔离原则（完整设计见 §6.6–§6.11）：

1. **归一化**：PvP 战场中所有英灵的基础属性按定位模板重置，不继承 PVE 的等级/星级/遗物强化数值。
2. **策略化**：养成投入在 PvP 中只影响**可选战术条目的数量与系数**（星级被动、技能等级、遗物套装、羁绊），且系数**打折并封顶**。养成深度 → 策略广度，而非数值大小。
3. **产出隔离**：PvP 产出只进竞技专属池，**不回流**银两、英灵经验、遗物强化石、抽卡结晶，避免"PvP 变强 → PVE 加速 → 数值飞轮失控"。

配套的架构约束：`core/systems/arena.ts` 中**禁止引用** `player.permBoost`（圣杯重启永久加成）等 PVE 无限加成项；PvP 结算函数不接受 PVE 养成数值，只接受竞技快照。这条约束需要有单元测试守护（见 §15.1）。

## 6. 战斗系统

### 6.1 形态

**回合制自动战斗**，双方最多 3 行动位（玩家前排 3 + 后排 3 编队映射到 6 人，但战斗同时最多 6v6？—— 简化如下）：

- 玩家侧：编队 6 人全员参战，按 `spd` 决定行动顺序。
- 敌方：一关 = 1–5 个怪 + 章末 BOSS。
- 每回合全体存活单位各行动一次；单场战斗典型 3–8 回合。
- 玩家不可手动操作，但**可在战前配置**：技能优先级（普攻/技能自动选）、预设"不上场"等。

### 6.2 伤害公式

```
基础伤害 D = atk × (atk / (atk + def_eff)) × 技能倍率
D ×= (1 + 暴击加成)         if 暴击
D ×= (1 - 减伤率)           // 减伤率上限 75%
D ×= 相性系数               // 我克 1.25 / 平 1.00 / 克我 0.85
D ×= 随机因子               // 0.95 – 1.05
D = max(1, round(D))
```

### 6.3 战斗表现（数值型，不做重演出）

Canvas 2D 渲染，自研轻量渲染器（约 400–600 行）：

- 布局：上排敌方 3 位、下排我方 3 位（按前/后排分组），头像圆形 + 血条 + 定位色标。
- 表现：技能触发时头像闪光 + 屏幕飘字（暴击/治疗/伤害数字），BOSS 额外描边与血条分段。
- 倍速：1× / 2× / 4× / 8×（跳过结算，直接展示结果摘要）。
- 结算：战后弹出"回合数 / 伤害统计 / MVP 英灵 / 掉落"，MVP 与伤害统计是重要的正反馈点。

> 若自研渲染器排期吃紧，降级方案：首版仅用 DOM + CSS 动画表现，Canvas 渲染器作为第二阶段增量。

> **实施修正（2026-11，站位与目标选择）**：原文「上排敌方 3 位、下排我方 3 位（按前/后排分组）」未定义
> **前后排的朝向**与**目标选择的并列判定**，实现时两处都做错了：
>
> 1. **渲染朝向反了**：原实现按「插入序号」排布并让前排落在远离敌人的一侧，
>    观战时看到的是后排贴敌、前排缩在角落。改为按**真实编队槽位号**（0-2 前排 / 3-5 后排）
>    定位，**前排朝敌、后排在后**。
> 2. **目标选择的并列判定用错了键**：同血并列时按 `id.localeCompare` 选目标——
>    英灵 id 是拼音字母序，与编队毫无关系，导致「怪开局固定去打 `caiwenji` 这类字母序最小的人」。
>    实测（6 人满编队）：蔡文姬首轮唯一被击中，项羽/周瑜/商鞅/陶渊明/王昭君整场未挨打。
>    改为并列时按**槽位序**（slot 小 = 前排先挨打），符合「前排承伤」的编队语义；
>    **集火低血的主规则不变**。
>
> 配套的数据约定：
> - `HeroRuntime.slot` 升为**必填**字段，语义是**真实编队槽位号**，不是「队伍里的第几个」
>   （队伍会跳过空槽位，用紧凑序号会让后排的人被当成前排）。
> - `BattleResult.roster` 由 core 产出参战名册（id / side / slot / name / maxHp）。
>   ⚠ **id 必须与日志的 `actorId` / `targetId` 完全一致**——表现层自行拼接 id
>   （敌人用 `def.id` 而战斗用 `def.id#0`）会导致查不到单位、血条永不变化，
>   同一类错误已由铁律 #8（表现层不得自行拼接 key）覆盖。
> - 敌方在名册里的 slot 是**该阵营内的出场序号**（0 起），不是战斗内部的全局 slot
>   （后者带 offset、召唤怪还会更大，拿来当画面行号会让怪画到画布外）。

> **实施修正（2026-11，数值型轻演出落地）**：本节原案已按 §6.3 实现（Canvas 2D 自研渲染器，
> 范围 = 推征观战 + 关卡详情预览；**不做配音、演出动画、剧情过场**）。落地的关键决策如下。
>
> 1. **回放模型 = 时间的纯函数 `f(t)`**（`presentation/utils/battle-timeline.ts`）：
>    战场状态由 `projectState(t)`、瞬时特效由 `collectEffects(t)` 按时刻**推导**，不做增量累积。
>    因此倍速只是时间缩放、跳回合直接设 `t`、重播清零，
>    **结构上不可能出现「快进后血条对不上」**。三个函数零 DOM 依赖，可直接在 Node 下单测。
> 2. **core 契约必须先扩，否则表现层只能靠猜**（铁律 #8 / #16）：
>    - `BattleLogKind` 新增 `'death'`：死亡改为**独立事件**（原是「damage + amount 0」的隐式约定），
>      `applyDots` 致死也补 death 事件（原完全不产日志）。
>    - `BattleUnitRosterEntry` 新增 `defId` / `role` / `element` / `mechanic?`：
>      职业色标、五行色、是否 BOSS、美术路径全部由 core 给出，**表现层一律不自行推导**。
>    - `BattleLogEntry` 新增 `absorbed?`：护盾吸收飘字需要 core 给出「这一击被盾吃了」这个事实，
>      表现层不得凭血量变化反推文案。
> 3. **美术零新增**：英灵取卡面顶部方块、敌人取 82% 见方去掉底部名字条，
>    裁取参数集中在 `core/config/art.ts` 的 `AVATAR_CROP`（唯一口径），
>    换图不破。英灵卡面源图为 3:4 全身图（头部在图高 8%~32%），故取 `sizeRatio 0.5`。
> 4. **战报上限 `MAX_LOG` 400 → 1500**：实测第 10 章 BOSS 在真实缩放下 **8/8 场撞满 400 上限**、
>    跑满 30 回合，上限过低会让回放被截断（后半场直接没了）。战报不入存档，内存无压力。
> 5. **倍速写回存档由页面负责**：组件只 `@speed-change` 抛事件，
>    视图层再写 `settings.speed` + `store.battleSpeed` + `persist()`（组件保持可复用）。
>    `settings.skipAnim` 此前是空壳，本次首次接线（开启后直接出结算）。
>
> **已知限制**：
> - `store.lastBattle` 仍是死代码，本次**不接入**（挂机结算不需要保留战报）。
> - 回放**不持久化**：刷新页面后战报丢失（战报按定义不入存档）。
> - 演出节奏常量（`EVENT_DURATION` / `HP_TWEEN_MS` / `FLOAT_MS` 等）在表现层
>   `battle-timeline.ts`，**不进 `core/config/economy.ts`**——它们是演出节奏，不是经济数值。

> **实施修正（2026-11，纵向排布遮挡）**：三排单位（真实槽位 0-2 / 3-5）同屏时，
> 首版行距只按「头像直径」估算（45.6px），导致**上排单位的血条被下排头像整个盖住**，
> 且下排的名牌压在上排头像上——两处信息都读不到。
>
> 1. **名牌与血条一律挪到头像下方**（头顶只留给飘字），行距按「名牌底 42」重算为 72；
> 2. **遮挡边界不是头像边缘，而是色环（r+2）与 BOSS 双环（r+6）画出的更高外缘**——
>    只按头像直径留距会被这两个外圈吃掉；
> 3. 画布高度 240 → **300px**，容得下「顶部飘字空间 + 3 排 + 底部事件条」；
> 4. 截图验收必须**满编 6 人**——少编只有一排，遮挡问题根本不暴露
>    （`tools/capture/screenshot.ts --battle` 已改为满编编排）。

### 6.4 敌人设计（合规关键）

- 敌人**全部为非历史人物**：无名灵体、妖异、幻想兵、器械造物。
- 敌人视觉与命名避免指向任何真实历史人物或族群（不用"某国军队""某族战士"这类命名）。
- 章主题通过**环境/氛围**表达（如"水患之章"以洪灾幻象为背景），而非让历史人物互相厮杀。
- BOSS 命名为原创幻象名（如"洪荒之影"），不复用任何史实名号。

### 6.5 BOSS 机制

每章 BOSS 有 1 个专属机制，保证每章有一次"卡点必须解决"的体验：

| 机制 | 示例 |
|---|---|
| 护盾阶段 | 前 30% 血量有护盾，需破盾才吃伤害 |
| 狂暴阶段 | 60% 血量后攻击 +40% |
| 召唤 | 每 3 回合召唤 2 个小怪 |
| 属性反转 | 免疫某属性（需换相性阵容） |
| 反伤 | 造成伤害时自身反弹 10% |
| 治疗锁 | 每回合回复，持续输出型阵容被针对 |

> **实施修正（2026-11，召唤机制）**：表里的「召唤」一行**配置齐全但从未真正触发**——
> `BossMechanic.summon` 的 `enemyId` / `count` 两个字段全被忽略，机制是空转的。
>
> 1. **模板查找用错了键（致命）**：实现取「已死亡敌人的显示名」去查敌人索引
>    （`template.name.split('#')[0]` → 「蜃楼幻身」），
>    而索引的 key 是**敌人 id**（`sand_mirage`）→ 永远查不到 → 直接 `continue`，
>    **召唤从未触发**，BOSS 阶段只剩本体，「卡点必须解决」的体验完全缺失。
>    改为按配置的 `mech.enemyId` 查 `ENEMY_TEMPLATES`（数据驱动，不再从战场反推模板）。
> 2. **数量字段被忽略**：`count` 从未使用，每次只召唤 1 个。改为按 `count` 召唤。
> 3. **援军属性过强**：原实现只砍血（`hp = maxHp × 0.4`）不砍攻，
>    造出「满攻玻璃炮」——实测第 2 章 BOSS（L30 档）通关率从 100% 掉到 **0%**。
>    改为攻防血**一起**按 `BATTLE.SUMMON_STAT_RATIO` 折算（援军是模板怪的削弱版）。
> 4. **援军无限叠加**：`everyTurns` 每 3 回合触发、一次 2 个，30 回合能叠到 20 个。
>    加 `BATTLE.MAX_LIVE_SUMMONS` 存活上限，援军是「持续压力」而非「滚雪球」。
> 5. **新规则「BOSS 锁定」（必要配套）**：援军血量必然低于 BOSS，
>    若仍按「集火最低血」打，队伍会永远在打小怪 → BOSS 永远不死 → 召唤型 BOSS 直接变成活门。
>    改为：**只要 BOSS 存活，我方单体攻击锁定 BOSS**；援军退化为 AoE 压力源。
>    影响面可控：竞技双方都不是 BOSS，非召唤关卡的 BOSS 关只有 1 个敌人 → 行为不变。
>

### 6.5 补充：关卡难度曲线重标定（数值断层修复）

> 本条目记录把「第 7~10 章 BOSS 实战通关率 0%」修掉的**独立提交**。
> 与前面的召唤机制修复分开提交，便于单独回滚。

#### 症状

`npm run balance:battle`（真实跑战斗）实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 实战能过的最后一关 | 第 **246** 关 | 第 **310** 关 |
| 第 7~10 章 BOSS 通关率 | **0%** | **100%** |
| 各章 BOSS 通关率（满养成档） | 1~2 章 100%，其余 0% | **全部 100%** |
| 战力模型 vs 实战 | 模型 310 / 实战 246 | **模型 310 / 实战 310** |

#### 根因（两层）

1. **难度曲线总量纲失控**：旧公式 `BASE_POWER × CHAPTER_GROWTH^(章序-1) × IN_CHAPTER_GROWTH^(关序-1)`
   让敌方属性缩放总跨度达到 **2.4×10⁵**，而玩家战力从 Lv1 到满养成只有约 **4.9×10³** 倍
   ——敌方强度比养成快 50 倍，玩家永远追不上。
   再叠上敌人**基础属性**本身跨章增长 7.5 倍（BOSS 血量 2400 → 18000），
   等于难度被**重复计入**两次。
2. **战力门槛与真实难度脱钩**：`powerRequired = BASE_POWER × scale` 完全不看敌人基础属性，
   于是「隐含门槛基数」随章从 3213 漂到 27933（8.7 倍漂移），
   门槛在后期比真实需求松 8.7 倍 → 挂机会把玩家推进到**打不过**的关卡 → 打输 →
   结算中断 → 玩家零收益卡死（这是比「打不过」更严重的失败模式）。

#### 修复

1. **机制前置修复**（不改数值就调不出合理曲线）：
   - 护盾阶段：原实现「盾被打掉后下一发又补」→ BOSS 实际无敌、难度对缩放极度敏感
     （第 10 章 BOSS 在缩放 733~1500 之间通关率从 83% 掉到 0%）。改为**护盾只挂一次**。
   - 狂暴阶段（`enrage`）配置齐全但战斗代码**从未读取** → 机制完全空转。补齐实现。
2. **难度曲线改为「逐章锚点 + 统一章内增长」**：
   - `STAGE.SCALE_ANCHORS`：每章**首关**的敌方缩放锚点，由真实战斗模拟标定
     （玩家水平取自经验投放模型推出的等级阶梯 Lv10/31/62/78/108/133/164/193/225/240；
     对该章 BOSS 二分「能稳过(≥90%)的最大缩放」→ 取其一半 → 除以章内总跨度 1.25）。
   - 章内 30 个普通关按 `IN_CHAPTER_SPAN = 1.087` 等比铺开，章末 BOSS 再 × `BOSS_MULTIPLIER = 1.15`
     （章内总跨度 1.25）。相邻章锚点比 ≥ 1.30，保证章边界严格递增。
   - 放弃「单一指数外推」：在「章边界严格递增 + 缩放总跨度 ≤ 玩家成长跨度」两个约束下，
     单指数结构**数学上无解**（章内跨度必须小于相邻章比值，而相邻章比值因各 BOSS 机制差异在 1.3~2.9 间波动）。
3. **战力门槛改为「逐章锚点 + 章内等比」**：
   - `STAGE.POWER_ANCHORS`：每章**BOSS 关**的门槛 = 玩家「刚能稳过该章 BOSS」时的战力。
   - 章内从「上一章 BOSS 门槛 × 1.05」等比升到本章 BOSS 门槛。
   - 门槛是挂机自动推进的**放行线**，必须**不晚于**该关真正打得赢的时刻，
     否则会推进到打不过的关卡 → 零收益卡死。宁可略紧不可略松。
4. **掉落曲线与难度曲线解耦**：旧实现把难度倍率（3.5）直接当掉落倍率用，
   两者互相绑死无法单独调整。现在掉落用独立的 `DROP_GROWTH = 3.5`（数值不变，
   只解耦语义），难度锚点反过来是按这条投放曲线推出的玩家水平标定的。

#### 修复后实测

- 10 章 BOSS 在各自玩家水平下通关率**全部 100%**，战斗回合 6~16 回合。
- 实战卡关点 = **第 310 关**（修复前 246 关）。
- 末关门槛 2.29×10⁷，满养成战力 3.60×10⁷ → 余量 **1.57×**（≥1.5× 不变量）。
- 竞技归一化后战力差 **5.19%**（<15% 不变量）。
- 投放回收五类资源全部 ≥1（经验 2.26× / 银两 111× / 术式结晶 2.11× / 遗物强化石 1.57× / 英灵印记 1.32×）。
- 新增 `tests/unit/stage-balance.test.ts` 守护：各章 BOSS 实战通关率 ≥80%、
  门槛放行线不早于「打得赢」、门槛与敌方缩放单调递增。

#### 已知限制

- **章内难度偏平**：敌方缩放在章内 30 关只增长 1.087 倍，而玩家战力在章内会涨 1.7~5 倍，
  于是同一章后段的战斗偏轻松（进度主要由门槛放行来把关）。
  这是「敌方基础属性跨章增长 7.5 倍 + BOSS 血量尖峰 5~10 倍」两个既有配置事实的产物：
  章内若按玩家成长等比铺开，章边界就会倒挂。彻底解决需要压平 `config/enemies.ts`
  的基础属性增长（改 30 条配置），本次未做。
- **`STAGE.SCALE_ANCHORS` / `POWER_ANCHORS` 是标定值**：英灵 / 成长 / 掉落数值变动后
  必须重跑 `npm run balance:battle` 重新标定，否则门槛会与真实难度重新脱节。
- **圣杯重启永久加成（`permBoost`）在真实战斗里从未被应用**
  （`resolveStats` 没有注入 progress 乘区），这是独立于本次的既有缺陷，
  标定时不依赖它。

### 6.6 PvP 扩展总原则

**问题定义**：PVE 养成线单调递增（等级、遗物强化只涨不跌），PvP 要求对等。若共用一套数值：

- 付费 5000 元的账号可以碾压所有 0 元账号 → 纯 Pay-to-Win；
- 战力数值无上界，PVP 平衡表永远追不上膨胀的养成曲线 → 无法收敛；
- 中低付费玩家发现"再努力也打不过氪金号" → 直接流失。

**三条候选路线与取舍**：

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A. 直接复用养成值 | PVE 数值原样进 PvP | 实现最省 | 纯 Pay-to-Win，且数值不可收敛 |
| B. 完全独立养成树 | PvP 有自己的独立成长线 | 绝对公平 | 与挂机主循环脱节，玩家视作两个游戏；PVE 养成在 PvP 中贬值 |
| **C. 竞技归一化 + 策略深化（采用）** | 剥离数值性养成，保留并放大策略性养成 | 公平且养成仍有意义 | 需战斗层预留 `BattleContext`（成本低，见 §6.7） |

**核心洞察**：在 PvP 中，养成深度应转化为**策略广度**，而不是**数值大小**。一个 30 级玩家和一个 240 级满养成玩家，在 PvP 战场上的**数值几乎相同**（都是模板值 × 封顶系数），但后者的**可选战术组合更多**——这才是真正的差距来源，且该差距**有上界、可封顶**。

### 6.7 战斗层架构预留（Phase 1 必须落地）

这是整个 PvP 扩展中成本最低、收益最高的一步，**必须在 Phase 1 与基础战斗同时实现**，否则后期需重写整套战斗系统。

```ts
// core/systems/battle.ts
export type BattleMode = 'pve' | 'arena' | 'tower';

export interface BattleContext {
  mode: BattleMode;
  /** 竞技模式下的属性归一化策略；pve 为 undefined */
  arenaProfile?: ArenaProfile;
  seed: number;
}

// core/systems/stats.ts —— 属性解析的唯一入口
export function resolveStats(hero: HeroRuntime, ctx: BattleContext): FinalStats;

// PVE 路径
resolveStats(hero, { mode: 'pve', seed })
  → applyGrowth(等级, 星级) → applyMultipliers(遗物, 技能, 羁绊, 永久加成)

// 竞技路径
resolveStats(hero, { mode: 'arena', arenaProfile, seed })
  → applyArenaTemplate(定位模板) → applyCappedStrategy(星级被动, 技能, 套装, 羁绊)
```

**硬性约束**：

- `resolveStats` 是**唯一**的属性入口。战斗系统内部不得直接读取 `hero.level` 等养成字段。
- `arena` 分支**禁止**引用 `player.permBoost`、`hero.exp`、`relic.level`、`hero.baseStats` 等 PVE 数值字段。
- 该约束由单元测试守护：构造两个 PVE 养成差距 100 倍的账号，归一化后战力差必须 < 15%（见 §15.1）。

### 6.8 竞技归一化公式

**定位模板**（集中在 `core/config/economy.ts` 的 `ARENA_TEMPLATES`，单一调参点）：

| 定位 | atk | def | hp | spd | 设计意图 |
|---|---|---|---|---|---|
| 猛将 | 100 | 50 | 1000 | 100 | 爆发高、容错低 |
| 统帅 | 70 | 60 | 1300 | 110 | 高生存、支援前排 |
| 谋士 | 85 | 45 | 950 | 130 | 高出手、控制 |
| 医者 | 60 | 50 | 1200 | 115 | 续航、稳定 |
| 器者 | 90 | 45 | 1000 | 120 | 持续伤害、异常 |

**养成来源在竞技模式中的处理**（完整映射表）：

| 养成来源 | 竞技模式处理 | 封顶 | 性质 |
|---|---|---|---|
| 等级 | **完全归一化，无效** | 0 | 数值性 |
| 英灵基础属性 | **完全归一化**，用定位模板 | — | 数值性 |
| 星级（被动解锁） | 被动生效，效果系数打折 | 每被动 ×0.6 | 策略性（广度） |
| 技能等级 | 技能效果强度提升 | +30% | 策略性 |
| 宝具解锁 | 解锁后可用，强度走技能封顶 | +30% | 策略性 |
| 遗物本体（选哪个） | 保留，**只取套装效果**，固定标准强度 | 套装效果 ×0.7 | 策略性（搭配） |
| 遗物随机词条 | **完全归一化，无效** | 0 | 数值性 |
| 遗物强化等级 | **完全归一化，无效** | 0 | 数值性 |
| 羁绊 | 保留，系数打折 | ×0.6 | 策略性（编队） |
| 印记 / 材料投入 | **完全无效** | 0 | 数值性 |
| 圣杯重启永久加成 | **完全无效**（且代码层禁止引用） | 0 | 数值性 |

**竞技等级（战术铭文）**——把长期养成转化为有界的战术配置自由度：

```
竞技等级 = f(已解锁被动数, 已解锁技能数, 可用套装数, 图鉴广度)
竞技铭文槽位 = min(3, floor(竞技等级 / 阈值))
```

竞技等级**不直接给任何属性加成**，只增加可装备的「战术铭文」槽位数量（最多 3 个）。铭文是纯策略道具（如"首回合爆发"、"受击反伤"、"低血护盾"）。这让养成投入在 PvP 中的影响是**配置灵活性**，而非数值，且**硬性封顶在 3 个槽位**。

### 6.9 竞技池与对局公平

- **竞技池 = 系统统一开放全部已上线英灵**，无论玩家是否已抽到。
  - 理由：若"你有没有抽到韩信"影响对局可用性，抽卡就成为 PvP 的付费杠杆——既是 Pay-to-Win，也是合规风险（不得以随机抽取与 PvP 竞争诱导过度消费）。
  - 代价：抽卡在 PvP 中无直接价值。这是**有意取舍**：抽卡动力留在 PVE（收集、图鉴、传记、外观、羁绊深度），PvP 只作为策略竞技与留存手段。
- **双方对称**：同一竞技池、同一模板值、同一铭文槽上限。
- **英灵解锁的差异如何体现**：通过**被动/技能/套装选项的丰富度**（有星级的英雄多几个被动可选），而非数值。

### 6.10 匹配、对局与结算

**匹配**：

- 段位分匹配（±1 段位内随机），**不按 PVE 战力分桶**（竞技已归一化，PVE 战力无参考意义）。
- 匹配后**冻结双方阵容快照**（含英灵 id、星级、技能等级、套装、铭文、竞技等级的 hash），战斗使用快照。
- 快照冻结后不可改动——杜绝"看到对手阵容再换阵"。

**对局形式**：**异步竞技场**（挂机游戏的正解）

- 玩家配置阵容 → 作为**进攻方**挑战 N 个防守阵容（爬梯）→ 同时布置一套**防守阵容**供他人挑战。
- 符合挂机定位：玩家只在配置阵容时在线，无需实时在线。
- 实时 PvP 需要服务器 tick、匹配服务、掉线补偿、反作弊，工作量与运维成本远高于收益，列为远期选项（见 §17）。

**结算**：

- 接入后端后，战斗在**服务器端**结算，客户端只提交阵容快照 + 种子，服务端用同一份 `core/systems/battle.ts` 复算并校验 hash。
- **幂等**：以 `challengeId` 去重，重复提交返回同一结果，断线重连不重复扣次数。
- **匹配超时/无对手**：退化为 AI 对手，UI **明确标注"演武"**，不消耗竞技次数、不计段位分。

### 6.11 PvP 产出与经济隔离（数值控制的关键）

PvP 产出**只进竞技专属池**，与 PVE 经济完全隔离：

| 来源 | 可获得 | **不可获得** |
|---|---|---|
| 段位奖励 | 竞技勋章（周上限） | ❌ 银两 |
| 竞技勋章兑换 | 限定头像框、称号、竞技专属外观、**有限**抽卡券（周上限） | ❌ 英灵经验 |
| 竞技周常 | 竞技专属材料（仅用于竞技铭文） | ❌ 遗物强化石 |
| PvP 赛季结算 | 赛季称号、外观 | ❌ 圣杯结晶 |

**理由**：若 PvP 产出回流 PVE 经济，会形成"PvP 变强 → PVE 推进更快 → 战力更高 → PvP 段位更难提升"的正反馈螺旋，直接放大数值膨胀并让 PvP 强度受养成深度支配，违背 §6.8 的隔离原则。

**合规约束**：

- 商城**不得出售**任何"竞技属性/竞技等级/竞技强度"类商品。
- PvP 不得作为付费转化的主要驱动入口；付费入口仅在 PVE 侧（抽卡、通行证、商城）。
- 排行榜需有反作弊与举报通道；玩家数据境内存储。

### 6.12 PvP 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **Phase 1（必做）** | `BattleContext` + `resolveStats(hero, ctx)` 架构预留；`arena` 分支先返回模板值 | 无 |
| **Phase 9** | 竞技场 PVE 天梯（§9.1），段位数据结构先行落地 | Phase 1 |
| **Phase 11** | 异步竞技场：归一化实战、铭文系统、匹配爬梯、防守阵容、后端结算 | Phase 9 + 后端 |
| 远期（可选） | 实时 PvP、赛季 PvP 奖励、竞技专属赛季英灵 | 需专门的后端与运维投入 |

> **注意**：Phase 11 排得较后是有意的。PvP 的平衡需要**真实玩家数据**校准，而团队/项目早期缺乏这类样本。先把 PVE 数值飞轮跑稳，再投入 PvP，是数值游戏的标准路径。

> 十连保底规则（§7.3 第 2 条）保证十连内至少 1 个 SR 及以上，
> 因此 SR+ / R+ / N 三行的十连综合概率恒为 100.00 个百分点；
> **有区分度的是 SSR 行**（十连内至少 1 个 SSR 的概率）与「当前保底进度下单抽实际概率」。

- 十连至少 1 个 SR+，且**十连内共用大保底计数**。
- **软保底**：第 71 抽起 SSR 概率线性提升，第 90 抽必出 SSR。
- **综合概率公示**：UI 同时展示"基础概率"与"含保底综合概率"两栏；综合概率由 `core` 的 `computeEffectiveRates()` 依据当前保底状态实时计算，**与实际抽卡调用同一函数**，杜绝公示与实现不一致。

> **实施修正（Phase 5）**：原表十连综合概率为 5.73% / 43.62% / 91.25% / 100%，与「十连至少 1 个 SR+」的规则**自相矛盾**——
> 43.62% + 91.25% + 100% 已超过 100%，说明原表把「至少出现 1 次」与「单次出现」混算了。
>
> 实现采用**精确动态规划**（非蒙特卡洛）计算「十连内至少出现 1 次**该稀有度或更高**」：
> `core/systems/gachaRates.ts` 的 `computeTenPullOutcomes()` 对当前保底状态做 10 步 DP，**与实际抽卡调用同一概率源**，
> 因此「公示 = 实际」在构造上成立（零公示噪声），而非统计意义上的近似。
> 上表数值为 `pitySSR = 0`（保底未启动）时的精确值，可由 `tools/balance/tenpull-rates.ts` 复现。
>
> **实测校验**：固定种子 100 万次十连模拟，SSR 综合命中率与 DP 公示值偏差 < 0.041%（4σ 窗口内）；
> 100 万次单抽 SSR 基础率与公示 0.60% 偏差 < 0.01%。两项断言已固化为单元测试（`tests/unit/gacha.test.ts`）。
>
> **同批修正（Phase 6 收尾）**：DP 终态原按「至少出现 1 次**该稀有度**」统计（`hasSR` 只被纯 SR 置位），
> 而公示表头写的是「该稀有度**或更高**」——标签与数值口径不一致，玩家会把 SR 行的 90.51% 误读为
> 「十连出 SR+ 的概率」（实际约 92%），低估自身收益。已改为累计口径（`hasSRPlus` / `hasRPlus`），
> 使**标签与数值严格一致**。
>
> **同批修正（Phase 6 收尾）**：纪元池只收录 SSR/SR，而基础概率表有四档。原实现抽到 R/N 时
> `pickHero` 直接抛错（抽卡崩溃），且公示的 70% N 概率与实际不符（合规问题）。
> 修正为 `projectToPool()`：池内不存在的稀有度，其概率**并入池内存在的最低稀有度**
> （纪元池 → SSR 0.60% / SR 99.40%），公示表按**当前卡池**计算并标注该稀有度是否收录。
>
> 卡池投影另有 9 项断言（`tests/unit/gacha-pool.test.ts`）覆盖「纪元池不崩溃 + 公示 = 实际」。

### 7.3 保底规则（必须显式公示）

1. 大保底计数上限 90 抽，跨所有卡池**继承**，换池不清零（合规要求）。
2. 十连内必出 SR+；若十连内出的是 SR 而非 SSR，SSR 计数 **+2**（补偿常见做法）。
3. 新手期首次 10 连保底 1 个 SSR。
4. 保底进度条常驻抽卡页，显示"距离必出 SSR 还差 N 抽"。

### 7.4 重复处理（合规要点）

| 抽到 | 转化 |
|---|---|
| 新 SSR | 直接获得 |
| 重复 SSR | 50 枚「英灵印记」+ 10 枚该英灵碎片 |
| 新 SR / 重复 SR | 重复 → 12 枚英灵印记 |
| R / N | R → 3 印记；N → 1 印记 + 银两 |

### 7.5 抽卡货币与合规位

| 货币 | 来源 | 性质 |
|---|---|---|

> **扣费口径（实施修正，Phase 6 收尾）**：原实现单抽**同时**扣「圣杯结晶 300 + 抽卡券 1」，
> 与 UI 文案「结晶 300 **或**券 1」矛盾（等于白烧玩家的券），且**完全不校验余额**——
> 结晶可被扣成负数，抽卡总闸门形同虚设。现改为：
> - **十连**：圣杯结晶 3000，**不消耗抽卡券**；
> - **单抽**：圣杯结晶 300 **或** 抽卡券 1，二选一，优先结晶（主抽卡货币），
>   结晶不足时自动改用抽卡券，UI 同步显示实际扣哪一项；
> - **余额不足**：直接拒绝本次召唤，不扣费、不产出，UI 禁用对应按钮。
>
> 判定落在 `core/systems/gacha.ts` 的 `resolvePayment()`（返回 `null` 即余额不足），
> `executePull()` 据此抛 `InsufficientFundsError`，表现层只负责提示。单测新增 5 项
> （`tests/unit/gacha.test.ts` 的「抽卡费用」），E2E 覆盖十连后余额归零、单抽改走抽卡券。

**预留付费位**：首发无任何真实支付入口，但 `platform/payment` 适配层定义好接口（`createOrder` / `verifyReceipt`），后续接入不改业务逻辑。

## 9. 竞技场与长循环玩法

竞技场是本作的中长循环载体，分为**已上线**的 PVE 天梯（Phase 9）与**扩展位**的异步 PvP（Phase 11）。两者共用段位体系，但**数值路径完全隔离**。

### 9.1 PVE 天梯（首发上线）

**每周一次 PVE 天梯**（首发不联网，AI 梯队模拟）：

- 玩家用自己收集的英灵组成 **3 队**（每队 6 人），依次挑战 3 个敌方梯队。
- 敌方梯队由历史人物组成的**虚构阵营**呈现（仅作为对手形象，定位为"演武场投影"，明确非史实对决，UI 文案需写清是竞技化设定，避免歪曲史实关系）。
- 段位：黑铁 → 青铜 → 白银 → 黄金 → 铂金 → 钻石 → 大师 → 王者，每周结算，赛季重置段位并开放新章节与新英灵。
- 奖励：竞技勋章 + 限定遗物材料 + 头像框（外观向，付费友好）。
- **此模式使用 PVE 完整数值**（正常养成值直接生效），是玩家检验养成成果的舞台。

### 9.2 异步 PvP 竞技场（扩展位，Phase 11）

- 完整设计见 **§6.6–§6.11**。要点复述：竞技归一化数值、竞技池系统统一开放、异步攻防爬梯、产出隔离在竞技专属池。
- 与 9.1 的关系：段位体系共用（同一赛季、同一段位段），但**两个模式的段位分独立计算**——9.1 衡量的是"养成强度"，9.2 衡量的是"战术水平"。二者不互相换算，避免玩家用 PvP 段位去推断自己的 PVE 强度。
- 9.1 的 AI 梯队可作为 9.2 的**训练场与教学场**：新手在 9.1 熟悉阵容搭配，再进入 9.2 竞争。

> 合规提醒：敌方梯队的"历史人物对决"设定必须在 UI 明确标注为架空演武，且不得暗示历史上真实发生过敌对关系（尤其近代国际人物之间）。

### 12.3 架构原则（实现者必须遵守）

1. **`core/` 纯度**：`core` 内禁止 `import` 任何 DOM/平台 API（`window`、`localStorage`、`document`）。时间通过 `time.ts` 注入，随机通过 `rng.ts` 注入。违反此原则将导致数值脚本无法在 Node 下运行。
   > **实施修正（Phase 8b 收尾）**：注入时钟的目的是**可测试**，不是**冻结时间**。表现层 store 必须注入会走动的 `systemClock`；`ManualClock` 只允许出现在测试代码里。
   > 历史教训：store 曾注入 `ManualClock` 且只在 `load()` 时 `set` 一次，导致整局游戏的 `history.at` / `obtainedAt` / `lastTickAt` 全部等于「页面加载那一刻」——抽卡记录时间戳全部相同，离线结算时长也按页面加载时刻算。排查一次「存档被莫名十连」时，这条冻结时钟让时间线完全对不上，浪费了大量时间。
2. **数据驱动**：新增英灵/关卡/遗物**只加配置不改逻辑**。所有系统逻辑必须遍历配置表，不得硬编码角色 id。
3. **单一数据源**：概率公示、抽卡执行、掉落表、掉落预览必须调用同一函数，不得复制定义（合规硬要求）。
4. **存档版本化**：`save/schema.ts` 带 `version` 与 `migrations: Record<number, (s)=>s>` 链，保证后续更新不丢档。
5. **配置与代码分离**：所有数值常数（曲线、概率、掉落率、乘区上限）集中在 `core/config/economy.ts`，便于调参与审阅。
6. **平台解耦**：`presentation` 不直接调用 `localStorage`，一律经 `platform/`。
7. **属性解析单一入口**（PvP 扩展的关键约束）：所有战斗必须经 `resolveStats(hero, ctx)` 取属性，战斗系统内部**不得**直接读取 `hero.level`、`relic.level`、`player.permBoost` 等养成字段。`ctx.mode === 'arena'` 时走归一化分支（§6.7）。违反此约束将导致 PvP 数值泄漏，破坏公平性——由 §15.1 的隔离测试守护。
8. **养成即配置**：竞技场相关的养成影响只允许通过"战术铭文槽位数量"与"系数封顶表"体现，禁止任何直接数值加成路径。
9. **存档写入单一入口 + 并发保护**：任何会改存档的动作都必须经 `presentation/stores/game.ts` 的 `persist()`，禁止绕过它直接写存储。`persist()` 采用**先读后写 + 外部优先**：写入前比对存储里的 `savedAt`，若存储版本比本进程已知的更新（说明另一个标签页/上下文在我们之后改过存档），**不得覆盖**，改为采纳外部版本并提示玩家；本次改动整体作废（存档是原子的，不会出现"扣了费却没出货"的中间态）。玩家主动的"重置进度"与"导入存档"允许强行写入。
   > **实施修正（Phase 8b 收尾）**：存档从 v3 升到 v4，新增 `savedAt` 字段与 `save/conflict.ts`（纯逻辑：`nextStamp` / `hasExternalUpdate`），由 `tests/unit/save-conflict.test.ts` 与 `tests/unit/store-save.test.ts` 守护。
   > 历史教训：原实现 `persist()` 无脑覆写存储，某个拿着过期存档的标签页/脚本一写就把另一方的进度整份抹掉，且毫无提示。同时，**localStorage 按 origin 隔离**——自动化脚本只要访问玩家正在游玩的 origin（`localhost:5173`），就会与玩家共用同一份存档。工具侧因此新增 `tools/capture/screenshot.ts`，内置 origin 守卫，禁止对玩家可能正在使用的 origin 截图。

### 12.4 核心数据结构（存档）

```ts
interface SaveData {
  version: number;
  createdAt: number;
  lastTickAt: number;              // 用于离线结算
  savedAt: number;                 // 最后一次成功写入存储的时间戳（多上下文冲突检测）
  player: {
    silver: number; exp: number; shards: Record<string, number>;
    emblems: number; crystals: number; tickets: number;
    skillStones: number; relicStones: number;
    permBoost: number;              // 圣杯重启累计永久加成
    rebirthCount: number;
  };
  heroes: Record<string, HeroState>;   // 已拥有的英灵实例
  relics: RelicInstance[];             // 遗物实例（含随机词条）
  equipped: { [slot: string]: { heroId: string; relicId: string } };
  team: { slots: (string | null)[]; presets: TeamPreset[] };
  gacha: { pitySSR: number; pity10: number; history: DrawRecord[]; pools: Record<string, PoolState> };
  campaign: { clearedStage: number; stageStars: Record<string, number>; chapterProgress: number };
  idle: { currentStage: number; autoAdvance: boolean; totalIdleSeconds: number };
  codes: string[];                      // 已兑换兑换码
  settings: { speed: number; sfx: boolean; skipAnim: boolean };
  stats: { firstStartAt: number; totalPulls: number; totalPower: number };
  // 竞技场（Phase 11；首发仅为 PVE 天梯段位数据）
  arena: {
    tierPoints: number;                 // PVE 天梯段位分
    pvpPoints: number;                  // 异步 PvP 段位分（与 tierPoints 独立换算）
    medals: number;                     // 竞技勋章（竞技专属，不可回流 PVE 经济）
    arenaLevel: number;                 // 竞技等级 → 战术铭文槽位数量
    runes: string[];                    // 已装备的战术铭文（最多 3）
    defenseLoadout: ArenaLoadout | null;   // 防守阵容快照
    snapshotHash: string | null;        // 阵容快照 hash，防止换阵
  };
}
```

**注意**：`arena` 字段与 `player.permBoost`（PVE 永久加成）在架构上严格隔离——竞技快照的生成函数不接收 `player` 对象，只接收显式列出的字段，从类型层面阻断数值泄漏。

**注意（实施修正 · Phase 8b 收尾）**：`savedAt` 是 v4 新增字段，旧档缺失时按 `0` 处理（`0` 永远「不比别人新」，因此旧档首次写入不会被误判成外部更新）。它只服务于**写入冲突检测**（§12.3 第 9 条），不参与任何数值结算。

## 15. 测试与验收标准

### 15.1 单元测试（Vitest，核心必须 100% 覆盖 `core/systems`）

| 测试 | 断言 |
|---|---|
| 属性合成 | 各乘区独立生效，无加法混入；上限生效 |
| 战力公式 | 边界值、单调性（任一属性提升战力必增） |
| 抽卡概率 | 100 万次实测 SSR 率 ∈ 公示值 ±0.01% |
| 保底 | 第 90 抽必出 SSR；十连内必出 SR+；SR 命中时计数 +2 |
| 保底继承 | 切换卡池后计数不变；十连共用计数 |
| 印记转化 | 重复英灵产出印记数量符合表；印记可兑换任意角色材料 |
| 离线结算 | 12h 封顶；8h 内效率 100%；8–12h 线性衰减；在线 3 倍率 |
| 战斗确定性 | 固定种子 → 相同战报（伤害序列逐条一致） |
| 伤害公式 | 减伤上限 75%、相性系数、暴击分支 |
| 羁绊 | 阈值触发/解除实时正确 |
| 存档迁移 | 旧版本存档升级后数据无损 |
| 配置校验 | id 唯一、引用存在、数值区间、无禁用词 |

**PvP 数值隔离测试（Phase 11 必过项，且 Phase 1 即需守护架构约束）**：

| 测试 | 断言 |
|---|---|
| **养成隔离** | 构造 PVE 养成相差 100 倍的两个账号（如 240 级满强化 vs 1 级裸装），`resolveStats(hero, {mode:'arena'})` 输出的**总战力差 < 15%**；且 `pve` 模式下两者战力差 > 50 倍（证明测试本身有效） |
| **永久加成屏蔽** | `player.permBoost` 变化对 `arena` 模式结果**零影响**（静态检查：`arena.ts` 不出现 `permBoost`） |
| **遗物强化屏蔽** | 遗物 60 级 vs 1 级，`arena` 模式下除套装效果外**零差异** |
| **封顶系数生效** | 技能加成不超过 +30%、套装效果不超过 ×0.7、羁绊不超过 ×0.6 |
| **竞技池对称** | 双方在 `arena` 模式下可用英灵集合完全相同，与玩家是否拥有该英灵无关 |
| **竞技等级只改槽位** | 提升竞技等级**不改变任何属性数值**，只增加铭文槽位（≤3） |
| **产出隔离** | 竞技结算产出的资源集合与 PVE 资源集合**无交集**（银两/经验/强化石/结晶 均为 0） |
| **快照不可变** | 匹配冻结后修改阵容，`snapshotHash` 校验失败，对局按原快照结算 |
| **幂等结算** | 同一 `challengeId` 重复提交结果一致、不重复扣次数 |
| **段位独立** | `tierPoints` 与 `pvpPoints` 互不换算、互不影响 |

### 15.2 E2E（Playwright）

1. 新玩家首启 → 完成 3 步引导 → 首次十连 → 获得 SSR → 放入阵位 → 挂机 10 场 → 领取收益 → 战力上升。
2. 抽卡页 → 打开概率公示 → 两栏数值与单测断言一致。
3. 注入 12 小时时间差 → 重启页面 → 离线结算弹窗数值正确。
4. 换编队 → 羁绊面板与战力数值即时变化。
5. **（Phase 11）** 竞技场配置阵容 → 提交进攻 → 匹配到防守阵容 → 对局结算 → 段位分变化 → 竞技勋章入账；且 PVE 侧银两/经验/强化石**数值未变**（产出隔离）。

### 15.3 PvP 公平性验收（人工 + 抽样）

- 抽样 200 组真实对局（若样本不足则用模拟对局替代），统计：
  - 段位越高胜率越接近 50%（无跨段位碾压）；
  - 使用同一阵容、仅养成投入不同的两个账号，对局胜率差 < 15 个百分点；
  - 不存在"某个特定英灵/套装"胜率显著偏离 50%（若偏离 > 8 个百分点，说明该组合过强，需调封顶系数）。
- 抽样 100 组"付费强度差距最大"的对局，验证低付费方仍有合理胜率空间。

### 15.4 性能与稳定性

- 战斗渲染 60fps（4× 倍速下不低于 30fps）。
- 挂机 2 小时内存不持续增长（日志与战报需截断，只保留最近 N 条）。
- 首屏可交互 < 3s（4G 模拟），首包 < 1.5MB（占位图阶段）。
- 无 console error；Safari/Chrome/微信内置浏览器/移动端适配通过。

### 15.5 合规验收（人工）

- 概率公示两栏齐全、精度两位小数、公示日期可见。
- 历史人物文本逐条过审：无贬义定性、无史实错误、无历史虚无表述。
- 敌人与 BOSS 全部为非历史人物，无任何指向真实历史人物的命名或形象。
- UI 全站无绝对化用语（跑禁用词扫描脚本）。
- 无真实支付入口、无诱导性文案。
- **（Phase 11）** 商城无任何"竞技属性/竞技强度"类商品；PvP 入口不被用作付费转化主路径；排行榜有举报通道；玩家数据境内存储。

## 16. 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| **范围过大**（单人开发） | 做不完 | 强制分阶段；Phase 0–6 完成即是一个可玩切片；美术占位优先；内容后置 |
| **Fate IP 边界** | 下架/律师函 | 不使用职阶制/职介卡/令咒/原作设定名词与美术；文案过禁用词扫描 |
| **历史题材审核** | 拒审 | 敌人非历史人物；文本中立；首发池避开近现代争议人物；每条史实可溯源 |
| **抽卡合规** | 整改/下架 | 公示与实现同源函数；保底继承；不拆角色强度；十连保底；历史记录可查 |
| **内容产能**（72 英雄 × 传记） | 拖期 | 分级投入：SSR 全文 / SR 2-3 段 / R-N 一句；配置与文本分离，可分批补 |
| **AI 立绘史实错误** | 口碑与合规 | 人工校验清单 + 禁用/替换机制；占位图先行不阻塞开发 |
| **数值后期崩坏** | 流失 | 独立乘区 + 飞升/圣杯重启 + 投放回收表 + 蒙特卡洛卡点分布模拟 |
| **无付费导致无收入** | 商业不可行 | 首发定位为"玩法验证 + 玩家测试"，预留支付适配层；商业化在二期 |
| **海外名人中文语境** | 舆论风险 | 传记只述史实；中立措辞；不做民族/宗教争议评价；不与真实国别对抗绑定 |
| **PvP 数值泄漏**（PVE 养成值混入竞技场） | 公平性崩塌，付费碾压 | `resolveStats` 单一入口 + `arena` 分支禁止引用养成字段 + 隔离测试（§15.1）守护 |
| **PvP 产出回流 PVE 经济** | 数值飞轮失控、PvP 反被养成支配 | 竞技专属池硬隔离，产出集合与 PVE 资源集合无交集，由测试断言 |
| **PvP 平衡缺少真实数据** | 上线即失衡，玩家流失 | 排期到 Phase 11；Phase 10 先用模拟做预校；无真实样本前不开放匹配 |
| **实时 PvP 的运维成本** | 拖垮单人开发节奏 | 首发只做异步竞技场（配置阵容即离线），实时对战列为远期可选 |
| **竞技池统一开放削弱抽卡动力** | 收集欲下降 | 有意取舍：抽卡动力留在 PVE（图鉴/传记/外观/羁绊深度）；用 PvP 的策略深度与段位奖励补偿留存 |

## 17. 未决决策（可在实施中确认，不阻塞开工）

1. **云存档**：首发是否需要跨设备同步？建议首发纯本地 + 导出/导入存档串，二期上后端。
2. **兑换码**：首发用内置一次性代码表（纯前端）还是直接上后端核销？建议内置表。
3. **遗物词条数量**：初版 4 主词条 / 3 副词条，还是精简到 3 / 2 以降低配置量？建议 3 主 / 2 副起步。
4. **战斗表现投入**：自研 Canvas 渲染器 vs 首版 DOM+CSS 降级。见 Phase 6 决策点。
5. **SSR 是否分池限时**：首发建议全常驻（无 UP、无限定强度差），后期运营再引入——限时池会引入保底继承与强度差的复杂合规面。
6. **英灵是否提供"第二形态"（真名解放/宝具解放）**：是，但强度提升必须走印记/材料路径而非抽卡重复，以满足 10% 合规线。
7. **PvP 的落地范围与节奏**：本方案已按"首发 PVE 天梯 + Phase 11 异步竞技场"排期。需确认的是——**是否接受首发不含实时 PvP**（推荐接受：实时对战的服务器/匹配/反作弊成本与单人开发不匹配），以及 PvP 是否值得占用 Phase 11 的资源（若 PVE 内容仍不足，可把该阶段让给内容扩充）。
8. **竞技池开放策略**：本方案建议"系统统一开放全部英灵"以保证绝对公平。替代方案是"按玩家拥有度加权"（未拥有的英灵数值打折而非禁用），能保留抽卡动力但公平性变复杂且更接近 Pay-to-Win——**不建议**。
9. **竞技等级与铭文的曲线**：§6.8 只给了"槽位 ≤3"的上限，具体阈值（竞技等级如何由养成折算、铭文强度）需在 Phase 10 用模拟定档。
10. **段位分跨模式换算**：本方案让 `tierPoints` 与 `pvpPoints` 完全独立。若产品侧希望"PVE 天梯段位能作为 PvP 匹配参考"，需引入有损换算——会增加匹配复杂度，需权衡。

## 18. 立即可执行的第一步

```bash
cd 超级圣杯战争
npm create vite@latest . -- --template vue-ts
npm i && npm i -D vitest @playwright/test
# 然后按 Phase 0 建 core/ 骨架
```

首个交付物应是 `core/` 纯逻辑层 + `tests/unit` 全绿 + `tools/balance/simulate.ts` 能打印出"第 1 章 30 关的难度曲线 vs 1 名 SSR 的养成曲线"两张对比图——这两张图是整个数值设计的地基，也是 Phase 1 之前唯一必须先看到的东西。

同时在 Phase 1 必须一起落地的还有 **PvP 架构预留**（`BattleContext` + `resolveStats(hero, ctx)`）：这是全案最容易被漏掉、且一旦漏掉代价最高的一步。漏做的后果不是"少个功能"，而是后期要重写整套战斗系统。
