# 《超级圣杯战争》抽卡数值挂机游戏 — 玩法与模块设计方案

> 版本：v1.0（设计阶段）｜平台：H5 网页（移动端竖屏优先，兼容桌面与微信内置浏览器）｜技术栈：Vue 3 + TypeScript + Vite + Pinia + Canvas 2D 自研战斗渲染器
> 本文件为实现前的最终设计基线，实现者请以此为准；开放决策集中在 §17，均不阻塞 Phase 0–2 开工。
> 当前实现以各节实施修正为准。合并后的实测结果见 [2026-11-18 合并验收记录](acceptance-2026-11-18-886b7c8.md)。

## Summary

**目标**：做一款以"抽卡收集全球历史名人"为驱动的**数值成长型挂机游戏**。玩家抽取英灵、编成小队、挂机自动推关，通过等级/星级/技能/遗物/羁绊五条养成线把战力推高，周而复始。

**范围**：H5 网页版，竖屏移动端优先；核心可玩闭环（抽卡 → 养成 → 编队 → 挂机推关 → 离线结算）完整；首发**不含真实充值**，用游戏内货币 + 兑换码跑通抽卡经济；美术走**占位图 → AI 生图**两阶段。

**关键设计决策**（详见各章）：

1. **双标签角色体系**（五行相性 × 五维定位），替代 Fate 式单一职阶制。既避开 IP 雷区，又让同一英灵可出现在不同阵容中，搭配深度高于职阶制。
2. **敌人全部为非历史人物**（灵体/妖异/幻想体）。历史人物只以正面友方英灵出现——这是历史题材在国内审核下的硬红线，不是风格选择。
3. **重复抽卡转化为通用"英灵印记"**，不给命座/潜能。直接满足"重复角色强度提升 ≤ 基础属性 10%"的合规要求，同时不惩罚收集党。
4. **数值全部走独立乘区**，养成系统之间用乘法而非加法堆叠，避免后期膨胀失控且便于单系统调参。
5. **核心逻辑层（`core/`）纯 TypeScript、零 DOM 依赖**，可在 Node 下跑数值模拟与单元测试；概率公示表由代码同一份数据生成，杜绝"公示与实现不一致"这一合规硬伤。
6. ~~**首发纯前端 + localStorage 存档**，不引入后端；后端（云存档/兑换码/配置下发）作为二期可插拔模块。~~
   → **已变更两次**：首发即有后端（认证 + 云存档），随后进一步改为**服务端权威**（见下方两次「实施修正」）。
7. **PVP 走"竞技归一化"路线（关键决策）**：PVP 战场中等级、遗物强化等级、印记投入**完全归零**，只保留星级被动、技能等级、遗物套装、羁绊并**打折封顶**。养成深度转化为**策略广度**（战术选项更多）而非数值大小，从根本上消除 Pay-to-Win。
8. **竞技池由系统统一开放全部英灵**，玩家的抽卡进度不影响对局可用性；PVP 产出只进竞技专属池（外观/称号/有限抽卡券），**绝不回流银两、经验、强化石**。抽卡动力留在 PVE（收集/图鉴/外观），PVP 靠策略——同时满足合规中"不得以随机抽取与 PvP 竞争诱导过度消费"的要求。
9. **战斗层现在就预留 `BattleContext`**：`resolveStats(hero, context)` 按 `pve` / `arena` 分流属性解析。这是 PVP 扩展成本最低、收益最高的架构决策，必须在 Phase 1 落地，否则后期需重写整套战斗系统。

### 实施修正（2026-11，后端与登录系统）

> **决策 6 已变更**：原方案「首发纯前端 + localStorage 存档，不引入后端」不再成立。
> 首发**必须**具备真实后端认证与云存档，否则无法满足「强制登录才能进游戏」与
> 「登录即跨设备同步」的产品要求，也拿不到可用于发行审核的账号体系与数据披露能力。

| 项 | 原方案 | 现方案（已实施） |
|---|---|---|
| 后端 | 二期再做，首发不做 | **首发即有**：Node + Fastify + SQLite，仓库内 `server/` |
| 认证 | 无 | 账号注册 / 登录 / 刷新 / 登出 / 注销，强制登录才能进游戏 |
| 存档 | 仅本机 localStorage | **每账号一份云存档** + 本机副本，登录即跨设备同步 |
| 冲突合并 | 未定 | 时间戳大者胜（`savedAt`），落后方采纳新版本，不做字段级合并 |
| 兑换码 | 内置一次性代码表 | 维持不变（`core/config/economy.ts` 的本地表） |
| 配置下发 / 排行榜 / 竞技结算服务 | P1 / P2 | 仍未做，优先级不变 |

**未随之变更的部分**：数值系统、合规口径、PvP 隔离、抽卡概率与保底规则**全部不变**——
后端只承载「认证 + 云存档」，不参与任何战斗与数值计算，`src/core/` 仍是纯逻辑层。

**仍待决策**：部署目标（托管方 / 域名 / 持久卷 / HTTPS）未定，当前默认本地跑通 + 预留 Dockerfile；
无 SMTP，找回密码暂缺，缓解手段是保留导出存档串并提示玩家定期导出。

### 实施修正（2026-11：服务端权威化 CS 架构）

> **决策 6 再次变更**：上一版的后端只做「认证 + 云存档」（客户端算完整份上传，
> 服务端当 blob 仓库）。现在改为**完全 CS**：**服务端是唯一权威真源**，
> 客户端只发「意图」，收结果，做渲染与播放。

| 项 | 上一版（客户端权威 + 整份上传） | 现方案（服务端权威） |
|---|---|---|
| 谁算结果 | 客户端算全部，再 `PUT /api/save` 整份上传 | **服务端算**（`core/systems/actions.ts` 纯函数），客户端只发动作 |
| 存档写入 | 客户端本地 + 整份上传（`PUT /api/save`） | **只有服务端能写**：`POST /api/action` 落库；`PUT /api/save` **已下线** |
| 本地存档 | 权威副本 | 降级为**只读缓存**（首屏加速 / 断网查看） |
| 冲突合并 | 时间戳大者胜（客户端侧） | 不需要合并：服务端串行执行，客户端只按响应覆盖镜像 |
| 随机序列 | 客户端持有种子与计数器 | **服务端持有**（`node:crypto` 生成种子并落库）；客户端只做域分离派生预览种子 |
| 离线收益 | 客户端按本地时钟结算 | **服务端按自己的时钟**在每次入口补算（断网不损失收益） |
| 断网时 | 照常能玩（本地算） | **离线只读**：能看缓存，操作一律拒绝 |
| 重试安全 | 无 | **幂等键 `actionId`**：同一 id 重放只回放上次结果，不重复扣费 |

**关键实现**（详见 AGENTS.md 铁律 #11 / #24 / #28 / #29）：

- **动作层下沉 core**：所有会改存档的编排写成 `core/systems/actions.ts` 的纯函数
  `(save, payload, ctx) → ActionOutcome`（先校验后修改、失败即原子、失败不消耗随机序列、
  收益只经 `rewards` 入库）。服务端 import **同一份** `src/core`，两端算出的结果天然一致。
- **协议只有一份**：`core/systems/action-protocol.ts`（请求 / 响应结构与负载校验）、
  `core/systems/actions.ts`（判别联合与结果）、`core/config/game-errors.ts`（错误码）。
- **服务端职责**：鉴权 → 调 core 动作层 → 落库 → 回结果；外加按账号串行化（`server/src/game/lock.ts`）、
  幂等日志（`action_log`）、账号标记（`user_flags`）、限流、离线补算。
- **数值系统、合规口径、PvP 隔离、抽卡概率与保底规则全部不变**——变的是「谁执行」。

**非目标**：真人匹配 / 排行榜实时刷新 / Postgres 与多实例部署 / 后台常驻 tick 队列 / AI 生图与美术管线。

### 权威链路整改（2026-11）

- **导入不是恢复旁路**：已有云存档禁止用导出串覆盖；仅无云档且未迁移账号可进行一次旧档迁移。迁移校验、账号标记及成功日志由服务端事务提交。客户端确认成功后才写本地完成标记，失败保留旧档、允许重试，不静默创建新档。
- **兼容风险**：旧档没有服务端签名，首次迁移的历史资产不能证明真实；账号级迁移标记也不能证明同份旧档未被别的账号使用。导入校验限制数据规模与数值、引用关系，重建随机状态及时间/周期控制字段，不能以旧时间戳追领收益。
- **时间归服务端**：`idle.tick.battles` 仅表示本次领取上限，不是可发收益依据。在线 3 倍与离线衰减保留，在线身份采用短时活跃租约，仅向未来续约；它是活跃协议，不是防脚本证明。在线/离线共享结算水位，余数保留，重复请求不得重复消费历史区间，频繁读取不能重置离线衰减。
- **PVE 编队战力、结算与观战**都通过 `buildPveContext` 计入永久加成和羁绊。通关事实、下一目标、失败目标分别记录，在线与离线结算共用这套口径。
- **断网恢复**：已载入游戏也能独立重新连接，拉取权威档成功后解除只读；换号后的旧响应不得覆盖新账号镜像，不自动重放未知结果的扣费动作。
- **竞技快照**：完整记录每英雄各槽位套装 ID；旧单值最多视为一件，不补猜多件。双方羁绊分别计算，永久养成继续隔离。奖励周期按北京时间周一零点切换，周计数与所属周一起持久化。

前述旧版「导出后跨设备粘贴导入恢复」「本地时间戳优先」方案均已被上述权威规则取代。

### P0 整改（2026-11-18）

- **抽卡**。登录后按当前卡池、保底进度与首次十连资格公示。首次十连资格适用于所有收录 SSR 的卡池，综合概率由执行与公示共同使用的保底规则得出。公开合规页在未登录时展示常规十连口径。
- **随机状态**。存档升级至 v6，旧权威档首次载入时由服务端轮换随机序列，保留角色、资源、抽卡历史和保底进度。云存档接口的拉档、成功、失败与重放路径统一投影客户端存档，客户端缓存和导出串也省略 `rng`。旧版账号缓存首次读取时会清理该字段，迁移通道原档保留。战斗预览使用独立的平台种子。
- **账号注销**。服务端确认 `DELETE /api/account` 后，客户端清理本机会话与对应的账号缓存。离线时保留会话及缓存并明确提示无法注销。令牌过期走续期后重试，且续期必须匹配原账号。若浏览器拒绝清理本机数据，界面会提示该状态。
- **动作幂等**。成功动作结果可重放 24 小时。超期后返回已执行状态与当前存档，动作 ID 在账号存续期间继续防重。过期正文在该账号后续成功业务动作时清理，心跳只计量与续约。SQLite 迁移保留仍存在的旧日志，旧版已淘汰的动作 ID 无法补回。
- **挂机卡关**。挑战目标与刷取关卡分别存档，实战战败只消费实际尝试场次。队伍回到已通关关卡继续获得掉落，满 10 个刷取胜场后重试挑战目标。回退关也战败时向低一关回退，到第 1 关仍失败时结束本次结算并保留剩余预算。玩家也可在关卡详情重新选择目标。在线领取、离线补算、分批领取共用同一规则。

## 1. 目标与范围

### 1.1 要做的东西

一款单页 H5 游戏。玩家进入后看到编队界面，队伍自动挂机打关卡；关卡提供经验与材料；玩家抽卡拿到新英灵、投入养成、把战力推过下一道关卡门槛。核心体验是**"数字在涨 + 搭配在变 + 离线也在变强"**。

### 1.2 首发交付清单

| 项 | 首发范围 | 二期 |
|---|---|---|
| 关卡 | 10 章 × 30 关 + 章 BOSS = 310 关 | 无限章节、难度回溯 |
| 英灵 | 72 位（SSR 12 / SR 24 / R 24 / N 12） | 扩池至 120+ |
| 遗物 | 60 件 + 12 套套装效果 | 遗物重铸/词条锁定 |
| 卡池 | 常驻池 + 2 个主题限定池 | 联动池、活动池 |
| 战斗 | 自动回合制，倍速/跳过 | 手动干预技能优先级 |
| 付费 | 无（兑换码 + 游戏内货币） | 支付 + 通行证 + 商城 |
| PvP | PVE 天梯段位（§9.1）+ 竞技数据结构 + `BattleContext` 架构预留（§6.7） | 异步竞技场（Phase 11）、实时 PvP（远期可选） |
| 联网 | 无（纯本地存档） | 云存档 + 排行榜 + 公告 |

> **实施修正（2026-11）**：首发已接入强制登录与服务端权威存档，竞技场提供归一化镜像试炼和段位天梯。接口见 §13，竞技场范围见 §9。

### 1.3 非目标（明确不做）

- 不做**实时** PvP 对战、不做公会、不做家园/社交系统、不做体力墙、不做每日强制在线时长。（PVP 扩展本身**纳入范围**，见 §6.6–§6.11：首发落地 PVE 天梯与异步竞技场的数据模型，实时对战列为远期选项。）
- 不做任何 Fate 原作元素：职阶制、职介卡、令咒、魔术体系、原作立绘、原作设定名词。借用的是"收集英灵 + 遗物 + 编队 + 自动战斗"的**结构**，表达全部原创。
- 不做真实支付、不接广告 SDK（仅预留适配层接口）。
- 不做配音（语音）、剧情过场；**演出动画仅限抽卡页**（战斗表现仍是数值型轻演出，见 §6.3）。

## 2. 约束与红线

### 2.1 内容合规（国内发行必须遵守）

| 项 | 要求 | 本方案落实 |
|---|---|---|
| 概率公示 | 游戏内显著位置公示，精确到小数点后两位，区分"基础概率"与"含保底综合概率" | 抽卡页固定「概率公示」入口 + 设置页二级入口；公示表由 `core` 同一份 `pool.rates` 数据渲染生成 |
| 保底规则 | 必须有保底、上限明确、进度可见、不得换池清零 | 90 抽大保底，计数跨常驻池与限定池**继承**并显式展示 |
| 拆分角色强度 | 重复获取带来的强度提升 ≤ 基础属性 10%，否则须提供免费替代 | 重复英灵 → 通用「英灵印记」，强度不绑定单一角色 |
| 历史题材 | 不歪曲事实、不抹黑英雄、不传播历史虚无主义 | ① 敌人为非历史人物；② 文本中立且以正面事迹为主；③ 首发池不含近现代争议人物；④ 传记只述史实不评功过 |
| 绝对化用语 | 禁止"必出""100%""最高品质"等表述 | 全站文案与 UI 禁用词清单（`content/compliance/forbidden-words.md`） |
| 未成年人 | 提示、理性消费提示、求助渠道 | 首发虽无充值，仍保留合规页与年龄声明 |
| 隐私 | 单独授权、境内存储、可导出 | 首发纯本地，无采集；埋点默认关闭且可一键清除 |

### 2.2 IP 边界

- 角色原型为真实历史人物（公有领域），美术必须原创，不得使用任何现成游戏/影视/博物馆图片（含博物馆摄影作品，摄影权另计）。
- 文案避免"某著名 IP 的某某英灵"的直接指涉；不出现"职阶""职介""从者""令咒"等强指向词。命定道具改称**「圣痕遗物」**。

### 2.3 技术约束（本机环境实测）

- Node.js v24.13.0、npm 11.11.0、Git 2.43.0 可用；**Python 不可用** → 所有数值模拟脚本用 Node + TypeScript 编写。

## 3. 设计支柱

1. **数值是唯一语言**：所有系统都必须能翻译成一个玩家看得懂的数字（战力）。看不懂的深度不做。
2. **挂机不等于无脑**：自动战斗负责执行，**编队、遗物、羁绊、抽卡时机**才是玩家做的决策。
3. **每次上线 30 秒内有正反馈**：一键收取、一键升级、战力数字跳动。
4. **不惩罚离开**：离线收益只衰减不归零（保底 8h 满额），但在线效率恒定在线 3 倍。
5. **收集驱动 + 泛化养成**：抽到新英灵是快乐，但重复的英灵也有明确去处（印记），杜绝抽卡挫败感。

## 4. 核心循环

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   [挂机推关] → 经验/银两/材料/关卡掉落                 │
        │                                              │
        ▼                                              │
   [养成] 等级·星级·技能·遗物·羁绊 → 战力↑              │
        │                                              │
        ▼                                              │
   [编队] 6 槽位 · 五行相性 · 定位搭配 → 战力↑          │
        │                                              │
        ▼                                              │
   [卡关] 战力 < 关卡需求 → 战力不足                    │
        │                                              │
        └──→ [抽卡] 获得新英灵/印记/遗物 ──┘
```

### 4.1 三层循环与目标感来源

| 层级 | 周期 | 玩家在做什么 | 目标感 |
|---|---|---|---|
| 短循环 | 30 秒 – 2 分钟 | 收离线收益、一键升级、领日常、点一次推关 | 数字在涨 |
| 中循环 | 2 小时 – 1 天 | 抽卡、突破、换遗物、推 1-2 章 | 下一关/下一颗星 |
| 长循环 | 2 周 – 4 周 | 集齐 12 SSR、满羁绊、清完 10 章、赛季段位 | 图鉴完成度 |

**自检**：任何一个系统如果"上线点一下就没了"，它是失败的孤岛，必须被移除或改造。

### 4.2 核心循环外的两个异步驱动

- **离线收益**：给不常上线玩家的正反馈，保证长周期不流失。
- **每日/每周常驻**：`每日签到`（7 天循环）+ `竞技场周常`（天梯段位，含 PVE 梯队与异步 PvP 防守阵容）。

## 5. 数值系统（核心）

### 5.1 属性面板

**基础六维**（英灵自身）：

| 属性 | 键 | 作用 | 数值型挂机中的角色 |
|---|---|---|---|
| 攻击 | `atk` | 伤害输出基数 | 主输出项 |
| 防御 | `def` | 减伤基数（参与伤害公式分母） | 承伤项 |
| 生命 | `hp` | 生存上限 | 主生存项 |
| 速度 | `spd` | 行动顺序 / 回合数效率 | 稀缺乘区，防同质化 |
| 暴击 | `crit` | 暴击率 | 副乘区 |
| 暴伤 | `cdmg` | 暴击倍率 | 副乘区 |

**衍生三性**（不占养成位，由基础值换算，避免属性面板过载）：

- `dodge`（闪避）= f(spd, 等级)
- `hit`（效果命中）= f(spd, 定位)
- `res`（效果抵抗）= f(def, 等级)

### 5.2 战力公式

```
主战 = atk × 2.2 + def × 1.6 + hp × 0.28
暴击乘区 = 1 + crit × cdmg          // crit、cdmg 均按小数计
速度乘区 = 1 + min(spd, 600) × 0.0012
战力 = 主战 × 暴击乘区 × 速度乘区
```

设计意图：
- 战力只做**横向可比**（用于 PVE 门槛判定、排行榜），**不做战斗输入**。战斗仍走独立伤害公式，避免"战力"变成黑箱。
- `spd` 乘区有上限（600），防止速度成为唯一最优解。
- 任何养成系统的贡献都能在战力面板上看到增量（成长可视化是数值挂机的留存命脉）。

### 5.3 属性合成：独立乘区原则

```
最终属性 = 基础属性(等级, 星级)
         × (1 + 遗物加成%)
         × (1 + 天赋/技能被动加成%)
         × (1 + 羁绊加成%)
         × (1 + 境界突破加成%)
         × (1 + 进度增益%)
```

规则：
- 每个系统**独占一个乘区**，不做加法叠加。加法堆叠会让后期数值失去意义且难调参。
- 每个乘区可独立调参，控制总膨胀速度（数值飞轮的两个阀门之一）。
- 上限：任一乘区系数 ≤ +300%，防止单点爆炸。

### 5.4 养成线（5 条）

| 养成线 | 消耗 | 上限/门槛 | 作用 |
|---|---|---|---|
| **等级** | 英灵经验 | 1–240，分 4 境界：凡阶(1-60)/名阶(61-120)/圣阶(121-180)/神阶(181-240) | 基础属性主成长 |
| **星级** | 同名碎片 + 英灵印记 | 1★–6★，每星解锁 1 条被动天赋 | 基础属性倍率 + 被动 |
| **技能** | 术式结晶 + 银两 | 3 技能 × 1–20 级 | 战斗行为改变 |
| **遗物** | 遗物本体 + 强化石 + 银两 | 6 槽位，遗物 1–200 级（Lv60 起进入淬炼段，价格指数上升），套装 2/4/6 件效果 | 最大乘区，深度主来源 |
| **羁绊** | 自动（编队触发） | 标签计数阈值 | 编队策略价值 |

**境界门槛**：进入下一境界需特定材料（如"名阶"需 1 张指定名阶突破书），制造周期性目标。

**经验曲线**：`expToNext(L) = 60 × 1.025^(L-1) × expScale(境界)`，`expScale` 为**绝对台阶系数**：凡阶 1 / 名阶 5 / 圣阶 15 / 神阶 40。

> **实施修正（Phase 2）**：原文写作 `60 × 1.115^(L-1)` 且「境界间用系数重置基准」。若指数按**境界内局部等级**重置，境界切换那一级的经验需求会断崖式下跌——
> `expToNext(60) = 60 × 1.115^59 × 1 = 36,929` → `expToNext(61) = 60 × 1.115^0 × 8 = 480`，**骤降 77 倍**。
> 后果是玩家一进新境界就能瞬间连升数级，境界门槛形同虚设。
>
> 修正为**全局等级指数 + 境界绝对台阶**：境界切换是 `expScale` 带来的**向上**台阶（真正的门槛），指数项按全局 239 级重新标定（`EXP_GROWTH` 由 1.115 下调为 1.025，`expScale` 由 1/8/40/200 重新标定为 1/5/15/40）。
> 实测：单人 Lv1→240 累计 ≈ 2.9×10⁷，6 人编队总需求 ≈ 1.77×10⁸，与主线经验投放 4.0×10⁸ 同量级（回收率 2.26×）。
>
> **同批修正**：`skillLevelCap` 原式 `realm.maxLevel - realm.minLevel + 1 + 10`，因每境界区间恒为 60，该表达式恒等于 70，**境界门槛完全失效**（Lv1 即可把技能升满 20 级）。改为 `level - realm.minLevel + 1 + 10`，进入新境界时技能上限回落至 11 级、随境界推进解锁到 20 级。

> **实施修正（养成闭环）**：「境界门槛」只有 core 里的配置（`REALMS[].breakMaterial = 'realm_book_famed'` 等），
> **从未真正实现**——那些道具 id 在整个项目里没有任何定义、掉落来源或 UI。而 `applyExp` 的等级硬上限是
> `next.minLevel - 1`，于是实测喂经验时英灵**卡死在 Lv60**：`blockedByRealm = true`，
> 喂多少经验都不再升级（`totalExpToReach(240) ≈ 2.9×10⁷` 实际只能吃到 `totalExpToReach(60) ≈ 7874`）。
>
> 同时，喂经验本身也是**只加不减**的：`applyExp` 直接把经验塞给英灵，玩家经验池 `player.exp`
> （战斗 / 挂机掉落的主要来源）只增不减 → 经验池是死资源，喂经验等于**白嫖等级**。
> 这两条叠在一起会造成最坏的结果：经验池被喂干，英灵却卡在 Lv60 升不动级。
>
> 修正：
> - **喂经验扣玩家经验池**（`player.exp`），按请求量扣，喂不完的部分存在英灵自己的 `hero.exp`，
>   卡在境界门槛上也不丢；余额不足直接拒绝并提示，不产生负数。
> - **境界突破用「英灵印记」实现**（复用已有资源，不新增道具系统）：消耗 10 / 20 / 40 枚，
>   等级跨入新境界的第 1 级（Lv60→61 / Lv120→121 / Lv180→181），
>   门槛上存着的经验立即兑现成等级。配置字段由 `breakMaterial` 改为 `breakCost: { emblems }`。
> - **喂经验档位收进 `economy.ts`**（`LEVEL.EXP_FEED_OPTIONS`），表现层不再就地写数字；
>   另加「全部喂入」按钮，避免玩家攒了几百经验却喂不出去。
>
> 数值影响：印记新增出口（单人 70 枚，6 人编队 420 枚），使印记回收率从 1.32× 掉到 0.98×（缺口），
> 故把印记投放上调（普通关 `2a`→`2.5a`，BOSS 关 `3a~8a`→`4a~11a`），回收率回到 **1.25×**；
> 其余四类资源回收率不变（经验 2.26× / 银两 111× / 术式结晶 2.11× / 强化石 1.57×）。
> 难度曲线与实战曲线未受影响（各章 BOSS 通关率仍为 100%，模型 / 实战都是第 310 关）。
>
> 回归守护：单测「喂经验 + 突破可以一路到 Lv240」+ E2E「喂到境界门槛后，
> 消耗英灵印记突破到新境界，存量经验立即兑现」。
>
> **实施修正（2026-11，roadmap P1-2 难度曲线重标定）**：`LEVEL.EXP_BASE` 60 → 900 之后，
> 单人 Lv1→Lv60 需要 118,500 经验（≈40 分钟真实挂机），这条 E2E 的**前置**改为用
> 玩家可用的 `save.import` 动作导入 Lv59 主角（走服务端动作层，不碰数据库），
> 经验仍由真实挂机刷出、喂经验 / 突破仍走真实服务端动作——实测约 1.5 分钟。
> 「Lv1→Lv60 要爬多久」由上面的 core 单测守着，E2E 守的是**门槛语义**
> （卡门槛 → 突破 → 存量经验兑现）。

> **实施修正（2026-11，文字战报列表）**：此前观战只有画布底部**一行**「当前事件」，
> 一闪而过、读不到全局，玩家无法整体回顾一场战斗。新增**可滚动的文字战报列表**
> （`presentation/components/BattleLogPanel.vue`，画布下方，默认展开、可折叠）。
>
> 关键决策：
> 1. **列表范围是时间的纯函数**：可见条目数 = `projectState(t).eventIndex`
>    （新增 `visibleLogEntries(timeline, t)` 纯函数，与画面同源）。
>    因此倍速 / 跳回合 / 重播都不会让战报和画面对不上——**不许**在组件里
>    自己维护一个「已读了多少条」的增量计数（那就退化成铁律 #20 禁止的累积式状态）。
> 2. **文案一律取 core 的 `entry.text`**，表现层不自己拼装战斗事实（铁律 #16）。

> 3. **自动跟底 + 手动上滚可停**：播放中列表贴着底部；玩家往上翻则停止跟底，
>    并出现「↓ 最新」按钮——否则想回看上一回合会被强行拽回去。
> 4. **战报上限 1500 条仍适用**：最坏情况（30 回合 BOSS）实测 356 条，
>    列表一次性渲染无压力；战报不入存档，内存无压力。

> **实施修正（2026-11，遗物获取途径）**：玩家反馈「遗物没有获取途径」。排查结论：**配置齐全但功能不可用**——
> 掉落表里写着「每场战斗必掉 1 件遗物」（`stage_c` 权重 N60/R30/SR10，`boss_c` 权重 R45/SR40/SSR15），
> 遗物配置 60 件 / 12 套装、强化石、套装效果、强化与分解一应俱全，
> 但玩家在仓库里**一件都拿不到**。
>
> 根因在 core 的**旁路数组**（AGENTS.md 新增铁律 #26）：
> `core/systems/idle.ts` 的 `rollRewards()` 把遗物放进**独立数组** `relics`，
> `mergeRewards()` 也**不合并**它 → `rewards.relics` **从未被赋值**；
> 而 store 的 `applyRewards()` **只读 `rewards`**（铁律 #4 的单一数据源），
> 于是它的遗物入库分支是**死代码**，挂机 / 离线结算产出的遗物 **100% 被丢弃**。
> `IdleRunResult.newRelics` 同样没人消费。
>
> 修复（改在 core 侧，不在表现层补一套消费逻辑）：
> - `rollRewards()` 把遗物清单**同时**放进 `rewards.relics`；
> - `mergeRewards()` 累加遗物数组（多场战斗的遗物必须逐场累加，否则只剩最后一场的）；
> - `scaleRewards()` **不缩放**遗物数组——遗物是「实例」（实物），外推段没有对应实例，
>   按比例裁数组会造出不存在的东西；
> - `newRelics` 保留，但**只用于「本次获得提示」**，入库仍只认 `rewards.relics`。
>
> 附带澄清：**手动「观战」是纯预览**（只播回放、不结算任何掉落），
> 遗物 / 银两 / 经验的唯一产出路径是**推征**（挂机按钮「推征 N 场」）与离线结算。
>
> 回归守护：`tests/unit/store-relic.test.ts`（真实 store 链路 5 例：挂机入库 / 实例结构完整 /
> 多场累加 / 落盘不丢 / 离线结算）+ `tests/e2e/relic.spec.ts`（玩家操作链路 2 例：
> 推征 → 仓库有遗物 → 刷新不丢 → 能打开详情并装备；连推两轮逐轮累加）。

> ① 遗物没有图标；② 英灵页要能一键推荐装备；③ 遗物要有 2/4/6 件套装加成。

> **实施修正（2026-11，roadmap P1-2 收尾 · 后期银两 / 强化石的回收出口）**
>
> 上一节末尾登记的「养成深度」问题 1（银两 / 强化石后期彻底过剩）在本轮解决。
>
> **问题量化**（`artifacts/baselines/recalibrate.json`，40 天真实推进模拟）：
> 累计产出银两 ≈ **4.74×10⁹**、遗物强化石 ≈ **1.5×10⁶**，
> 而**旧口径的终身出口**只有 1.06×10⁶ 银两 + 4,248 石
> （36 件 × 59 级 × 500 银两 / 2 石）——**差 3~4 个数量级**。
>
> 根因不是产出太多，而是**出口是常数**：遗物强化封顶 Lv60、单位成本恒定，
> 理性玩家**第 2 章就把 36 件遗物全部顶满**，此后银两与强化石再无任何去处。
> 而产出是**指数增长**的（银两 2.7×/章、强化石 1.3×/章）——
> **恒定出口永远吸收不了指数产出**。
>
> **修正（config-only，不新增动作 / 存档字段 / UI 系统）**：
> - **标准段（Lv1 → 60）逐位不变**：价格恒定 500 银两 + 2 石，主词条 +3%/级。
>   早期经济与首日节奏完全不动（实测：若从 Lv1 就指数上涨，新号首日遗物只能到 Lv45，
>   推进从「第 154~181 关」掉到「第 147 关」——**过剩出在后期，出口就只该开在后期**）。
> - **淬炼段（Lv > 60）价格指数上升**：银两每级 ×1.10（`COST_GROWTH`）、
>   强化石每级 ×1.06（`STONE_COST_GROWTH`）。
>   两个底数**分开**的原因：强化石产出增速（1.3×/章）远低于银两（2.7×/章），
>   共用一个底数会让强化石先见底。
> - **淬炼段收益递减**：主词条 +0.6%/级（`PCT_PER_LEVEL_OVER`）。
>   淬炼段是**回收阀门**不是新的战力来源——若仍 +3%/级，推到 Lv160 就是 ×4.6 倍遗物倍率，
>   会单方面拉爆难度曲线（标定锚点是按参考队伍战力量出来的）；递减后推到上限也只有 ×1.30。
> - **强化上限 60 → 200**（`MAX_LEVEL`）：上限只是**护栏**——
>   成本随等级指数上升后，玩家在 40 天主线内大约推到 Lv150~170，**永远碰不到上限**
>   （碰不到才是「出口一直开着」）。
> - **分解返还改为按累计投入折算**：`(累计投入 + 稀有度残值) × 0.5`。
>   旧公式（`500 × 等级 × 稀有度系数`）让 SSR 遗物「强化到 60 级再分解」**净赚 2.54×**
>   （投入 29,500 银两、返还 75,000）——那是**造币漏洞**，不是回收阀门。
>   保留「稀有度残值」是为了让 1 级废件的返还与旧口径逐位相同（SSR 1,250 银 / 2 石），
>   仓库溢出自动分解才不会变成纯惩罚。
>
> **配套修掉的三个口径问题**：
> - **批量强化扣费**从「单级价 × 级数」改为 `relicTotalCost(to) − relicTotalCost(from)`
>   （指数成本下前者会算错）；
> - **分解返还与强化成本共用同一份累计成本**（`relicTotalCost`），
>   玩家逐级点的账与批量按钮的账必须逐位对得上（铁律 #4）；
> - **工具侧护栏**（`tools/balance/newplayer.ts` / `recalibrate.ts`）的强化次数上限
>   由 3,000 抬到「满编 × 上限」，否则 7000+ 次升级会被中途截断、模拟出的消耗偏小。
>
> **规则必须看得见（铁律 #27）**：铸造页与遗物详情页在遗物 Lv ≥ 60 时显示淬炼段规则
> （价格每级 ×1.10、强化石 ×1.06、主词条每级 +0.6%），
> 文案与数字的唯一出处是 `presentation/utils/relic-hint.ts`（两处视图共用）。
>
> **实测（40 天真实推进模拟，`npm run balance:recalibrate`）**：
> - 已装备遗物平均等级 **Lv6.4 → Lv162.1**（持续增长，永不撞 200 上限）；
> - **银两逐章回收比 1.00×**（旧基线第 3 章是 424.56× 的纯堆积），
>   玩家余额常年停在「几百银两」——**钱没有堆积，出口一直开着**；
> - 遗物强化石的**逐章回收比最小 1.82×**（旧基线 8.7×/7.8×），
>   仍是全场最紧的资源，但它已被吸进遗物等级，不再是躺着的死资源；
> - **术式结晶仍是过剩项**（最小 24.96×）：它的**终身出口本身就很小**
>   （3 技能 × 20 级 × 6 人 × 12 石 = 4,320 颗），而产出按 `ADVANCE_GROWTH` 指数增长——
>   这是**结构性**过剩，与本轮的遗物阀门无关，已单独登记为 roadmap 待办。
>
> **回归守护**：`tests/unit/relic-economy.test.ts`（14 例：标准段恒价 / 淬炼段指数递增与连续性 /
> 累计投入 = 逐级累加 / 淬炼段收益递减且上限增幅有界 / 分解返还不构成造币通道 /
> 批量强化扣费 = 逐级累加 / 余额不足拒绝且不产负数）
> + `tests/unit/actions.test.ts`（满级拒绝读 `RELIC.MAX_LEVEL`）+ `tests/e2e/relic.spec.ts`。
>
> **闸门口径同步修正**（`tools/balance/recalibrate.ts`）：
> 回收阀门建好之后，逐章流量比会**贴着 1.0 上下摆动**（实测第 3 章银两 0.99995×），
> 因为产出与消耗都是**离散动作**（一次强化 = 500 银两 + 2 石）——
> 「差一次动作」不是缺钱，而是**出口已饱和**。因此判定改成两条件：
> ① **累计净额全程 ≥ 0**（玩家从未入不敷出）；
> ② 逐章欠账不超过**一次最小消费动作**的成本（容差取自游戏自己的决策粒度，
> 不是随手取的小 epsilon；且必须按玩家**当章实际付过的最贵一次**取——
> 淬炼段一次强化几十万银两，用基础价 500 会把「差一步」误判成「缺一大截」）。
> 判定口径抽成纯函数 `tools/balance/recycle-verdict.ts`，

> 导致第 1 章凭空少一块、报出一个不存在的卡手。

### 5.7 离线收益曲线

```
离线时长 t (小时) → 效率 eff(t)：
  t ≤ 1    → 100%
  1 < t ≤ 3 → 线性衰减 100% → 60%
  t > 3    → 0（默认封顶 3h）

实际收益 = 在线速率 × 有效时长(小时) × eff(t) × 挂机倍率
```

> **实施修正（roadmap P1-2 难度曲线重标定）**
>
> - 满效率时长由 **8h 收窄到 1h**、封顶由 **12h 收窄到 3h**。原值下「一天的挂机预算」
>   = 8h × 600 场/h = **4,800 场**，而全游戏只有 310 关 ≈ 1,000 场 —— 一天的预算是整个游戏的
>   4~5 倍，于是新号首日就把等级顶格、经验与银两彻底贬值（实测见 §12.7）。
> - 收窄后 **f(24h) = 2.6h**（1h 满效率 + 2h 尾部均值 0.8），即「每天上线一次领奖」的被动档
>   一天拿 1,560 场。
> - ⚠ **上线频率是口径的一部分，不是细节**：离线曲线按「**累计时长**」折算，而累计时长
>   只在玩家**活跃**（`onlineMs > 0`）时才归零，于是
>   「每小时上线一次」与「每天上线一次」的首日收益相差 **9 倍**。
>   两处基线必须写清用的是哪一个：`balance:newplayer` 默认「每小时上线一次」（活跃首日），
>   `balance:recalibrate` 用「每天上线一次」（被动档，40 天通关基线）。
> - 铁律：**任何模拟挂机的工具都必须走真实的「上线 → 心跳 → 领奖」序列**，
>   不得直接改 `save.idle.measuredAt` / `activeUntil`——那样永远走不到「累计归零」那条分支，
>   累计时长涨到封顶后收益恒为 0（历史 bug：首日基线只算了 2.6 小时的收益）。

- **在线效率恒定为离线的 3 倍**（活跃玩家 1 小时在线 ≈ 离线 3 小时），保证活跃有价值。
- 收益结算按"最近 N 场战斗"回放，而非简单按时长线性给——战斗有随机性，回放结算让收益与实际推关表现挂钩，且不会出现"挂机 12h 打不过却照样领满"的割裂感。
- 结算弹窗展示明细（打了多少场、掉落什么、经验多少），并预留「立即结算」按钮位（后续可接激励视频/道具），首发该按钮为"直接领取"。

> **实施修正（2026-11，服务端时间账本）**
>
> - 可见页面每 5 秒发送 `idle.heartbeat`，服务端向未来续约 15 秒。有效租约期间按基础速率的 3 倍计量，其他时段按离线曲线计量。
> - 离线曲线描述每一段新增时间的效率，按曲线累计折算。前 1 小时按基础速率计算，后 2 小时从 100% 线性降至 60%。离线 3 小时及以上一律折算 2.6 小时（封顶）。

### 5.9 PvP 数值隔离原则（摘要）

挂机游戏的养成线是**单调递增**的，而 PvP 要求**对等**——这是两者最根本的冲突。若直接把 §5.1–§5.4 的 PVE 数值搬进 PvP，结果是纯 Pay-to-Win：付费玩家用战力直接碾压，且战力数值无上界、无法收敛。

因此确立三条隔离原则（完整设计见 §6.6–§6.11）：

1. **归一化**：PvP 战场中所有英灵的基础属性按定位模板重置，不继承 PVE 的等级/星级/遗物强化数值。
2. **策略化**：养成投入在 PvP 中只影响**可选战术条目的数量与系数**（星级被动、技能等级、遗物套装、羁绊），且系数**打折并封顶**。养成深度 → 策略广度，而非数值大小。
3. **产出隔离**：PvP 产出只进竞技专属池，**不回流**银两、英灵经验、遗物强化石、抽卡结晶，避免"PvP 变强 → PVE 加速 → 数值飞轮失控"。

配套的架构约束：`core/systems/arena.ts` 中**禁止引用** `player.permBoost`（圣杯重启永久加成）等 PVE 无限加成项；PvP 结算函数不接受 PVE 养成数值，只接受竞技快照。这条约束需要有单元测试守护（见 §15.1）。

## 6. 战斗系统

### 6.1 形态

**回合制自动战斗**，双方最多 3 行动位（玩家前排 3 + 后排 3 编队映射到 6 人，但战斗同时最多 6v6？—— 简化如下）：

- 玩家侧：编队 6 人全员参战，按 `spd` 决定行动顺序。
- 敌方：一关 = 1–5 个怪 + 章末 BOSS。
- 每回合全体存活单位各行动一次；单场战斗典型 3–8 回合。
- 玩家不可手动操作，但**可在战前配置**：技能优先级（普攻/技能自动选）、预设"不上场"等。

### 6.2 伤害公式

```
基础伤害 D = atk × (atk / (atk + def_eff)) × 技能倍率
D ×= (1 + 暴击加成)         if 暴击
D ×= (1 - 减伤率)           // 减伤率上限 75%
D ×= 相性系数               // 我克 1.25 / 平 1.00 / 克我 0.85
D ×= 随机因子               // 0.95 – 1.05
D = max(1, round(D))
```

### 6.3 战斗表现（数值型，不做重演出）

Canvas 2D 渲染，自研轻量渲染器（约 400–600 行）：

- 布局：上排敌方 3 位、下排我方 3 位（按前/后排分组），头像圆形 + 血条 + 定位色标。
- 表现：技能触发时头像闪光 + 屏幕飘字（暴击/治疗/伤害数字），BOSS 额外描边与血条分段。
- 倍速：1× / 2× / 4× / 8×（跳过结算，直接展示结果摘要）。
- 结算：战后弹出"回合数 / 伤害统计 / MVP 英灵 / 掉落"，MVP 与伤害统计是重要的正反馈点。

> 若自研渲染器排期吃紧，降级方案：首版仅用 DOM + CSS 动画表现，Canvas 渲染器作为第二阶段增量。

> **实施修正（2026-11，站位与目标选择）**：原文「上排敌方 3 位、下排我方 3 位（按前/后排分组）」未定义
> **前后排的朝向**与**目标选择的并列判定**，实现时两处都做错了：
>
> 1. **渲染朝向反了**：原实现按「插入序号」排布并让前排落在远离敌人的一侧，
>    观战时看到的是后排贴敌、前排缩在角落。改为按**真实编队槽位号**（0-2 前排 / 3-5 后排）

### 6.5 补充：关卡难度曲线重标定（数值断层修复）

> 本条目记录把「第 7~10 章 BOSS 实战通关率 0%」修掉的**独立提交**。
> 与前面的召唤机制修复分开提交，便于单独回滚。

#### 症状

`npm run balance:battle`（真实跑战斗）实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 实战能过的最后一关 | 第 **246** 关 | 第 **310** 关 |
| 第 7~10 章 BOSS 通关率 | **0%** | **100%** |
| 各章 BOSS 通关率（满养成档） | 1~2 章 100%，其余 0% | **全部 100%** |
| 战力模型 vs 实战 | 模型 310 / 实战 246 | **模型 310 / 实战 310** |

#### 根因（两层）

1. **难度曲线总量纲失控**：旧公式 `BASE_POWER × CHAPTER_GROWTH^(章序-1) × IN_CHAPTER_GROWTH^(关序-1)`
   让敌方属性缩放总跨度达到 **2.4×10⁵**，而玩家战力从 Lv1 到满养成只有约 **4.9×10³** 倍
   ——敌方强度比养成快 50 倍，玩家永远追不上。
   再叠上敌人**基础属性**本身跨章增长 7.5 倍（BOSS 血量 2400 → 18000），
   等于难度被**重复计入**两次。
2. **战力门槛与真实难度脱钩**：`powerRequired = BASE_POWER × scale` 完全不看敌人基础属性，
   于是「隐含门槛基数」随章从 3213 漂到 27933（8.7 倍漂移），
   门槛在后期比真实需求松 8.7 倍 → 挂机会把玩家推进到**打不过**的关卡 → 打输 →
   结算中断 → 玩家零收益卡死（这是比「打不过」更严重的失败模式）。

#### 修复

1. **机制前置修复**（不改数值就调不出合理曲线）：
   - 护盾阶段：原实现「盾被打掉后下一发又补」→ BOSS 实际无敌、难度对缩放极度敏感
     （第 10 章 BOSS 在缩放 733~1500 之间通关率从 83% 掉到 0%）。改为**护盾只挂一次**。
   - 狂暴阶段（`enrage`）配置齐全但战斗代码**从未读取** → 机制完全空转。补齐实现。
2. **难度曲线改为「逐章锚点 + 统一章内增长」**：
   - `STAGE.SCALE_ANCHORS`：每章**首关**的敌方缩放锚点，由真实战斗模拟标定
     （玩家水平取自经验投放模型推出的等级阶梯 Lv10/31/62/78/108/133/164/193/225/240；
     对该章 BOSS 二分「能稳过(≥90%)的最大缩放」→ 取其一半 → 除以章内总跨度 1.25）。
   - 章内 30 个普通关按 `IN_CHAPTER_SPAN = 1.087` 等比铺开，章末 BOSS 再 × `BOSS_MULTIPLIER = 1.15`
     （章内总跨度 1.25）。相邻章锚点比 ≥ 1.30，保证章边界严格递增。
   - 放弃「单一指数外推」：在「章边界严格递增 + 缩放总跨度 ≤ 玩家成长跨度」两个约束下，
     单指数结构**数学上无解**（章内跨度必须小于相邻章比值，而相邻章比值因各 BOSS 机制差异在 1.3~2.9 间波动）。
3. **战力门槛改为「逐章锚点 + 章内等比」**：
   - `STAGE.POWER_ANCHORS`：每章**BOSS 关**的门槛 = 玩家「刚能稳过该章 BOSS」时的战力。
   - 章内从「上一章 BOSS 门槛 × 1.05」等比升到本章 BOSS 门槛。
   - 门槛是挂机自动推进的**放行线**，必须**不早于**该关真正打得赢的时刻，
     否则会推进到打不过的关卡 → 零收益卡死。宁可略紧不可略松。
4. **掉落曲线与难度曲线解耦**：旧实现把难度倍率（3.5）直接当掉落倍率用，
   两者互相绑死无法单独调整。现在掉落用独立的 `DROP_GROWTH = 3.5`（数值不变，
   只解耦语义），难度锚点反过来是按这条投放曲线推出的玩家水平标定的。

**一、旧标定流程的三处结构性缺陷**

1. **标定输入是「模拟涌现的阶梯」→ 自我放大**：
   用模拟跑出来的等级阶梯做标定输入，等于「BOSS 打得轻松 → 玩家提前进阶 → 下一章提前 →
   锚点被压低」，锚点一路走低，收敛到「第 8 章就顶格 Lv240、第 9~10 章永远打不过」的**坏不动点**。
   改为**外生设计阶梯** `L(N) = 24 × N`（= `LEVEL.MAX / CHAPTERS`）：
   第 N 章 BOSS 的目标等级固定为 24N，与模拟无关 ⇒ 标定**确定且可复现**。
2. **章边界单调下限隐含了「敌方基础属性不跨章增长」**：
   原规则「锚点比 ≥ 章内总跨度」在章内总跨度抬到 2.03 后会失真——
   敌方**基础属性本身**跨章增长约 **1.25×/章**（实测 BOSS 基础战力 897 → 6,382），
   字面执行会让难度增速 = 1.25 × 2.03 = **2.54×/章** > 玩家养成 1.03²⁴ = **2.03×/章** ⇒ 没有不动点。
   正确的下限必须按「难度 = 基础属性 × 缩放锚点」折算：
   `anchor[c] ≥ anchor[c-1] × 章内总跨度 × (基础[c-1] / 基础[c])`（基础增速从 `enemies.ts` 实算，不另立常数）。
3. **门槛取「设计等级」→ 末关余量只有 1.0×**：
   改取「**刚好打得赢**」那一档的战力（`minWinnableLevel` 二分）⇒ 末关余量 **1.90×**（≥1.5× 不变量）。
   且门槛必须在锚点**定稿之后**重算——单调下限会抬高锚点，先算门槛会让它与真实难度脱节
   （实测第 3 章门槛点通关率 0%）。

> 上面的 40 天曲线是在**只跑主线**的口径下采的。v10 把五行技能材料 / 三档强化石

> 本轮把**副本刷取**接进 `recalibrate` / `newplayer` 的口径
> （共享实现 `tools/balance/dungeon-loop.ts`，铁律 #4），并补齐了三条硬约束：
>
> 1. **时间单位 = 一段完整会话**（`recalibrate` 1 天/段、`newplayer` 1 小时/段）。
>    一段离线期的有效时长是**一整块**（core 的离线曲线按累计时长折算），
>    期间切去向只会让这一整块按**旧去向**结清 ⇒ 切分只能发生在段与段之间；
>    段内不得让租约生效，否则离线曲线被重跑一遍、有效时长成倍膨胀。
> 2. **三个去向的增益必须同单位**（都取「全队战力相对增幅（ln）」）：
>    主线 = **人均**涨级 × `ln(1.03)`；技能 = 技能等级**总数 ÷ 队伍人数**；
>    强化 = 遗物倍率比 × **已装备遗物的英灵占比**。
> 3. **银两瓶颈必须进增益口径**：副本**只发材料不发银两** ⇒ 一夜能升多少级
>    取决于**买得起多少**，不是「材料够多少」。
>
> 另有两条防死锁约束：**副本必须已解锁**（core 的 `dungeonUnlocked`）、
> **境界门槛上主线是唯一出路**（突破要银两，银两只有主线给 ⇒ 门槛上主线增益 = ∞）。
>
> ⚠ **两处模型口径错**（本轮实测抓出并修掉，记在这里防止再犯）：
> - **技能增益漏了「÷ 队伍人数」** ⇒ 被系统性放大 4~6 倍 ⇒
>   新号开局先刷 6 小时技能副本、主线一关不打（首日进度从第 123 关掉到第 85 关）。
> - **副本难度自适应晚一天生效**（`recalibrate` 里「先决策、后更新难度」的顺序错位）
>   ⇒ 「降一档难度」要等一天才生效，白打一天。

- **`STAGE.SCALE_ANCHORS` / `POWER_ANCHORS` 是标定值**：英灵 / 成长 / 掉落数值变动后

  基线与当前锚点不一致时会拒绝出表并提示重采。

### 6.6 PvP 扩展总原则

**问题定义**：PVE 养成线单调递增（等级、遗物强化只涨不跌），PvP 要求对等。若共用一套数值：

- 付费 5000 元的账号可以碾压所有 0 元账号 → 纯 Pay-to-Win；
- 战力数值无上界，PVP 平衡表永远追不上膨胀的养成曲线 → 无法收敛；
- 中低付费玩家发现"再努力也打不过氪金号" → 直接流失。

**三条候选路线与取舍**：

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A. 直接复用养成值 | PVE 数值原样进 PvP | 实现最省 | 纯 Pay-to-Win，且数值不可收敛 |
| B. 完全独立养成树 | PvP 有自己的独立成长线 | 绝对公平 | 与挂机主循环脱节，玩家视作两个游戏；PVE 养成在 PvP 中贬值 |
| **C. 竞技归一化 + 策略深化（采用）** | 剥离数值性养成，保留并放大策略性养成 | 公平且养成仍有意义 | 需战斗层预留 `BattleContext`（成本低，见 §6.7） |

**核心洞察**：在 PvP 中，养成深度应转化为**策略广度**，而不是**数值大小**。一个 30 级玩家和一个 240 级满养成玩家，在 PvP 战场上的**数值几乎相同**（都是模板值 × 封顶系数），但后者的**可选战术组合更多**——这才是真正的差距来源，且该差距**有上界、可封顶**。

### 6.7 战斗层架构预留（Phase 1 必须落地）

这是整个 PvP 扩展中成本最低、收益最高的一步，**必须在 Phase 1 与基础战斗同时实现**，否则后期需重写整套战斗系统。

```ts
// core/systems/battle.ts
export type BattleMode = 'pve' | 'arena' | 'tower';

export interface BattleContext {
  mode: BattleMode;
  /** 竞技模式下的属性归一化策略；pve 为 undefined */
  arenaProfile?: ArenaProfile;
  seed: number;
}

// core/systems/stats.ts —— 属性解析的唯一入口
export function resolveStats(hero: HeroRuntime, ctx: BattleContext): FinalStats;

// PVE 路径
resolveStats(hero, { mode: 'pve', seed })
  → applyGrowth(等级, 星级) → applyMultipliers(遗物, 技能, 羁绊, 永久加成)

// 竞技路径
resolveStats(hero, { mode: 'arena', arenaProfile, seed })
  → applyArenaTemplate(定位模板) → applyCappedStrategy(星级被动, 技能, 套装, 羁绊)
```

**硬性约束**：

- `resolveStats` 是**唯一**的属性入口。战斗系统内部不得直接读取 `hero.level` 等养成字段。
- `arena` 分支**禁止**引用 `player.permBoost`、`hero.exp`、`relic.level`、`hero.baseStats` 等 PVE 数值字段。
- 该约束由单元测试守护：构造两个 PVE 养成差距 100 倍的账号，归一化后战力差必须 < 15%（见 §15.1）。

### 6.8 竞技归一化公式

**定位模板**（集中在 `core/config/economy.ts` 的 `ARENA_TEMPLATES`，单一调参点）：

| 定位 | atk | def | hp | spd | 设计意图 |
|---|---|---|---|---|---|
| 猛将 | 100 | 50 | 1000 | 100 | 爆发高、容错低 |
| 统帅 | 70 | 60 | 1300 | 110 | 高生存、支援前排 |
| 谋士 | 85 | 45 | 950 | 130 | 高出手、控制 |
| 医者 | 60 | 50 | 1200 | 115 | 续航、稳定 |
| 器者 | 90 | 45 | 1000 | 120 | 持续伤害、异常 |

**养成来源在竞技模式中的处理**（完整映射表）：

| 养成来源 | 竞技模式处理 | 封顶 | 性质 |
|---|---|---|---|
| 等级 | **完全归一化，无效** | 0 | 数值性 |
| 英灵基础属性 | **完全归一化**，用定位模板 | — | 数值性 |
| 星级（被动解锁） | 被动生效，效果系数打折 | 每被动 ×0.6 | 策略性（广度） |
| 技能等级 | 技能效果强度提升 | +30% | 策略性 |
| 宝具解锁 | 解锁后可用，强度走技能封顶 | +30% | 策略性 |
| 遗物本体（选哪个） | 保留，**只取套装效果**，固定标准强度 | 套装效果 ×0.7 | 策略性（搭配） |
| 遗物随机词条 | **完全归一化，无效** | 0 | 数值性 |
| 遗物强化等级 | **完全归一化，无效** | 0 | 数值性 |
| 羁绊 | 保留，系数打折 | ×0.6 | 策略性（编队） |
| 印记 / 材料投入 | **完全无效** | 0 | 数值性 |
| 圣杯重启永久加成 | **完全无效**（且代码层禁止引用） | 0 | 数值性 |

**竞技等级（战术铭文）**——把长期养成转化为有界的战术配置自由度：

```
竞技等级 = f(已解锁被动数, 已解锁技能数, 可用套装数, 图鉴广度)
竞技铭文槽位 = min(3, floor(竞技等级 / 阈值))
```

竞技等级**不直接给任何属性加成**，只增加可装备的「战术铭文」槽位数量（最多 3 个）。铭文是纯策略道具（如"首回合爆发"、"受击反伤"、"低血护盾"）。这让养成投入在 PvP 中的影响是**配置灵活性**，而非数值，且**硬性封顶在 3 个槽位**。

> **实施修正（2026-11，Phase 11 决策闸门实测）——定位模板的绝对量级已重新标定**
>
> 上表的**映射关系（哪些养成进竞技、封顶多少）完全不变**，只改了**绝对量级**：
> 模板整体 ×1.6 攻 / ×1.5 防 / ×0.65 血（`ARENA_TEMPLATES`，见 `economy.ts`）。
>
> 为什么必须改：原表是一组**从未跑过真实竞技对局**的纸面数值。
> 实测（`npm run balance:pvp`，240 场/组）3 人以上的队伍**打不满 30 回合**
> （100% 打满、双方都还活着）→ 战斗循环按回合上限退出 → 胜负停在默认值 →
> **进攻方恒判负**。玩家看到的是「天天挑战失败」：勋章只给 3 枚（胜利 12 枚）、
> 永远拿不到抽卡券。这是**已上线功能**里的缺陷，不是 Phase 11 的事。
>
> 重新标定后的实测：所有阵容的对局都能**真正打完**（兜底判定 0%），
> 回合数落在 6~26（6 人满编最长 38），镜像对局进攻方胜率 48~53.5%。
>
> 为什么改绝对值不影响公平性：竞技是「同一套模板给双方」，绝对值只影响**对局长短**，
> 不影响双方的对称性。定位之间的相对关系保持
> （猛将爆发高容错低 / 统帅高生存 / 谋士高出手 / 医者续航 / 器者持续伤害）。
>
> 配套：`ARENA_CAPS.MAX_ROUNDS = 45`（竞技专属回合上限，比主线宽）；
> 回合上限仍用尽时**按双方剩余血量比例判胜**（依据 `BattleResult.hpById`），
> 并在竞技场页把这条规则写给玩家看。
>
> ⚠ **竞技模板的改动必须跑 `npm run balance:pvp` 复核**（口径与标定见
> [§12.11](phase11-gate.md)），不能只跑主线的 `balance`——主线那套看不见竞技对局。

### 6.9 竞技池与对局公平

- **竞技池 = 系统统一开放全部已上线英灵**，无论玩家是否已抽到。
  - 理由：若"你有没有抽到韩信"影响对局可用性，抽卡就成为 PvP 的付费杠杆——既是 Pay-to-Win，也是合规风险（不得以随机抽取与 PvP 竞争诱导过度消费）。
  - 代价：抽卡在 PvP 中无直接价值。这是**有意取舍**：抽卡动力留在 PVE（收集、图鉴、传记、外观、羁绊深度），PvP 只作为策略竞技与留存手段。
- **双方对称**：同一竞技池、同一模板值、同一铭文槽上限。
- **英灵解锁的差异如何体现**：通过**被动/技能/套装选项的丰富度**（有星级的英雄多几个被动可选），而非数值。

> **实施修正（2026-11，Phase 11 决策闸门实测）——先手权按对局种子掷签**
>
> 「双方对称」不只包括数值：还包括**行动顺序**。
> 竞技单位 id 是 `a_<英灵>` / `e_<英灵>`，同速时 `a_` 恒定排在 `e_` 前
> → **进攻方永远先手** → 镜像对局进攻方胜率 76~93%，对称性在战斗层就已经破了。
>
> 现在竞技模式按**对局种子掷一次签**决定先手权（双方各 50%），`BattleResult.initiativeSide`
> 把本场先手方带出来，供公平性判据度量。PVE 不掷签：我方固定先手是主线
> 「打不过就回去刷」的预期手感。
>
> 不用「按回合奇偶交替」：那样胜负会取决于**最后一回合的奇偶**，
> 实测同一套阵容在不同参数下进攻方胜率在 0.5%~87.5% 之间乱跳（是奇偶，不是实力）。
>
> ⚠ **「对称」与「平衡」是两件事**：掷签保证了双方各 50% 拿到先手（对称），
> 但镜像实测**先手方胜率 88.33%**——**先手值 76.67 个百分点**。
> 也就是说：段位分若现在上真实爬梯，衡量的会是掷签结果而不是战术水平。
> 这是 Phase 11 启动前必须定案的设计项（先手规则 / 后手补偿），
> 详见 [Phase 11 决策闸门](phase11-gate.md)。

### 6.10 匹配、对局与结算

**匹配**：

- 段位分匹配（±1 段位内随机），**不按 PVE 战力分桶**（竞技已归一化，PVE 战力无参考意义）。
- 匹配后**冻结双方阵容快照**（含英灵 id、星级、技能等级、套装、铭文、竞技等级的 hash），战斗使用快照。
- 快照冻结后不可改动——杜绝"看到对手阵容再换阵"。

**对局形式**：**异步竞技场**（挂机游戏的正解）

- 玩家配置阵容 → 作为**进攻方**挑战 N 个防守阵容（爬梯）→ 同时布置一套**防守阵容**供他人挑战。
- 符合挂机定位：玩家只在配置阵容时在线，无需实时在线。
- 实时 PvP 需要服务器 tick、匹配服务、掉线补偿、反作弊，工作量与运维成本远高于收益，列为远期选项（见 §17）。

**结算**：

- 接入后端后，战斗在**服务器端**结算，客户端只提交阵容快照 + 种子，服务端用同一份 `core/systems/battle.ts` 复算并校验 hash。
- **幂等**：以 `challengeId` 去重，重复提交返回同一结果，断线重连不重复扣次数。
- **匹配超时/无对手**：退化为 AI 对手，UI **明确标注"演武"**，不消耗竞技次数、不计段位分。

### 6.11 PvP 产出与经济隔离（数值控制的关键）

PvP 产出**只进竞技专属池**，与 PVE 经济完全隔离：

| 来源 | 可获得 | **不可获得** |
|---|---|---|
| 段位奖励 | 竞技勋章（周上限） | ❌ 银两 |
| 竞技勋章兑换 | 限定头像框、称号、竞技专属外观、**有限**抽卡券（周上限） | ❌ 英灵经验 |
| 竞技周常 | 竞技专属材料（仅用于竞技铭文） | ❌ 遗物强化石 |
| PvP 赛季结算 | 赛季称号、外观 | ❌ 圣杯结晶 |

**理由**：若 PvP 产出回流 PVE 经济，会形成"PvP 变强 → PVE 推进更快 → 战力更高 → PvP 段位更难提升"的正反馈螺旋，直接放大数值膨胀并让 PvP 强度受养成深度支配，违背 §6.8 的隔离原则。

**合规约束**：

- 商城**不得出售**任何"竞技属性/竞技等级/竞技强度"类商品。
- PvP 不得作为付费转化的主要驱动入口；付费入口仅在 PVE 侧（抽卡、通行证、商城）。
- 排行榜需有反作弊与举报通道；玩家数据境内存储。

### 6.12 PvP 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **Phase 1（必做）** | `BattleContext` + `resolveStats(hero, ctx)` 架构预留；`arena` 分支先返回模板值 | 无 |
| **Phase 9** | 竞技场 PVE 天梯（§9.1），段位数据结构先行落地 | Phase 1 |
| **Phase 11** | 异步竞技场：归一化实战、铭文系统、匹配爬梯、防守阵容、后端结算 | Phase 9 + 后端 |
| 远期（可选） | 实时 PvP、赛季 PvP 奖励、竞技专属赛季英灵 | 需专门的后端与运维投入 |

> **注意**：Phase 11 排得较后是有意的。PvP 的平衡需要**真实玩家数据**校准，而团队/项目早期缺乏这类样本。先把 PVE 数值飞轮跑稳，再投入 PvP，是数值游戏的标准路径。

### 7.2 概率（基础概率，游戏内公示到两位小数）

| 稀有度 | 单抽基础概率 | 十连综合概率（至少 1 次该稀有度或更高） |
|---|---|---|
| SSR（传说） | 0.60% | 11.69% |
| SR（史诗） | 5.10% | 100.00% |
| R（稀有） | 24.30% | 100.00% |
| N（普通） | 70.00% | 100.00% |

> 十连保底规则（§7.3 第 2 条）保证十连内至少 1 个 SR 及以上，
> 因此 SR+ / R+ / N 三行的十连综合概率恒为 100.00 个百分点；
> **有区分度的是 SSR 行**（十连内至少 1 个 SSR 的概率）与「当前保底进度下单抽实际概率」。

- 十连至少 1 个 SR+，且**十连内共用大保底计数**。
- **软保底**：第 71 抽起 SSR 概率线性提升，第 90 抽必出 SSR。
- **综合概率公示**：UI 同时展示"基础概率"与"含保底综合概率"两栏；综合概率由 `core` 的 `computeEffectiveRates()` 依据当前保底状态实时计算，**与实际抽卡调用同一函数**，杜绝公示与实现不一致。

> **实施修正（Phase 5）**：原表十连综合概率为 5.73% / 43.62% / 91.25% / 100%，与「十连至少 1 个 SR+」的规则**自相矛盾**——
> 43.62% + 91.25% + 100% 已超过 100%，说明原表把「至少出现 1 次」与「单次出现」混算了。
>
> 实现采用**精确动态规划**（非蒙特卡洛）计算「十连内至少出现 1 次**该稀有度或更高**」：
> `core/systems/gachaRates.ts` 的 `computeTenPullOutcomes()` 对当前保底状态做 10 步 DP，**与实际抽卡调用同一概率源**，
> 因此「公示 = 实际」在构造上成立（零公示噪声），而非统计意义上的近似。
> 上表数值为 `pitySSR = 0`（保底未启动）时的精确值，可由 `tools/balance/tenpull-rates.ts` 复现。
>
> **实测校验**：固定种子 100 万次十连模拟，SSR 综合命中率与 DP 公示值偏差 < 0.041%（4σ 窗口内）；
> 100 万次单抽 SSR 基础率与公示 0.60% 偏差 < 0.01%。两项断言已固化为单元测试（`tests/unit/gacha.test.ts`）。
>
> **同批修正（Phase 6 收尾）**：DP 终态原按「至少出现 1 次**该稀有度**」统计（`hasSR` 只被纯 SR 置位），
> 而公示表头写的是「该稀有度**或更高**」——标签与数值口径不一致，玩家会把 SR 行的 90.51% 误读为
> 「十连出 SR+ 的概率」（实际约 92%），低估自身收益。已改为累计口径（`hasSRPlus` / `hasRPlus`），
> 使**标签与数值严格一致**。
>
> **同批修正（Phase 6 收尾）**：纪元池只收录 SSR/SR，而基础概率表有四档。原实现抽到 R/N 时
> `pickHero` 直接抛错（抽卡崩溃），且公示的 70% N 概率与实际不符（合规问题）。
> 修正为 `projectToPool()`：池内不存在的稀有度，其概率**并入池内存在的最低稀有度**
> （纪元池 → SSR 0.60% / SR 99.40%），公示表按**当前卡池**计算并标注该稀有度是否收录。
>
> 卡池投影另有 9 项断言（`tests/unit/gacha-pool.test.ts`）覆盖「纪元池不崩溃 + 公示 = 实际」。

### 7.3 保底规则（必须显式公示）

1. 大保底计数上限 90 抽，跨所有卡池**继承**，换池不清零（合规要求）。
2. 十连内必出 SR+；若十连内出的是 SR 而非 SSR，SSR 计数 **+2**（补偿常见做法）。
3. 新手期首次 10 连保底 1 个 SSR。
4. 保底进度条常驻抽卡页，显示"距离必出 SSR 还差 N 抽"。

> **实施修正（P0）**。常驻池在零保底进度时，常规十连至少一位 SSR 的概率为 11.69%，首次十连有资格时为 100.00%。两种状态下单抽基础概率都为 0.60%。抽卡执行与十连动态规划共用最后一抽的替换条件，消耗资格后两处公示都更新。

### 7.4 重复处理（合规要点）

| 抽到 | 转化 |
|---|---|
| 新 SSR | 直接获得 |
| 重复 SSR | 50 枚「英灵印记」+ 30 枚该英灵碎片 |
| 新 SR / 重复 SR | 重复 → 12 枚英灵印记 |
| R / N | R → 3 印记；N → 1 印记 + 银两 |

> **实施修正（2026-11，重复 SSR 碎片 10 → 30）**：
> 碎片**不进任何掉落表**（关卡给 0），唯一来源是重复 SSR。
> 实测（真实 `executePull` 蒙特卡洛 400 次，含软/硬保底 + 重复率随收藏增长）：
>
> | 重复 SSR 碎片 | 六人满星（600 枚）中位数抽数 | 对应结晶 | 单人满星（100 枚） |
> |---|---|---|---|
> | 10（改前） | 3,490 抽 | 104.7 万 | 950 抽 / 28.5 万 |
> | **30（改后）** | **1,520 抽** | **45.6 万** | **540 抽 / 16.2 万** |
>
> 改前「六人满星」按纯签到（671 结晶/天）需 **223 周 ≈ 4.3 年**，单人满星也要 61 周——
> 属于「看得到够不着」的目标。改后单人满星 ≈ 34 周、六人满星 ≈ 97 周，
> 收集党的养成目标变得可追，而**六人满星仍保留为长期目标**（不进主线投放，
> 避免把碎片变成第二个「印记」而失去专属件的稀缺意义）。
> ⚠ 关卡**不掉圣杯结晶**，抽卡货币只能靠日常签到（每 7 天 4,700）+ 竞技兑换券（每周 10 张），
>   所以「抽多少」的真正上限是**时间**而非关卡进度。
>
> 数值只改 `src/core/config/economy.ts` 的 `GACHA.DUPLICATE_SSR_SHARDS`；
> 抽卡页与合规页的公示都引用同一常量，自动同步（合规：公示与实现同源）。

**英灵印记**用途（泛化养成，合规的免费替代途径）：
- 兑换任意英灵的等级突破材料、星级碎片、技能材料。
- 兑换"指定英灵自选券"（每月限 1 张），保证重复也有定向价值。

### 7.5 抽卡货币与合规位

| 货币 | 来源 | 性质 |
|---|---|---|
| 圣杯结晶 | 日常/周常/关卡产出 | 主抽卡货币（首发等价于"付费货币"位） |
| 抽卡券 | 签到/成就/兑换码 | 免费补充 |

> **扣费口径（实施修正，Phase 6 收尾 / Phase 7 补齐）**：原实现单抽**同时**扣「圣杯结晶 300 + 抽卡券 1」，
> 与 UI 文案「结晶 300 **或**券 1」矛盾（等于白烧玩家的券），且**完全不校验余额**——
> 结晶可被扣成负数，抽卡总闸门形同虚设。现改为**逐抽计价**：
> - **每一抽**的价是「圣杯结晶 300 **或** 抽卡券 1」——单抽与十连共用同一单价；
> - **十连** = 10 抽 → 结晶 3000 **或** 券 10，**两者可混合**：结算时优先扣结晶，
>   结晶不够的差额用券补（结晶按整抽计价，不足一抽的零头不参与）；
> - **单抽**：结晶 300 **或** 券 1，二选一，优先结晶（主抽卡货币）；
> - **余额不足**：直接拒绝本次召唤，不扣费、不产出，UI 禁用对应按钮。
>
> 判定落在 `core/systems/gacha.ts` 的 `resolvePayment()`（返回 `null` 即余额不足），
> `executePull()` 据此抛 `InsufficientFundsError`，表现层只负责提示。
> UI 上「实际扣哪一项」也**直接取 `resolvePayment()`**，不在表现层复算（铁律 #4）。
> 单测见 `tests/unit/gacha.test.ts` 的「抽卡费用」，E2E 覆盖「结晶耗尽 → 十连改走抽卡券」
> 与「十连混合支付只扣对应余额（结晶 2700 + 券 1）」——后者走真实玩家路径
> （新手 3000 结晶 + 10 券 → 先单抽一次扣掉 300 结晶 → 结晶只够 9 抽，
> 十连必须 9 抽结晶 + 1 张券补齐），断言只扣对应余额、另一项分毫不动。

**预留付费位**：首发无任何真实支付入口，但 `platform/payment` 适配层定义好接口（`createOrder` / `verifyReceipt`），后续接入不改业务逻辑。

**合规页面**（首发即做，内容随真实运营更新）：
- 概率公示页（含基础/综合双栏、保底规则、继承规则、公示日期）
- 抽卡历史记录查询页（近 100 次）
- 理性消费提示、未成年人保护声明、客服与求助渠道
- 用户协议与隐私政策（首发无采集，需明示）

### 7.6 抽卡体验细节

- 十连动画：逐张翻开，可跳过；SSR 特殊演出（光效 + 语音文本）。
- 保底触发时明确提示"大保底触发"。
- 抽卡结果页提供"再来一次 / 前往养成"快捷入口，缩短**抽卡→战力**的反馈链路（关键留存点）。

> **实施修正（抽卡演出落地）**：§1.3 的「不做演出动画」在**抽卡页局部放开**
> （战斗表现仍是数值型轻演出，见 §6.3），并按分级演出实现：
>
> 1. **分级**：SSR → 全屏爆点（光爆 + 放射光束 + 粒子爆炸 + 震屏 + SSR 大字），
>    **独占时间**（爆点没演完，后面的卡牌不翻）；SR → 光晕 + 铃音；
>    N / R → 安静翻开。
> 2. **演出是时间的纯函数 `f(t)`**（同 §6.3 / 铁律 #20）：
>    `presentation/utils/gacha-reveal.ts` 的 `planReveal()` 排事件表，
>    `projectReveal(t)` 推导画面，组件只维护一个时间量 `t`。
>    跳过 = 直接设 `t` 到末尾；模块零 DOM 依赖，可单测（18 例）。
> 3. **音效为 WebAudio 合成**（`gacha-audio.ts`，零素材零依赖）：
>    蓄力嗡鸣 / 翻牌轻响 / SR 铃音 / SSR 轰鸣。
>    **不含任何语音或配音素材**（红线只禁配音，音效是纯合成音）。
>    音频上下文在用户手势内解锁，失败静默降级。
> 4. **演出事实来自 core**：`store.pull()` 返回完整名册 `items`
>    （英灵 id / 稀有度 / 是否新获得），表现层只画不推导。
> 5. **先演后结算**：演完才出结算弹窗（避免弹窗盖住演出）；
>    结算内容不变（新获得英灵 + 印记 / 碎片 / 银两）。
>
> E2E 覆盖「逐张翻牌 → SSR 全屏爆点 → 演完才出结算」与「跳过立即结束」；
> 截图工具 `tools/capture/screenshot.ts --gacha-reveal` 抓蓄力 / 翻牌 / 爆点三帧。

> **实施修正（2026-11，SSR 爆点停住等点击）**：爆点动画放完就切走的话，玩家来不及看清
> 「谁 · 什么稀有度 · 是不是新获得」——高潮反而看不清。最初做的是「驻留 1.8 秒自动继续」，
> 玩家反馈仍然来不及看，于是改成**停住等玩家点击**：
>
> 1. **时间轴在闸门点冻结**：爆点动画结束时刻即**闸门点**（`plan.gates`），
>    时间轴推进到那里就停住，**不自动结束**；`projectReveal(t)` 由 `t` 是否落在
>    闸门点推出 `burst.waiting`（阶段 `'hold'`）——演出状态仍是 `f(t)` 的纯函数。
> 2. **点击才继续**：点画面任意处 = 放行闸门（时间轴解冻，演一小段收束再翻下一张）；
>    右上「跳过」仍是「把 `t` 设到末尾」直接进结算。
> 3. **停住不等于死掉**：组件另有一个**墙钟**只驱动氛围动效（提示脉动 / 光束流转 /
>    卡片浮动），**不参与任何演出事实的推导**；闸门闩锁只是一个「等输入」的布尔量。
> 4. **收束计入总时长**（`duration = releaseEndAt + SETTLE_MS`），
>    不给玩家「画面已经结束但时间没走完」的错觉。
>
> 截图工具产出停住帧（`gacha-reveal-hold.png`）；单测覆盖「闸门点 / 停住语义 /
> 放行后收束 / 纯函数性 / 计入总时长」（26 例）；E2E 断言「停 3 秒也不会自己出结算，
> 必须点一下才继续」。

> **实施修正（2026-11，抽卡随机性）**：本节「概率公示」承诺的是**随机**抽取，
> 但实现里**每一次抽卡的随机序列都是固定的**——实测同一账号三次十连抽到的
> 10 个英灵**完全同序同稀有度**（蔡文姬→徐霞客→赵云→周瑜(SR)→陶渊明→王昭君→
> 曹大家→商鞅→毕昇→范蠡），且**所有玩家一致**。这不是手感问题，而是
> §7.2 的公示概率与实际行为**脱节**（合规硬伤）。根因有两层：
>
> 1. **浮点种子被截断**（根因）：`executePull(..., rng.next())` 传的是 `[0,1)` 的浮点，
>    而 `Rng` 构造函数直接 `seed >>> 0` → 浮点被截断成 **0** → 全部落到兜底常量
>    `0x9e3779b9` → **每次抽卡同一颗种子**。挂机掉落 / 战斗 / 竞技场同理
>    （它们也传浮点种子）。改为：`Rng` 对浮点种子按 2^32 放大，
>    并新增 `rng.nextSeed()` 派生整数种子；store 的 4 个调用点统一改用整数种子。
> 2. **种子写死 + 计数器不落盘**：store 曾写 `new Rng(0x5eed)`，且计数器只在内存里 →
>    刷新页面即回到序列开头（可无限「刷新重抽」）。改为：存档新增
>    `rng: { seed, counter }`（存档版本 4→5），载入时 `Rng.fromSnapshot()` 复原、
>    `persist()` 时同步计数器；新存档的种子来自平台随机源 `platform/random.ts`
>    （表现层不得直接用 `Math.random()`）。
>    **实施修正（服务端权威化）**：**种子由服务端生成并落库**（客户端不再持有抽卡序列，
>    旧档缺种子时由服务端补一条）；观战预览种子用 `hashSeed(seed, 'preview', n)` 域分离派生。
>
> **同批修正**：「是否新获得」原按**批次开始前**的持有快照判定 →
> 同一批里抽到同一英灵两次时两张都算「新获得」：重复转化（印记 / 银两）少给一份，
> 结算弹窗的「新获得英灵」又把同一个人列了两次。改为按**逐张累积**判定
> （`core/systems/gacha.ts` 的 `grantedInBatch`）。
>
> 回归守护：`tests/unit/rng-state.test.ts`（快照复原 / 浮点截断 / 两次十连序列不同 /
> 刷新后不复现）+ `tests/unit/gacha.test.ts`（同批重复按重复转化）
> + E2E「抽卡随机性」（两次十连序列不同、刷新后不复现）。
> 另修一条**靠 bug 才通过**的老用例：「重复 SSR 转化为印记 + 同名碎片」原靠
> 「固定种子恰好抽出项羽」成立，现改为把所有 SSR 放进「已拥有」，不依赖具体序列。

## 9. 竞技场与长循环玩法

竞技场是本作的中长循环载体。当前版本提供归一化镜像试炼和段位天梯。下文保留首发天梯与异步 PvP 的原设计。

> **实施修正（2026-11，当前可玩范围）**：`arena.settle` 由服务端使用玩家自己的阵容快照作为对手，执行归一化战斗并结算分数和奖励。快照按槽位保留套装件数，双方羁绊独立计算，勋章与抽卡券的周计数按北京时间周一零点切换。真人匹配和玩家间异步攻防属于 Phase 11 扩展范围。

### 9.1 PVE 天梯（原首发设计）

**每周一次 PVE 天梯**（首发不联网，AI 梯队模拟）：

- 玩家用自己收集的英灵组成 **3 队**（每队 6 人），依次挑战 3 个敌方梯队。
- 敌方梯队由历史人物组成的**虚构阵营**呈现（仅作为对手形象，定位为"演武场投影"，明确非史实对决，UI 文案需写清是竞技化设定，避免歪曲史实关系）。
- 段位：黑铁 → 青铜 → 白银 → 黄金 → 铂金 → 钻石 → 大师 → 王者，每周结算，赛季重置段位并开放新章节与新英灵。
- 奖励：竞技勋章 + 限定遗物材料 + 头像框（外观向，付费友好）。
- **此模式使用 PVE 完整数值**（正常养成值直接生效），是玩家检验养成成果的舞台。

### 9.2 异步 PvP 竞技场（扩展位，Phase 11）

- 完整设计见 **§6.6–§6.11**。要点复述：竞技归一化数值、竞技池系统统一开放、异步攻防爬梯、产出隔离在竞技专属池。
- 与 9.1 的关系：段位体系共用（同一赛季、同一段位段），但**两个模式的段位分独立计算**——9.1 衡量的是"养成强度"，9.2 衡量的是"战术水平"。二者不互相换算，避免玩家用 PvP 段位去推断自己的 PVE 强度。
- 9.1 的 AI 梯队可作为 9.2 的**训练场与教学场**：新手在 9.1 熟悉阵容搭配，再进入 9.2 竞争。

> 合规提醒：敌方梯队的"历史人物对决"设定必须在 UI 明确标注为架空演武，且不得暗示历史上真实发生过敌对关系（尤其近代国际人物之间）。

3. **遗物淬炼段（Lv60+ 的指数成本）**（2026-11 新增，周目内的**流量阀门**）：

     淬炼是**周目内**阀门（把本轮的收入吃掉）——两者叠加才不会出现「后期资源躺着没人要」。
   - 详见 §5.4「实施修正（后期银两 / 强化石的回收出口）」。

### 12.3 架构原则（实现者必须遵守）

1. **`core/` 纯度**：`core` 内禁止 `import` 任何 DOM/平台 API（`window`、`localStorage`、`document`）。时间通过 `time.ts` 注入，随机通过 `rng.ts` 注入。违反此原则将导致数值脚本无法在 Node 下运行。
   > **实施修正（Phase 8b 收尾）**：注入时钟的目的是**可测试**，不是**冻结时间**。表现层 store 必须注入会走动的 `systemClock`；`ManualClock` 只允许出现在测试代码里。
   > 历史教训：store 曾注入 `ManualClock` 且只在 `load()` 时 `set` 一次，导致整局游戏的 `history.at` / `obtainedAt` / `lastTickAt` 全部等于「页面加载那一刻」——抽卡记录时间戳全部相同，离线结算时长也按页面加载时刻算。排查一次「存档被莫名十连」时，这条冻结时钟让时间线完全对不上，浪费了大量时间。
2. **数据驱动**：新增英灵/关卡/遗物**只加配置不改逻辑**。所有系统逻辑必须遍历配置表，不得硬编码角色 id。
3. **单一数据源**：概率公示、抽卡执行、掉落表、掉落预览必须调用同一函数，不得复制定义（合规硬要求）。
4. **存档版本化**：`save/schema.ts` 带 `version` 与 `migrations: Record<number, (s)=>s>` 链，保证后续更新不丢档。
5. **配置与代码分离**：所有数值常数（曲线、概率、掉落率、乘区上限）集中在 `core/config/economy.ts`，便于调参与审阅。
6. **平台解耦**：`presentation` 不直接调用 `localStorage`，一律经 `platform/`。
7. **属性解析单一入口**（PvP 扩展的关键约束）：所有战斗必须经 `resolveStats(hero, ctx)` 取属性，战斗系统内部**不得**直接读取 `hero.level`、`relic.level`、`player.permBoost` 等养成字段。`ctx.mode === 'arena'` 时走归一化分支（§6.7）。违反此约束将导致 PvP 数值泄漏，破坏公平性——由 §15.1 的隔离测试守护。
8. **养成即配置**：竞技场相关的养成影响只允许通过"战术铭文槽位数量"与"系数封顶表"体现，禁止任何直接数值加成路径。
9. **存档的唯一写入口在服务端**（2026-11 服务端权威化后修订）：服务端是唯一权威真源，客户端**不得**本地算完再整份上传。
   - 任何会改存档的动作都经 `POST /api/action`，由服务端用 `core/systems/actions.ts` 的纯函数执行后落库；
   - `PUT /api/save`（整份覆盖）**已下线**——它是绕过服务端校验与扣费逻辑的旁路；
   - 客户端 localStorage 里的存档降级为**只读缓存**（首屏加速 / 断网查看），不是权威；
   - 客户端**禁止**直接改 `store.save.<字段>`：那会在下一次服务端响应时被覆盖（表现为「点了没反应」）；
     要改存档一律**加一个动作**；
   - 服务端侧：同一账号的动作进 Promise 串行队列，存档与幂等日志**同一事务**落库。
   - **本地缓存按账号分槽位**（`sgw.save.<账号 id>`，槽位名口径取 `core/config/account.ts`）；
     存量单槽位 `sgw.save.main` 是**旧档迁移通道**，新版客户端**禁止**写入
     （`store.persist()` 对该槽位直接跳过）——写进去会让第一个账号把这份新档当旧档导入，
     并占掉一次性迁移标记 `sgw.legacyMigrated`，玩家真正的旧档从此迁不过来（静默丢档）。
   - 自动化（E2E / 工具）读缓存**必须按账号槽位取**，禁止「取第一个 `sgw.save.*` 键」——
     localStorage 的键序不保证，读到哪个槽位是随机的。
   > 历史教训（两代）：① 原 `persist()` 无脑覆写存储，某个拿着过期存档的标签页/脚本一写就把另一方的进度整份抹掉，
   > 且毫无提示；② 改成「客户端算 + 整份上传」后，两台设备进度不一致、重复扣费、并发覆盖接连出现——
   > 根子都是**存档有第二个权威**。现在权威只有一份，冲突问题从根上消失。
   > 附带教训：localStorage 按 origin 隔离——自动化脚本只要访问玩家正在游玩的 origin（`localhost:5173`），
   > 就会与玩家共用同一份缓存。工具侧因此有 `tools/capture/screenshot.ts`（内置 origin 守卫）。
   > 追加教训（2026-11）：服务端权威化后，客户端在**未登录**状态下（槽位还是存量单槽位）
   > 把新档写进了迁移通道——单测与 E2E 当时全绿也看不出来，只表现为「读缓存读到的值随机变化」
   > （实测约 1/3 概率失败）。这类静默数据损坏只有真正跑通真实链路才会暴露。

10. **随机数状态随存档持久化，且种子归服务端**：`SaveData` 带 `rng: { seed, counter }`（存档 v4→v5）。
    种子与计数器必须落盘——只存内存时刷新页面即回到序列开头（玩家可无限「刷新重抽」）；种子不得写死常量
    （所有玩家会抽到完全相同的序列）。服务端权威化后，**种子由服务端用 `node:crypto` 生成并落库**，
    **P0 实施修正（v6）**。回包、缓存和导出使用省略随机状态的投影。观战预览的种子由平台随机源独立产生。
    表现层禁止直接用 `Math.random()`。详见 §7.6「抽卡随机性」实施修正与铁律 #24。

11. **改变存档的编排必须是 core 纯函数，服务端与客户端共用同一份**（2026-11 新增）：
    所有动作写成 `(save, payload, ctx) → ActionOutcome` 的纯函数——先校验后修改（失败即原子）、
    失败不消耗随机序列、收益只经 `rewards` 入库、时间与随机源由 `ctx` 注入。
    动作负载 / 结果 / 错误码表各只有一份（`action-protocol.ts` / `actions.ts` / `game-errors.ts`）。
    新增动作必须同时补齐 `GameAction` / `ActionResultMap` / `HANDLERS` 三处，少一处编译不过。

### 12.4 核心数据结构（存档）

```ts
interface SaveData {
  version: number;
  createdAt: number;
  lastTickAt: number;              // 用于离线结算
  savedAt: number;                 // 最后一次成功写入存储的时间戳（多上下文冲突检测）
  rng: { seed: number; counter: number };  // 随机数状态快照（种子 + 已消耗个数）——刷新后不复现抽卡序列
  player: {
    silver: number; exp: number; shards: Record<string, number>;
    emblems: number; crystals: number; tickets: number;
    skillStones: number; relicStones: number;
    permBoost: number;              // 圣杯重启累计永久加成
    rebirthCount: number;
  };
  heroes: Record<string, HeroState>;   // 已拥有的英灵实例
  relics: RelicInstance[];             // 遗物实例（含随机词条）
  equipped: { [slot: string]: { heroId: string; relicId: string } };
  team: { slots: (string | null)[]; presets: TeamPreset[] };
  gacha: { pitySSR: number; pity10: number; history: DrawRecord[]; pools: Record<string, PoolState> };
  campaign: { clearedStage: number; stageStars: Record<string, number>; chapterProgress: number };
  idle: { currentStage: number; autoAdvance: boolean; totalIdleSeconds: number };
  codes: string[];                      // 已兑换兑换码
  settings: { speed: number; sfx: boolean; skipAnim: boolean };
  stats: { firstStartAt: number; totalPulls: number; totalPower: number };
  // 竞技场（Phase 11；首发仅为 PVE 天梯段位数据）
  arena: {
    tierPoints: number;                 // PVE 天梯段位分
    pvpPoints: number;                  // 异步 PvP 段位分（与 tierPoints 独立换算）
    medals: number;                     // 竞技勋章（竞技专属，不可回流 PVE 经济）
    arenaLevel: number;                 // 竞技等级 → 战术铭文槽位数量
    runes: string[];                    // 已装备的战术铭文（最多 3）
    defenseLoadout: ArenaLoadout | null;   // 防守阵容快照
    snapshotHash: string | null;        // 阵容快照 hash，防止换阵
  };
}
```

**注意**：`arena` 字段与 `player.permBoost`（PVE 永久加成）在架构上严格隔离——竞技快照的生成函数不接收 `player` 对象，只接收显式列出的字段，从类型层面阻断数值泄漏。

**注意（实施修正 · Phase 8b 收尾）**：`savedAt` 是 v4 新增字段，旧档缺失时按 `0` 处理（`0` 永远「不比别人新」，因此旧档首次写入不会被误判成外部更新）。它只服务于**写入冲突检测**（§12.3 第 9 条），不参与任何数值结算。

## 12.6 存档分包与仓库治理（实施修正 · roadmap P1-1）

> 本节是 **P1-1 实施期**追加的设计修正，不改写前文：§12.4 的 `SaveData`
> 仍是 core 层的唯一真源，**分包只发生在「持久化表示」与「线上协议」两层**。

### 12.6.1 为什么分包

遗物是唯一随挂机时长线性增长的存档字段：12 小时离线可积出 **6,720 件**，
整份存档 JSON 约 **1.3 MB**。而心跳每 5 秒一次、每次都整份重写存档并整份回包
→ 写库量与带宽都被遗物数量绑架（实测 ≈ 0.94 GB/小时/玩家）。

### 12.6.2 分包后的形态

| 层 | 内容 | 体积 | 存放 |
|---|---|---|---|
| 存档主体（body） | 玩家 / 英灵 / 编队 / 任务 / 竞技 / 挂机账本 / `relicSeq` … | **与遗物数量无关**（实测 3.6 KB） | `saves.payload` |
| 遗物实例 | 每件一行（uid / defId / level / subStats / locked） | 随件数线性 | `relic_instances`（新增表，schema v4） |
| 客户端投影 | 主体（去权威随机状态）+ **已装备**遗物（≤36 件） | 约 10 KB | 动作回包 / `GET /api/save` |

**core 的 `SaveData` 不变**：动作层看到的仍是完整存档（主体 + 遗物合并后）。
服务端的 `readSaveForUser` 负责把两层合并回一个 `SaveData`。

### 12.6.3 新增只读接口（不改变存档）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/relics` | GET | 仓库分页（`page` / `size` / `rarity` / `setId` / `defId` / `sort`） |
| `/api/relics/stats` | GET | 仓库总件数 + 按遗物定义 id 分组（顶栏件数与图鉴收藏数） |
| `/api/relics/advice` | GET | 遗物推荐预览（与服务端执行 `relic.autoEquip` **同一函数** → 预览 = 执行） |
| `/api/relics/:uid` | GET | 单件遗物详情 |
| `/api/save/export` | GET | 导出存档串（**服务端**产出，含全部遗物） |

### 12.6.4 遗物治理规则

- **库存上限** `RELIC.INVENTORY_CAP = 3000`：超限时自动分解**最没用**的
  （未锁定 → 未装备 → 等级低 → 稀有度低）。
  **锁定件与已装备件永不自动分解**——宁可突破上限，也不销毁玩家标记过的东西；
  溢出全是受保护件时允许突破并上报 `skipped`（不静默吞掉落）。
- **锁定**（`relic.lock`）：语义 = 永不被自动分解（含库存溢出）。
  此前 `RelicInstance.locked` 恒为 `false` 且无动作可置位 → 相关分支不可达。
- **批量动作**：`relic.decomposeBatch` / `relic.upgradeBatch` / `relic.decomposeByFilter`，
  单次上限 `RELIC.BATCH_MAX = 200`（同步执行，不能让事务长时间持锁）。
  契约：**先校验后修改**、锁定件跳过并回报、已装备件先卸下、重复 uid 只处理一次。
- **导出串**：必须由服务端产出（客户端镜像只有已装备遗物，自己拼会丢仓库）。
  超过导入通道上限（`SAVE_IMPORT.MAX_ENCODED_CHARS`）的大档**无法**靠导出串恢复，
  正式恢复路径是**数据库备份**（见 roadmap P1-3）。

### 12.6.5 轻量心跳

心跳（`idle.heartbeat`，每 5 秒一次）：

- **不回传存档主体**（只续约租约、不发奖 → 客户端镜像无需刷新）；
- **只载入「已装备」的遗物**（≤36 件），不拉整张遗物表；
- **不写遗物行**（心跳改不了遗物；若此时同步，会把仓库里其余几千件当成「已删除」抹掉）。

实测（3,000 件遗物）：心跳 6 ms → **1 ms/次**，堆内存无增长。

### 12.6.6 离线结算弹窗阈值（`IDLE.OFFLINE_SETTLE_THRESHOLD_SEC = 60`）

服务端每次进入游戏 / 每次动作都会补算挂机收益（断网期间不损失收益），
但**只有「距上次计量 ≥ 60 秒」才把结算明细回传去弹窗**。

> 少了这道闸门，在线期间每点一下都会弹一次「离线推征结算」：
> 心跳每 5 秒把在线时长按 3 倍倍率记进时间账本，积累够了就在下一次动作里
> 一次性结算——那明明是**在线收益**，不该弹「离线结算」。

收益照算、照落库；只是**不弹窗**。

### 12.6.7 实测基线（`npm run perf:long-hang`，3,000 件遗物 + 满养成 6 人）

| 指标 | 分包前 | 分包后 |
|---|---|---|
| 存档主体（`saves.payload`） | ≈ 1.3 MB | **3.6 KB**（与遗物数无关） |
| 客户端回包 | ≈ 1.3 MB | **10.4 KB**（主体 + 已装备遗物） |
| 12 小时离线补算 | — | **1,067 ms**（2,000 场上限，仓库稳定在 3,000 件 = 上限） |
| 分批结算 4 × 500 场 | — | **1,259 ms** |
| 心跳耗时（3,000 件） | 整份重写 ≈ 6 ms/次 | **1 ms/次**（只读已装备件 + 不写遗物行） |
| 2 小时长挂（1,440 次心跳） | — | **1,313 ms** 累计，**堆内存 19.3 → 19.5 MB**（无泄漏） |
| 数据库文件（3,000 件） | — | **1,188 KB** |

> 复跑：`node --expose-gc --import tsx tools/perf/long-hang.ts --relics 3000 --hours 12 --hang-hours 2`
> （`--expose-gc` 让内存读数可信：不跑 GC 读到的是「还没来得及回收的垃圾」，
> 看起来像泄漏，其实只是 V8 懒得回收。）

## 12.7 新号数值基线（roadmap P1-2）

> 本节是 **P1-2 实施期**追加的基线采集结论，不改写前文。

### 12.7.1 为什么要有这个脚本

`npm run balance` 比的是**战力数字**、`npm run balance:battle` 比的是**满养成**队伍——
两者都跳过了「新号第一分钟到第一天」这段真实体验。玩家实际遇到的是：

> 「新手十连抽到谁」→「第一天能养到什么程度」→「第一个 BOSS 能不能过」→「什么时候能凑出下一次十连」

这段体验此前**没有任何脚本覆盖**，于是「新手卡在第几关」「抽卡资源够不够」只能靠人肉试玩发现。

`tools/balance/newplayer.ts`（`npm run balance:newplayer`）按**真实规则**模拟一个新号：

- 存档从 `createNewSave` 起（新手资源就是 `START_RESOURCES`）；
- 抽卡 / 挂机 / 养成全部走**动作层**（`applyAction`），工具不自己复算规则
  → 改数值时游戏与工具一起变（铁律 #4 单一数据源）；
- 挂机是**真的跑战斗**（`idle.tick` → 逐场回放），不是按时长线性发奖；
- 时间与随机源由脚本注入，core 不读真实时钟（铁律 #1）；
- 逐阵容（4 档稀有度配比）记录：胜率、首次失败关、**回退刷取时间**、
  材料缺口、抽卡资源来源，并输出**每小时成长曲线**；
- 基线落 `artifacts/baselines/newplayer.json`。

### 12.7.2 实测基线（**重标定前**，2026-11，3 个账号 × 4 档阵容）

> ⚠ 本小节的数字是**重标定前**的原始采集记录，保留是为了对照。
> 重标定后的复采结果见 **§12.7.7**。

**首抽**（新手池十连，保底 1 位 SSR）：

| seed=20260106 | SSR 1 / SR 1 / R 2 / N 6 | 圣杯结晶 3,000 | 结晶 0 · 券 10 |
| seed=20260107 | SSR 1 / SR 0 / R 2 / N 7 | 圣杯结晶 3,000 | 结晶 0 · 券 10 |

**第一天成长曲线**（8 小时满效率挂机，seed=20260105，四档阵容走势一致）：

| 小时 | 通关关卡 | 等级 | 编队战力 | 银两 | 经验池 | 仓库 |
|---|---|---|---|---|---|---|
| 1 | 第 19 关 | Lv62 | 6.8×10⁴ | 240 | 0 | 600 |
| 2 | 第 92 关 | Lv106 | 2.2×10⁵ | 58 | 0 | 1,152 |

差异只在个位百分比的战力（1.71×10⁷ ~ 1.85×10⁷）；
**「回退刷取下一级所需时间」在全部 12 个样本里都是 0.0 小时**
——经验富余到连下一级都是瞬间的事。

### 12.7.3 五条发现

1. **首日 5 小时顶格**：等级在第 5 小时就顶到上限，第 6 小时仓库撞到 3,000 件上限，
   首日结束时已过 **第 278 / 310 关（89%）**、第 1 章 BOSS 通关率 100%。
2. **经验与银两彻底贬值**：第 5 小时起经验池以 1.2×10⁹/小时堆积（等级已满，无处可花）；
   银两第 8 小时达 1.7×10⁹。投放回收表印证：**银两回收率 111×**、遗物本体 8.6×。
3. **阵容在首日毫无意义**：从「1 SSR + 5 N」到「全 SSR」四档配比，
   终局**完全一致**（Lv240 / 第 278 关 / BOSS 100%）——首日强度差被养成速度彻底抹平。
4. **抽卡瓶颈不在推征**：首抽吃掉全部 3,000 结晶；**推征不掉圣杯结晶**（只掉经验 / 银两 /
   材料 / 遗物）。第二个十连靠新号自带的 10 张券（正好一个十连），
   第三个要等签到约 **5 天**（7 天循环共 4,700 结晶、日均 671）。
5. **仓库治理规则被真实触发**：第 6 小时撞到 `RELIC.INVENTORY_CAP`，
   溢出自动分解按规则生效（P1-1 的护栏在真实节奏下确实会被用到）。

### 12.7.4 根因（量化）

- **首日挂机预算 = 8 h × 600 场/h = 4,800 场**，而全游戏只有 **310 关**（每章 31 关）
  → 首日预算够把全游戏打 **15 遍**。「能不能通关」因此不是约束，**养成速度**才是。
- 第 1 章一场战斗的经验是 60~140，而一名英灵升 1 级只要 60~254 经验
  → 早期「**1~2 场升 1 级**」。
- 等级战力乘子 1.03/级、全游戏 240 级 → 顶格战力 ≈ 1.03²⁴⁰ = 375× 基础；
  掉落曲线 3.5×/章 与境界经验台阶（1 / 5 / 15 / 40）叠加后，
  **第 10 章一场战斗的经验（7.9×10⁶）≈ 一名英灵从 Lv181 升到 Lv240 全程需求（2.8×10⁷）的 28%**
  ——打 4 场就满级。
- 于是：第 5 小时等级顶格 → 战力顶格 → 第 5 小时已经站在第 10 章。

### 12.7.5 建议的重标定（**已执行**，见 §6.5 实施修正与 §12.7.7）

1. **让「一天的挂机预算」与「全游戏所需场次」同量级**（目前差 15×）。三选一：
   ① 提高单场收益的绝对量级（等级成本 ×15，早期不再是「1~2 场 1 级」）；
   ② 收窄离线满效率时长（`IDLE.FULL_EFFICIENCY_HOURS` 8 → 0.5~1）；
   ③ 加长章节与章内难度跨度（每章 31 关 → 更多），让一章需要反复刷。
2. **章内难度跨度与养成速度对齐**：章内跨度 =
   `IN_CHAPTER_SPAN`(1.087) × `BOSS_MULTIPLIER`(1.15) = **1.25×**，
   而玩家每章养成带来约 2.1× 战力（30 级 × 1.03）
   → 玩家每章比难度多涨 1.68×，十章累积 165×。
3. **掉落曲线与境界台阶重新对齐**：`DROP_GROWTH`（3.5×/章）与养成速度（≈2.1×/章）不匹配。

### 12.7.6 为什么当时没有直接改数值（已在本次提交中解决）

> 以下三条顾虑**全部成立**，也正是本次重标定必须整体重算、不能单独调一个参数的原因。
> 结论与执行见 §6.5 的「实施修正（roadmap P1-2 难度曲线重标定）」。

这三处是**耦合**的，单独改任何一处都会把游戏改坏：

- 单独把 `DROP_GROWTH` 降到与养成速度匹配（3.5 → 2.9），经验总产出从 3.99×10⁸ 掉到
  约 7.7×10⁷，而全游戏需求是 1.77×10⁸ → **回收率跌破 1**，
  玩家永远升不满级、末关不可通（已用 `npm run balance:report` 实测确认）；
- 单独抬高等级成本，会让早期「1~2 场 1 级」变成「30 场 1 级」，首章节奏反而崩；
- 章内难度跨度一旦从 1.25× 提到约 2.1×，相邻章锚点比必须全部 ≥ 2.1，
  而现锚点比只有 1.30~2.93 → 必须按 §6.5 的标定流程**整体重算**
  `SCALE_ANCHORS` / `POWER_ANCHORS` / 等级阶梯 / 掉落曲线。

这属于 §6.5 规定的**难度曲线重标定**，需要独立提交并全量复跑
（`balance` / `balance:battle` / `balance:report` / `balance:newplayer` + 单测 + 全量 E2E），
不适合与 P1-2 的基线采集混在一次提交里。

> **基线留档**：`artifacts/baselines/newplayer.json`（3 个账号 × 4 档阵容 × 24 小时曲线）。
> 后续任何调参都应先重跑 `npm run balance:newplayer` 与这份基线对比，
> 确认「新号第一天」没有再次被数值改动带偏。

## 12.8 厂商中立部署件与运维（roadmap P1-3）

> 本节是 **P1-3 实施期**追加的部署结论，不改写前文。
> **完整手册见 [`deploy.md`](deploy.md)**（托管形态 / 持久化 / 备份恢复 / 回滚 / HTTPS / 兼容性 / 扩容边界）。

### 12.8.1 交付形态

**单实例 + SQLite 持久化卷 + nginx 反向代理**，两个容器：

| 容器 | 镜像 | 职责 |
|---|---|---|
| `api` | `node:24-alpine` | Fastify + `node:sqlite`（Node 内置，零原生依赖） |
| `web` | `nginx:1.27-alpine` | 托管 SPA 静态资源 + 把 `/api` 反代到 api |

- **厂商中立的关键**：前端 API 地址用**相对路径 `/api`**（同源）→ 换域名 / 换托管**不必重新构建**；
  部署件只依赖 Docker + nginx 标准模块 + 一份 `.env`。
- **镜像不携带数据**（库与备份都在命名卷 `sgw-data`）→ 代码回滚与数据回滚互相独立。
- **生产密钥强制**：`SGW_JWT_SECRET` 没设时 compose 直接拒绝启动（`${SGW_JWT_SECRET:?}`），
  服务端在 `NODE_ENV=production` 且密钥为默认值时也拒绝启动。

### 12.8.2 备份 / 恢复演练（已实测）

- 备份用 SQLite 的 `VACUUM INTO`（一致性单文件快照），
  **不直接复制 `.db`**——库开着 WAL，直接复制会漏掉未落盘的事务，复制中有写入还会得到撕裂文件；
- 恢复**必须停服**，并且**必须**删掉 `-wal` / `-shm` 伴生文件（旧 WAL 会被重放回新库）。

演练（真实服务端 + 真实存档）结论：

| 验证项 | 结果 |
|---|---|
| 备份时库内容 | `users 1` · `sessions 1` · `saves 1` · `action_log 9` · `relic_instances 3` |
| 恢复后登录 A（备份点之前） | `200` —— 数据完好 |
| 恢复后登录 B（备份点之后） | `401` —— 被回滚 |
| 恢复后仓库遗物数 | `3`（与备份时一致） |

### 12.8.3 浏览器兼容实测（2026-11-18）

用「**引擎 + 限速**」近似真机：Safari → Playwright WebKit；微信 Android → X5/Chromium；
低端 Android + 4G → Chromium + 4 倍 CPU 降速 + CDP 4G 限速。

| 配置 | 登录页 FCP | 登录后首页 FCP | 渲染 | 脚本错误 |
|---|---|---|---|---|
| 低端 Android（4× CPU + 4G） | 1,140 ms | 1,632 ms | 正常 | 0 |
| 微信内置浏览器（Android + 4G） | 1,092 ms | 1,500 ms | 正常 | 0 |
| Safari 引擎（WebKit，**未限速**） | 112 ms | 162 ms | 正常 | 0 |

- 传输体积为**未压缩值**（95 KB / JS 91.8 KB）；nginx 开 gzip 后 JS 约 **55 KB**。
- WebKit 无 CDP 限速 → 该行只证明**引擎兼容性**，不代表弱网表现；
  真机（微信 iOS/Android、低端安卓机）仍需人工补测（清单见 `deploy.md` §10.3）。

## 12.9 每日任务与周目标（roadmap P2-1）

> 本节是 **P2-1 实施期**追加的结论，不改写前文。

### 12.9.1 任务表：四条来源、两个周期

配置在 `src/core/config/tasks.ts`（纯数据，新增任务只加配置），
逻辑在 `src/core/systems/tasks.ts`（纯函数），执行在 `core/systems/actions.ts`
（`daily.claimTask` 动作，服务端权威）。

| 周期 | 条目 | 来源口径 | 目标 | 重置 |
|---|---|---|---|---|
| 每日 | 推征 30 场 | `battle` | 30 | 北京时间 0 点 |
| 每日 | 完成 1 次召唤 | `pull` | 1 | 同上 |
| 每日 | 强化遗物 2 件 | `relicUpgrade` | 2 | 同上 |
| 每日 | 每日签到 | `signIn` | 1 | 同上 |
| 周目标 | 累计推征 200 场 | `battle` | 200 | 北京时间周一 0 点 |
| 周目标 | 累计召唤 5 次 | `pull` | 5 | 同上 |
| 周目标 | 累计强化遗物 15 件 | `relicUpgrade` | 15 | 同上 |

- **计数按 `metric:period` 分桶**（`battle:daily` / `battle:weekly` …）：
  同一个行为同时推进每日与每周两个口径，但两者重置边界不同 → 不能共用一个数。
- 每条任务带**引导路由名**，任务页能一键到对应玩法（铁律 #10）；
  路由名对不对由 E2E「点前往真的跳过去」守护，不靠静态清单。
- 计数来自**真实动作**（召唤 / 推征 / 遗物强化 / 签到），客户端不自己上报进度。

### 12.9.2 服务端权威的累计与领取

| 场景 | 处理 |
|---|---|
| 跨日 / 跨周 | 周期归属字段（`taskDay` / `taskWeek`）与当前周期不一致 → 该口径的计数与领取记录清零 |
| 断线重试 | 动作带 `actionId` → 服务端幂等日志重放，同一个 id 不会发两次奖 |
| 重复领取 | 换一个 `actionId` 再领 → 服务端按「本周期已领取」拒绝（`TASK_ALREADY_CLAIMED`），资源不变 |
| 换设备 | 进度存在存档里 → 服务端权威，另一台设备看到同一份进度与领取状态 |
| 未完成 | 拒绝（`TASK_NOT_COMPLETED`），**先校验后修改**：存档一字节未变 |

领取时的顺序是「**先滚动周期 → 再校验 → 最后才改**」：
不先滚动的话，昨天没领的每日任务今天会被重复领取。

### 12.9.3 三条红线的量化核对

roadmap 要求任务奖励「没有冲击抽卡间隔、养成资源回收或竞技产出隔离」。
三条都不是靠承诺，而是靠**类型与数字**：

1. **抽卡间隔**：任务奖励类型 `TaskReward` 里**没有** `crystals` / `tickets` 字段
   → 编译器挡住「顺手加个结晶」。任务奖励里的圣杯结晶与抽卡券恒为 **0**，
   抽卡节奏仍只由签到决定（签到 7 天 4,700 结晶）。
2. **养成资源回收**：只发强化石与术式结晶，且日投放被 `validate:config` 卡在
   **每小时挂机产出的 2% 以内**。实测：
   - 任务日投放：强化石 38.3 · 术式结晶 17.1
   - 每小时挂机产出（第 1 章 × 600 场）：强化石 2,700 · 术式结晶 1,200
   - 占比 **1.42% / 1.43%**（分母是**一小时**的挂机产出）
   - 首周（7 天）后回收倍数：术式结晶 2.11× → 2.19×，遗物强化石 1.57× → 1.63×
     （主线投放是一次性的，日常投放每天都有，天数为 D 时线性上升）
3. **竞技产出隔离**：任务奖励不含任何竞技资源 → 竞技产出仍然只有竞技场一个来源。

### 12.9.4 本轮没做什么

- **没有**改签到奖励表（签到是抽卡节奏的唯一来源，动它就是动抽卡间隔）；
- **没有**做「任务连击 / 连续完成加成」——那会让每日任务变成**必须**完成，
  与「任务是引导不是门槛」相悖；
- **没有**把任务进度接到竞技场（竞技产出隔离，不混算）；
- **没有**做任务奖励的「抽卡券」选项（券是抽卡资源，等于动抽卡间隔）。

## 12.10 PVE 长线挑战 · 三队天梯（roadmap P2-2）

> 本节是 **P2-2 实施期**追加的结论，不改写前文。

### 12.10.1 玩法定案：3 队 × 3 梯队，每周一轮

| 项 | 定案 | 出处 |
|---|---|---|
| 结构 | 玩家组 **3 队**（各 6 人），依次挑战 **3 个敌方梯队**；一轮 = 3 场战斗 | `core/config/ladder.ts` |
| 频率 | **每周一轮**（北京时间周一 0 点切换），一轮定胜负 | `arena.ladderChallenge` + `lastSettledWeek` |
| 数值口径 | **PVE 完整数值**（等级 / 星级 / 遗物强化 / 羁绊 / 永久加成全部生效） | `core/systems/ladder.ts` 的 `ladderContext` |
| 段位分 | 写入 `arena.tierPoints`（**PVE 天梯段位分**），与 `arena.pvpPoints` 独立换算 | §9.2 |
| 赛季 | 4 周一赛季；赛季结算按 **40%** 保留段位分（软重置） | `LADDER.SEASON_WEEKS` / `SEASON_CARRY_PCT` |
| 回流 | 离线 ≥ 3 天判为回流，30 天冷却；奖励含养成材料 + 竞技勋章 | `LADDER_RETURN_REWARDS` |

**敌方梯队全部是非历史人物**：原案（§9.1）写的是「历史人物组成的虚构阵营」，
与本项目的敌人合规红线（`config/enemies.ts`：**敌人一律为灵体 / 妖异 / 幻想体 / 器械造物**）冲突
→ **以合规红线为准**：梯队改成「**演武场投影**」，UI 明确标注为架空演武。

**段位分的归属被拆开了**（这是一次口径修正，不只是加功能）：

- `arena.tierPoints` = **PVE 天梯段位分** → 由 `arena.ladderChallenge` 独占写入；
- `arena.pvpPoints` = **归一化对战分** → 由 `arena.settle`（镜像试炼）独占写入。

此前镜像试炼同时写两个分，段位是「养成强度」与「战术水平」的混合物，
§9.2 要求的「二者不互相换算」根本没成立。现在两个模式各写各的。

### 12.10.2 三条红线的量化核对

| 红线 | 怎么守住的 | 实测 |
|---|---|---|
| **积分与奖励隔离** | 天梯产出白名单只有 `medals` / `arenaMaterials`；赛季奖励只含勋章 / 竞技材料 / 称号 | 挑战后银两 / 经验 / 强化石 / 术式结晶 / 圣杯结晶**全部不变** |
| **不冲击抽卡间隔** | 回流奖励不含圣杯结晶 / 抽卡券（`validate:config` 静态挡） | 回流奖励里的结晶 = 0、券 = 0 |
| **不冲击养成回收** | 回流日均投放 ≤ 每小时挂机产出的 2%（与任务同一把尺） | 强化石 **0.19%** · 术式结晶 **0.56%** |

产出隔离还有一处**结构性的**修正：镜像试炼的 `arenaMaterials` 此前只出现在结算结果里、
**从未入库**（`resolveArenaRewards` 返回了但没人存）。现在 `arena.arenaMaterials`
进了存档，与天梯共用同一份**周预算**（`weeklyMedals` / `weeklyMaterials`）——
两个模式各发一份却各算各的上限，玩家一周实际能拿到的会是上限的两倍。

### 12.10.3 推进节奏与三队养成成本（真实战斗模拟标定）

`npm run balance:ladder` 跑**真实战斗**（不是比战力数字）。
标定口径：对每一层的参考队伍（该层预期养成水平）二分敌方缩放，
使梯队 1 / 2 / 3 的通关率落在 **90% / 65% / 40%**。

| 层 | 参考养成 | 梯队 1 | 梯队 2 | 梯队 3 |
|---|---|---|---|---|
| 0 | L10/2★ | 93% | 66% | 31% |
| 1 | L31/2★ | 93% | 63% | 35% |
| 2 | L62/3★ | 93% | 74% | 43% |
| 3 | L78/3★ | 96% | 78% | 45% |
| 4 | L108/4★ | 92% | 72% | 54% |
| 5 | L133/4★ | 88% | 63% | 38% |
| 6 | L164/5★ | 89% | 66% | 52% |
| 7 | L193/5★ | 93% | 69% | 45% |

> ⚠ **缩放必须逐梯队独立标定**。最初试过「层锚点 × 梯队位系数」，
> 实测把缩放从 0.75× 提到 1.0×，通关率就从 90% 直接掉到 0%
> ——6v6 里敌方血量与攻击同时放大，玩家既打不动也被秒，曲线陡到乘系数压不住。
> 最终配置是 8 层 × 3 梯队 = 24 个独立锚点（`LADDER.SCALE_ANCHORS`）。

**推进节奏**（满编一周 2,000 分）：青铜 1 周、白银 1 周、黄金 1 周、铂金 2 周、
钻石 4 周、大师 8 周、**王者 15 周**（≈ 3.8 个赛季）。半程打法则翻倍。

**三队养成成本（roadmap 明确要评估的那一项）**：同一层内，
「三支队伍用同一批英灵（省钱打法）」vs「三支不同队伍（标准打法）」的
平均通关率差 **-3 ~ -20 个百分点（平均约 -13）**——

> **结论：三支独立队伍的边际收益不显著，甚至更差。**
> 所以「跨队复用同一名英灵」是**允许**的（编队校验只禁止「同一队内重复」）。
> 玩家不必为三队天梯额外养 12 个英灵，但后两个梯队会更难打——
> 这是设计选择，不是 bug，界面上写明了。

### 12.10.4 服务端权威的周期滚动

赛季结算与回流判定都是**惰性**的：不需要后台定时任务，
每次服务端入口（载入 / 动作）都调一次 `rollLadderPeriods(save, now)`
（`core/systems/ladder.ts`，服务端只负责**调用**，规则不另写一份）。

| 场景 | 处理 |
|---|---|
| 首次参与 | 赛季从当前周起算（`season = 1`，`seasonStartWeek = 当前周`） |
| 赛季切换 | 段位分按 40% 保留；发放赛季奖励（勋章 / 竞技材料 / 称号）；赛季积分清零；赛季号 +1 |
| 跨多个赛季 | 逐个结算（一次动作里结算 N 个赛季） |
| 每周一轮 | `lastSettledWeek === 当前周` → 拒绝（`LADDER_ALREADY_SETTLED`） |
| 回流判定 | 距上次活跃 ≥ 3 天且已过 30 天冷却 → 置位 `returnPending` |
| 换设备 | 全部在存档里 → 服务端权威 |

**「上次活跃时间」由服务端在每次入口刷新**（含心跳）。
若只按「真实动作」刷新，一个挂着页面三天不点任何按钮的玩家会被误判成回流。

⚠ 顺带修掉一个**会静默丢档**的坑：导入失败时服务端手里捏着一份刚建出来的空档，
把它落库就会让账号「有存档了」→ `save.import` 之后被 `IMPORT_FORBIDDEN` 拦下，
玩家真正的旧档**再也迁不过来**。现在导入失败**不落库**。

### 12.10.5 本轮没做什么

- **没有**做「赛季排行榜 / 赛季榜」——排行榜要真实玩家样本，属于 Phase 11 的范围；
- **没有**把天梯接入竞技场的铭文系统（铭文本身是 Phase 11 的能力）；
- **没有**做「天梯扫荡 / 一键跳过」——每周一轮的定位就是要玩家认真摆阵；
- **没有**做赛季商店（商城不得出售任何「竞技属性」类商品，见 §6.11 的合规约束）。

### 12.11.3 闸门挖出并修掉的两个已上线缺陷

采集器不是走过场——它挖出了**当前版本就存在**的两个竞技场缺陷：

1. **多队伍镜像对局恒判负**：归一化模板偏「肉」，3 人以上队伍打不满 30 回合 →
   双方都还活着 → 胜负停在默认值 → 进攻方恒负（实测 3 人队进攻方胜率 **0.0%**）。
   玩家天天「挑战失败」，勋章只给 3 枚、永远拿不到抽卡券。
2. **进攻方恒定先手**：同速时 `a_` 恒定排在 `e_` 前，违反 §6.9 双方对称
   （镜像对局进攻方胜率 76~93%）。

修法与标定见 §6.8 / §6.9 的实施修正。修完：镜像对局进攻方胜率 48~53.5%、
兜底判定 0%、回合 6~26。

## 12.12 资源 / 背包 / 材料副本（资源/背包版本 v10）

> **本章是 v10 的唯一设计基线**。它**取代**本文档里更早章节关于
> 「抽卡券 / 英灵印记 / 玩家经验池 / 术式结晶 / 遗物强化石」的描述
> （§5 数值系统、§10 资源与经济、§12.9 每日任务、§12.10 天梯产出白名单）。
> 那些章节保留原样是为了留痕，**口径以本章为准**。
> 详细设计与逐步实施记录见
> [资源背包设计](resource-backpack-design.md) /
> [资源背包实现](resource-backpack-implementation.md)。

### 12.12.1 为什么要收敛

老口径下钱包有六种通用数值（银两 / 圣杯结晶 / 抽卡券 / 英灵印记 / 术式结晶 /
遗物强化石）+ 一个玩家经验池。后果是：

- **同名不同义的坑**：`player.exp`（玩家经验池）与 `hero.exp`（英灵升级进度）
  混过一次（技能升级把两者搞混，扣了 `player.crystals`）；
- **大量材料没有专属来源**：术式结晶与遗物强化石由主线均匀投放，
  产出与消耗节奏对不上（回收比 7.33× / 16.74×，结构性过剩）；
- **玩家看不出「这个材料从哪来、为什么不够」**。

### 12.12.2 收敛后的资源模型

| 类别 | 位置 | 内容 |
|---|---|---|
| **钱包数值** | `player.<字段>` | **只有银两 + 圣杯结晶**（顶栏只显示这两项） |
| **背包堆叠物** | `save.items[<道具 id>]` | 通用经验书（2 档）× 五行技能材料（5）× 遗物强化石（3 档） |
| **同名碎片** | `player.shards[<英灵 id>]` | 按英灵分堆（形状天然不同，不进 `items`） |
| **退役字段** | — | 抽卡券 / 英灵印记 / 玩家经验池 / 术式结晶 / 遗物强化石 |

- 道具登记唯一出处：`src/core/config/items.ts` 的 `ITEM_DEFS`
  （类型是 `Record<ItemId, ItemDef>` → **新增 id 而没登记 = 编译期报错**）。
- 数值（面额 / 每级消耗 / 档位区间 / 升星所需）只在
  `src/core/config/economy.ts`。
- `save.items` 是**完整表**（零值填充）：**显式 0 必须被尊重**，
  否则玩家清空背包后物品被自动补回。`START_ITEMS` 只由 `createNewSave()` 发放。
- 旧余额按 `LEGACY_CONVERSION` 折算后**只读保留**（不发放）：
  券 → 圣杯结晶、印记 → 银两、术式结晶 → 玩家自选五行材料、
  遗物强化石 → 玩家自选石档（`legacy.allocateMaterials` 动作）。

### 12.12.3 养成链路的扣费口径（全部改过）

| 养成动作 | 旧 | 新 |
|---|---|---|
| 喂经验 | 扣玩家经验池 | 扣**经验书**（`hero.feedBooks`） |
| 升技能 | 扣术式结晶 + 银两 | 扣**该五行技能材料**（12 个）+ 银两（800） |
| 升星 | 扣同名碎片 + 英灵印记 | 扣**同名碎片**（20/星） |
| 境界突破 | 扣英灵印记（10/20/40） | 扣**银两**（20,000 / 40,000） |
| 遗物强化 | 扣通用强化石 | 扣**目标等级所属档**的强化石 + 银两 |
| 分解遗物 | 返还银两 + 强化石 | **只返还银两** |

> **实施修正（喂书结果的语义）**：`FeedBooksResult.applied` 曾写成
> `expConsumed + expRemaining`，而 `expRemaining` 是英灵**全部**存量经验 ——
> 每次喂书都把存量重报一遍（喂 10 次虚报 10 倍），界面显示的「投入经验」是错的。
> 现在 `applied` = **本次投入**（`booksUsed × 面额`），存量另走 `expRemaining`。

### 12.12.4 材料副本（两类材料的唯一来源）

- **平行配置**：`src/core/config/dungeons.ts` + `src/core/systems/dungeons.ts`。
  副本**不进 `STAGES`**（那里有三处硬约束，混进去会破难度标定的不变量）。
- **8 个变体**：技能副本 × 5（五行）+ 强化副本 × 3（初阶 / 中阶 / 高阶）；
  **3 档难度**取材主线第 1 / 4 / 8 章，产量倍率 1.0 / 1.6 / 2.6。
- **元素主题落在「产出材料」上，不落在敌人上**（敌人池五行分布不均，
  换敌人会脱离已标定的难度锚点）。
- **副本胜利只发所选材料**；**不写 `campaign`**（进度与主线分开记账）。
- **解锁判定在 systems 层**：技能副本要「该五行有可升技能的英灵」，
  强化副本要「持有该档解锁线以上的遗物」（初阶 1 / 中阶 60 / 高阶 130）。
  ⚠ **强化副本的解锁线必须用服务端统计的仓库最高等级**
  （`dungeonUnlocked(save, variant, { maxRelicLevel })`）：
  客户端镜像里 `save.relics` **只有已装备件**（存档分包）→
  直接从 `save.relics` 取会把「已解锁」误判成「未解锁」；
  统计**没读到之前不下结论**（按钮置灰 + 「正在读取仓库信息…」）。
- **三个去向共用一份挂机时间账本**：主线 / 技能副本 / 强化副本。
  切换时服务端**先按旧去向结清**再换新去向，剩余预算**结转**（不清零）。
- **战败即停并给「降一档难度」建议**，界面必须把这个出口摆在玩家眼前。
- **副本场次不计入「推征」任务口径**。

### 12.12.5 背包页（「铸造」页升级为「背包」）

- 路径 `/forge` 与路由名 `forge` **全部保留**（E2E / 截图工具 / 任务跳转都不用改），
  `/backpack` 是别名，两者 `meta.tab` 都是 `forge` → 底部标签栏高亮一致。
- **5 个分类**：遗物 / 技能材料 / 强化材料 / 经验书 / 卡碎片。
  分类与筛选条件写在 **URL query**（`?tab=…&element=…`），
  从英灵页 / 遗物页跳进来能「自动带入相关筛选」。
- **闭环**：材料 → 副本直达（`backpack-go-dungeon-<道具>`），
  碎片 → 升星入口（`backpack-shard-<英灵>`），
  经验书 → 直接投喂（预览走 core 的 `previewFeed`）。
- **「强化材料」页只统计编队内可强化的遗物数** —— 客户端镜像里只有已装备遗物，
  不拿它冒充全仓库统计。

### 12.12.6 主线首通结晶

- 首通发**圣杯结晶**（普通关 / 章末 BOSS 两档，数值在 `economy.ts` 的
  `FIRST_CLEAR_CRYSTALS`），这是结晶的重要来源之一。
- 判定用 `campaign.clearedStage` **高水位** + `campaign.creditedStages` 记账，
  跨设备 / 跨重启天然幂等。
- **服务端一次性补发**（`FIRST_CLEAR_COMPENSATED_FLAG`）：旧档迁移到 v10 时，
  服务端按高水位补一次历史首通结晶；**不在迁移里做**（迁移是纯函数，
  服务端才有权威水位）。

### 12.12.7 数值待策划确认

| 项 | 位置 | 本轮先取的值 |
|---|---|---|
| 小 / 大经验书面额 | `economy.ts` `EXP_BOOK` | 1,000 / 10,000 |

### 12.12.8 本轮顺带修掉的既有缺陷

1. **`normalizeItems` 以 `START_ITEMS` 为起点且只在 `n > 0` 时写入**
   → 玩家清空背包后物品被**自动补回**（背包永远清不空）。
   现改为**全 0 起点 + 尊重显式 0**。
2. **`FeedBooksResult.applied` 把存量经验重复计入**（见 §12.12.3）。
3. **`FeedBooksResult` 在 `core/systems/growth.ts` 与 `core/systems/actions.ts`
   各写一份** → 两处必然分叉。现统一为 `growth.ts` 独家，`actions.ts` 转出。
4. **强化副本的解锁判定用了客户端看不见的数据**：`dungeonUnlocked` 从
   `save.relics` 取最高等级，而客户端镜像里 `save.relics` **只有已装备件**
   → 玩家明明有 Lv60 遗物，副本页却一直显示「当前最高 Lv0」且按钮点不动。
   现改为服务端统计仓库最高等级并显式传入。
5. **背包页的五行反推用错口径**：`def.id.replace('skillMat','')` 得到的是英文后缀
   （`Fire`）而游戏内五行是中文（`火`）→ 「去副本」跳错副本 + 五行筛选全置灰
   + 可用英灵统计恒 0。现统一走 core 的 `itemElement()`。
6. **副本页把内部 id 当玩家文案显示**（`relicStoneTier1`）→ 改为
   core 的 `dungeonVariantLabel()`（显示「初阶」）。
7. **模板里残留 markdown 粗体语法**（截图验收发现，单测与 E2E 全绿也没拦住）：
   Vue 模板**不渲染 markdown**，`**只发所选材料**` 会被**原样印给玩家**（8 处）→
   改为 `<b>…</b>`，顶栏资源弹窗复用合规页那份 `richParts` 解析器；
   新增铁律 #50 与 `tests/unit/ui-text.test.ts` 守护。
8. **经验书是「概率 × 数量」投放**，早期章节出书率只有 10%~73%
   → 「一场一定有书」是错的假设。E2E 改为**有界重试 + `test.slow()`**，
   规则本身交给确定性单测 `tests/unit/drop-table.test.ts`（出书率 ≈ 配置概率）。

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/auth/register` | POST | 注册并直接签发令牌；用户名不区分大小写 |
| `/api/auth/login` | POST | 用户不存在与口令错误返回**同一**错误码（防账号枚举） |
| `/api/auth/refresh` | POST | refresh token 轮换（旧 token 立即吊销） |
| `/api/auth/logout` | POST | 吊销 refresh token |
| `/api/auth/me` | GET | 当前账号 |
| `/api/action` | POST | **动作入口**：`{ actionId, action }` → 服务端执行 core 动作层并落库，回 `{ ok, result, save, offline }` |
| `/api/save` | GET | 拉取**服务端权威存档**（规范化后的版本 + 离线结算明细）；404 = 该账号还没有存档 |
| `/api/save/export` | GET | 导出存档串（服务端产出，含全部遗物；见 §12.6） |
| `/api/relics` | GET | 遗物仓库分页（见 §12.6） |
| `/api/relics/stats` | GET | 遗物统计（仓库总数 / 按定义分组 / **仓库最高等级** —— 强化副本解锁线要用，客户端镜像里看不见仓库） |
| `/api/relics/advice` | GET | 遗物推荐预览（与服务端执行同源） |
| `/api/relics/:uid` | GET | 单件遗物详情 |
| `/api/account` | DELETE | 注销账号，级联删除账号 / 会话 / 存档 |
| `/api/health` | GET | 健康检查（Playwright webServer 等待就绪用） |

> ⚠ **`PUT /api/save` 已下线**：整份覆盖是一条绕过服务端校验的旁路，
> 留着它「服务端权威」当场失效（谁都能整份覆盖存档）。写入只有 `POST /api/action` 一条路。

**安全要点**：口令用 scrypt(N=16384) + 随机盐哈希，`timingSafeEqual` 比对；access token 为 HS256 JWT（载荷只含 sub + username），refresh token 只存 sha256；同一「用户名 + IP」窗口内失败 5 次后 429；动作接口按账号窗口限流（阈值在 `core/config/account.ts`）。

**权威与幂等口径**：
- 同一账号的动作进 Promise 串行队列（`server/src/game/lock.ts`），跨账号并行；
- 存档与幂等日志**同一事务**落库，避免「扣了费却没记日志 → 重试再扣一次」；
- **P0 实施修正**。`actionId` 记录随账号保留，成功结果在 24 小时内可重放，超期仍防重。失败动作可重试。心跳不占用业务动作的幂等记录。
- **P0 实施修正**。账号删除以服务端确认为准，客户端随后清除该账号的本地会话、缓存并回到登录页。
- `GET /api/save` 和普通动作入口可按服务端时钟补结算挂机收益。在线领取、离线领取与心跳按 §5.7 的时间账本处理，心跳只计量与续约。
- 旧档导入通过 `save.import` 校验，仅对尚无云档且未迁移的账号开放。迁移标记与导入结果一并落库，重连通过重新拉取权威档恢复操作。

| 存档迁移 | 旧版本存档升级后数据无损 |
| 配置校验 | id 唯一、引用存在、数值区间、无禁用词 |

**PvP 数值隔离测试（Phase 11 必过项，且 Phase 1 即需守护架构约束）**：

| 测试 | 断言 |
|---|---|
| **养成隔离** | 构造 PVE 养成相差 100 倍的两个账号（如 240 级满强化 vs 1 级裸装），`resolveStats(hero, {mode:'arena'})` 输出的**总战力差 < 15%**；且 `pve` 模式下两者战力差 > 50 倍（证明测试本身有效） |
| **永久加成屏蔽** | `player.permBoost` 变化对 `arena` 模式结果**零影响**（静态检查：`arena.ts` 不出现 `permBoost`） |
| **遗物强化屏蔽** | 遗物 60 级 vs 1 级，`arena` 模式下除套装效果外**零差异** |
| **封顶系数生效** | 技能加成不超过 +30%、套装效果不超过 ×0.7、羁绊不超过 ×0.6 |
| **竞技池对称** | 双方在 `arena` 模式下可用英灵集合完全相同，与玩家是否拥有该英灵无关 |
| **竞技等级只改槽位** | 提升竞技等级**不改变任何属性数值**，只增加铭文槽位（≤3） |
| **产出隔离** | 竞技结算产出的资源集合与 PVE 资源集合**无交集**（银两/经验/强化石/结晶 均为 0） |
| **快照不可变** | 匹配冻结后修改阵容，`snapshotHash` 校验失败，对局按原快照结算 |
| **幂等结算** | 同一 `challengeId` 重复提交结果一致、不重复扣次数 |
| **段位独立** | `tierPoints` 与 `pvpPoints` 互不换算、互不影响 |

### 15.2 E2E（Playwright）

1. 新玩家首启 → 完成 3 步引导 → 首次十连 → 获得 SSR → 放入阵位 → 挂机 10 场 → 领取收益 → 战力上升。
2. 抽卡页 → 打开概率公示 → 两栏数值与单测断言一致。
3. 注入 12 小时时间差 → 重启页面 → 离线结算弹窗数值正确。
4. 换编队 → 羁绊面板与战力数值即时变化。
5. **（Phase 11）** 竞技场配置阵容 → 提交进攻 → 匹配到防守阵容 → 对局结算 → 段位分变化 → 竞技勋章入账；且 PVE 侧银两/经验/强化石**数值未变**（产出隔离）。

### 15.3 PvP 公平性验收（人工 + 抽样）

- 抽样 200 组真实对局（若样本不足则用模拟对局替代），统计：
  - 段位越高胜率越接近 50%（无跨段位碾压）；
  - 使用同一阵容、仅养成投入不同的两个账号，对局胜率差 < 15 个百分点；
  - 不存在"某个特定英灵/套装"胜率显著偏离 50%（若偏离 > 8 个百分点，说明该组合过强，需调封顶系数）。
- 抽样 100 组"付费强度差距最大"的对局，验证低付费方仍有合理胜率空间。

### 15.4 性能与稳定性

- 战斗渲染 60fps（4× 倍速下不低于 30fps）。
- 挂机 2 小时内存不持续增长（日志与战报需截断，只保留最近 N 条）。
- 首屏可交互 < 3s（4G 模拟），首包 < 1.5MB（占位图阶段）。
- 无 console error；Safari/Chrome/微信内置浏览器/移动端适配通过。

### 15.5 合规验收（人工）

- 概率公示两栏齐全、精度两位小数、公示日期可见。
- 历史人物文本逐条过审：无贬义定性、无史实错误、无历史虚无表述。
- 敌人与 BOSS 全部为非历史人物，无任何指向真实历史人物的命名或形象。
- UI 全站无绝对化用语（跑禁用词扫描脚本）。
- 无真实支付入口、无诱导性文案。
- **（Phase 11）** 商城无任何"竞技属性/竞技强度"类商品；PvP 入口不被用作付费转化主路径；排行榜有举报通道；玩家数据境内存储。

## 16. 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| **范围过大**（单人开发） | 做不完 | 强制分阶段；Phase 0–6 完成即是一个可玩切片；美术占位优先；内容后置 |
| **Fate IP 边界** | 下架/律师函 | 不使用职阶制/职介卡/令咒/原作设定名词与美术；文案过禁用词扫描 |
| **历史题材审核** | 拒审 | 敌人非历史人物；文本中立；首发池避开近现代争议人物；每条史实可溯源 |
| **抽卡合规** | 整改/下架 | 公示与实现同源函数；保底继承；不拆角色强度；十连保底；历史记录可查 |
| **内容产能**（72 英雄 × 传记） | 拖期 | 分级投入：SSR 全文 / SR 2-3 段 / R-N 一句；配置与文本分离，可分批补 |
| **AI 立绘史实错误** | 口碑与合规 | 人工校验清单 + 禁用/替换机制；占位图先行不阻塞开发 |
| **数值后期崩坏** | 流失 | 独立乘区 + 飞升/圣杯重启 + 投放回收表 + 蒙特卡洛卡点分布模拟 |
| **无付费导致无收入** | 商业不可行 | 首发定位为"玩法验证 + 玩家测试"，预留支付适配层；商业化在二期 |
| **海外名人中文语境** | 舆论风险 | 传记只述史实；中立措辞；不做民族/宗教争议评价；不与真实国别对抗绑定 |
| **PvP 数值泄漏**（PVE 养成值混入竞技场） | 公平性崩塌，付费碾压 | `resolveStats` 单一入口 + `arena` 分支禁止引用养成字段 + 隔离测试（§15.1）守护 |
| **PvP 产出回流 PVE 经济** | 数值飞轮失控、PvP 反被养成支配 | 竞技专属池硬隔离，产出集合与 PVE 资源集合无交集，由测试断言 |
| **PvP 平衡缺少真实数据** | 上线即失衡，玩家流失 | 排期到 Phase 11；Phase 10 先用模拟做预校；无真实样本前不开放匹配 |
| **实时 PvP 的运维成本** | 拖垮单人开发节奏 | 首发只做异步竞技场（配置阵容即离线），实时对战列为远期可选 |
| **竞技池统一开放削弱抽卡动力** | 收集欲下降 | 有意取舍：抽卡动力留在 PVE（图鉴/传记/外观/羁绊深度）；用 PvP 的策略深度与段位奖励补偿留存 |

## 17. 未决决策（可在实施中确认，不阻塞开工）

1. **云存档**：~~首发是否需要跨设备同步？~~ **已定**：首发即**服务端权威**（跨设备同步是基本要求，见「实施修正（2026-11：服务端权威化 CS 架构）」）。
2. **兑换码**：首发用内置一次性代码表（纯前端）还是直接上后端核销？建议内置表。
3. **遗物词条数量**：初版 4 主词条 / 3 副词条，还是精简到 3 / 2 以降低配置量？建议 3 主 / 2 副起步。
4. **战斗表现投入**：自研 Canvas 渲染器 vs 首版 DOM+CSS 降级。见 Phase 6 决策点。
5. **SSR 是否分池限时**：首发建议全常驻（无 UP、无限定强度差），后期运营再引入——限时池会引入保底继承与强度差的复杂合规面。
6. **英灵是否提供"第二形态"（真名解放/宝具解放）**：是，但强度提升必须走印记/材料路径而非抽卡重复，以满足 10% 合规线。
7. **PvP 的落地范围与节奏**：本方案已按"首发 PVE 天梯 + Phase 11 异步竞技场"排期。需确认的是——**是否接受首发不含实时 PvP**（推荐接受：实时对战的服务器/匹配/反作弊成本与单人开发不匹配），以及 PvP 是否值得占用 Phase 11 的资源（若 PVE 内容仍不足，可把该阶段让给内容扩充）。
8. **竞技池开放策略**：本方案建议"系统统一开放全部英灵"以保证绝对公平。替代方案是"按玩家拥有度加权"（未拥有的英灵数值打折而非禁用），能保留抽卡动力但公平性变复杂且更接近 Pay-to-Win——**不建议**。
9. **竞技等级与铭文的曲线**：§6.8 只给了"槽位 ≤3"的上限，具体阈值（竞技等级如何由养成折算、铭文强度）需在 Phase 10 用模拟定档。
10. **段位分跨模式换算**：本方案让 `tierPoints` 与 `pvpPoints` 完全独立。若产品侧希望"PVE 天梯段位能作为 PvP 匹配参考"，需引入有损换算——会增加匹配复杂度，需权衡。

## 18. 立即可执行的第一步

```bash
cd 超级圣杯战争
npm create vite@latest . -- --template vue-ts
npm i && npm i -D vitest @playwright/test
# 然后按 Phase 0 建 core/ 骨架
```

首个交付物应是 `core/` 纯逻辑层 + `tests/unit` 全绿 + `tools/balance/simulate.ts` 能打印出"第 1 章 30 关的难度曲线 vs 1 名 SSR 的养成曲线"两张对比图——这两张图是整个数值设计的地基，也是 Phase 1 之前唯一必须先看到的东西。

同时在 Phase 1 必须一起落地的还有 **PvP 架构预留**（`BattleContext` + `resolveStats(hero, ctx)`）：这是全案最容易被漏掉、且一旦漏掉代价最高的一步。漏做的后果不是"少个功能"，而是后期要重写整套战斗系统。
