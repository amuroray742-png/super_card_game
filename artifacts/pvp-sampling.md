# 对局样本采集方案（roadmap P2-3 · Phase 11 决策闸门配套）

> 本文是 [Phase 11 决策闸门](phase11-gate.md) 的配套件。
> 闸门要回答「证据够不够、能不能启动 Phase 11」，而**证据的形式是一批对局样本**。
> 本文定义「采什么、怎么采、存哪、留多久、谁能看」，
> 判据与阈值的**代码口径**在 [`src/core/systems/pvp-sample.ts`](../src/core/systems/pvp-sample.ts)。

---

## 1. 两类样本，分工不同

| 类型 | 来源 | 作用 | 不能回答的问题 |
|---|---|---|---|
| **合成样本** | `npm run balance:pvp`（本地模拟，不连服务器） | 验证**判据管线本身**可用；发现结构性偏差（如先手偏差）；在真实样本到位前守住回归 | 「真实玩家会不会这样打」——合成对手是脚本摆的，不含人类策略 |
| **真实样本** | 服务端权威结算时落库（**当前未开启**） | 回答「真实玩家的养成差距/胜率分布长什么样」，这是启动 Phase 11 的**硬前提** | — |

⚠ **合成样本永远不能替代真实样本做「是否启动 Phase 11」的最终决策**。
合成样本的作用是：闸门判定时，先确认「我们连测量管线都还没有」这件事，
以及把**结构性/系统性偏差**在零真实玩家成本的前提下先挖出来。

---

## 2. 样本口径（单一来源）

字段定义在 `src/core/systems/pvp-sample.ts` 的 `PvpMatchSample`，
真实采集与合成采集**必须**能填出同一组字段。口径不允许各写一套：

| 字段 | 含义 | 真实链路怎么取 |
|---|---|---|
| `challengeId` | 对局唯一 id | 服务端动作层生成（幂等键） |
| `group` | 分组标签 | 由采集器按实验设计打标（真实链路按「同段位/同竞技等级」分桶） |
| `attackerWin` | 进攻方是否获胜 | `ArenaMatch.result.win` |
| `initiativeSide` | 本场**先手方** | `ArenaMatch.result.initiativeSide`（core 产出，**不得自行推断**） |
| `rounds` | 回合数 | `ArenaMatch.result.rounds` |
| `attackerSurvivorRatio` / `defenderSurvivorRatio` | 双方存活单位占比 | 由 `roster` + `survivors` 推导（`sampleFromArenaMatch`） |
| `attackerPower` / `defenderPower` | 双方**归一化**总战力 | 双方单位 `computePower` 之和（竞技口径，非 PVE 战力） |

> ⚠ 战力必须是**竞技口径**（`resolveStats(mode:'arena')` + `computePower`）。
> 存 PVE 战力会得到「高养成方战力 100 倍」这种**正确但无用**的数字，
> 反而掩盖了「归一化后还差多少」这个真正要问的问题。
>
> ⚠ `initiativeSide` 必须取自 core 的对局结果：竞技模式按对局种子**掷签**决定先手
> （§6.9 双方对称），**先手方 ≠ 进攻方**。自己推断「谁先手」会拿到假数据，
> 先手偏差这一整条判据就成了摆设。

## 3. 判据与阈值

阈值集中在 `PVP_SAMPLE_THRESHOLDS`（不散落到工具、文档、测试三处）：

| 判据 | 阈值 | 含义 | 依据 |
|---|---|---|---|
| 样本量 | ≥ 200 | 低于此数量的胜率结论**不可用于决策** | 统计常识 + plan.md §15.1 |
| 归一化后战力差 | ≤ 15% | 养成差距在竞技场被压平 | §15.1「养成隔离」 |
| 进攻方胜率偏差 | ≤ 5pp | 进攻/防守不存在系统性优势 | §15.1「胜率偏差」（阈值为本项目提案） |
| 先手偏差 | ≤ 5pp | 先手方与后手方胜率之差 | roadmap P2-3「双方先后手」（阈值为本项目提案） |

> ⚠ §15.1 只给了「养成隔离 < 15%」这一条数值阈值，其余三条是本项目按
> 「镜像对局应当五五开」反推的**工程口径**，真实玩家样本到位后要按真实分布复核。

判定函数：`evaluatePvpFairness(samples, { exclude })` → 逐条判据 + 总判定。
- 先手 / 后手胜率**由样本自己算**（`initiativeSide` + `attackerWin`），
  不接受外部传入的「先手胜率」——传进来就等于让调用方自己算判据，判据失去意义；
- `exclude` 用于跨阵容实验：两队本来就不一样强，
  「进攻方胜率偏差」在那种样本上没有意义，必须**显式排除**，
  否则会把「B 队更强」误报成「引擎不公平」。

## 4. 真实样本采集方案（**本轮不落地玩法，只出方案**）

### 4.1 采集点

**只在服务端的权威结算点采集**（`POST /api/action` 执行竞技动作成功之后），
不采客户端上报的数据。原因与铁律 #11 同源：客户端数据不可信，
一旦允许客户端上报对局结果，榜单与段位分立刻可被伪造。

### 4.2 开关（默认关闭）

- 采集开关是**服务端环境变量**（如 `SGW_TELEMETRY=1`），默认**关闭**。
- 默认关闭的理由（plan.md Phase 9「埋点（默认关闭）」）：试玩阶段不需要无差别收集，
  需要时按需开启、限定窗口（如「只在新版本灰度期间开启 14 天」）。
- 关闭时**不产生任何写入**，也不影响结算耗时。

### 4.3 存储

- 独立表 `pvp_samples`，与玩家存档**分表存放**——存档表是业务真源，
  样本表是可丢弃的观测数据，混在一起会让「删样本」变成「删存档」。
- 字段：样本口径字段 + `created_at` + `season` + `tier` + `arena_level`（分桶用）。
- **不留存**：账号 id（用一次性 hash 关联，见 4.4）、用户名、玩家自由文本。

### 4.4 脱敏与合规

| 项 | 口径 |
|---|---|
| 身份 | 用 `hash(accountId + 赛季盐)` 作为关联键；盐每赛季轮换，跨赛季不可串联 |
| 玩家可见 | 玩家自己的对局记录**对自己可见**（可查胜率、对手、先后手） |
| 他人可见 | 段位分可见，**逐场战斗详情不可见**（避免针对个人刷针对） |
| 存储位置 | 境内存储（与存档同库，沿用部署形态） |
| 留存期 | 赛季结束后 **30 天**清理原始样本；聚合指标长期保留 |
| 举报通道 | 举报入口挂在战报页（Phase 11 实施时一并落地，本方案先定口径） |
| 商城约束 | 商城不得出售任何「竞技属性/竞技等级/竞技强度」类商品（§6.11） |

### 4.5 采样偏差（**必须主动规避**）

只收「高段位玩家的对局」会得到一份**乐观偏差**的样本（低段位玩家的策略被漏掉）。
因此分桶口径固定为：`段位 × 竞技等级 × 时间窗`，**每桶都要有样本**，
闸门判定时按桶分别判定，不允许只看全量汇总。

## 5. 采集器自检（合成样本能干什么）

`npm run balance:pvp` 跑三组实验：

| 实验 | 设计 | 能发现什么 |
|---|---|---|
| **E1 养成隔离（镜像）** | 两个 PVE 养成差 100 倍的账号（Lv240 满强化 vs Lv1 裸装），**竞技快照相同**，镜像对打 | 归一化是否真的压平养成差距；镜像对局是否五五开；**先手值多少**（镜像里唯一的变量就是先后手） |
| **E2 跨阵容（描述性）** | 两套不同定位配比的阵容互打 | 阵容强度分布；**战力公式能不能预测胜负**（本轮实测：归一化战力差 2.25%，胜率却是 3.75% vs 97.92% —— 不能） |
| **E3 策略宽度（描述性）** | 同一支队伍的两种养成档（1★1技能 vs 5★18技能） | §6.8 封顶后的策略修正带来多少差距（这部分是**有意保留**的策略广度，不是数值泄漏） |

⚠ 合成样本的已知局限：
- 对手是脚本摆的，**不含人类的针对性换阵**；
- 种子是固定的，**不代表玩家实际的随机性**；
- 因此合成结果只能用于「发现结构性 bug」，**不能用于「宣称公平」**。

> 💡 合成样本的价值已经被验证过：它挖出了两个**当前版本就存在**的竞技场缺陷
> （多队伍镜像对局恒判负、进攻方恒定先手），详见
> [决策闸门 §2](phase11-gate.md)。

## 6. 验收方式

| 层级 | 验收 |
|---|---|
| 单测 | `tests/unit/pvp-sample.test.ts`：样本口径、汇总统计、逐条判据的判定逻辑（含边界与空样本） |
| 合成链路 | `npm run balance:pvp` 可复现（固定种子），产出 `artifacts/baselines/pvp-sample.json` |
| 真实链路 | **Phase 11 实施时**才存在：多账号真实攻防 E2E（§15.2 第 5 条） |

---

## 7. 已知限制

- 本轮**没有**真实玩家样本：试玩尚未开展，样本表与开关均未落地；
- 因此 [Phase 11 决策闸门](phase11-gate.md) 的结论只能是「**测量基建可启动、玩法启动需等真实样本**」；
- 合成样本的 E1/E2/E3 结论会随竞技配置（模板值、封顶系数）变化，**改配置必须重跑**。
